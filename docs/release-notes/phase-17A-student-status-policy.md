# Phase 17A: 원생 휴원/퇴원 상태 정책 설계 및 정의 (보정 반영본)

본 문서는 튜링음악학원 DayDay 시스템에서 원생의 재원, 휴원, 퇴원 상태가 시스템의 핵심 도메인(출결, 수강료, 교재, 메시징, 대시보드)에 미치는 비즈니스 규칙과 영속 데이터 모델 후보군을 정리하고 조율하기 위한 정책 검토 문서입니다.

---

## 1. 현재 원생 상태 구조 파악 (Current State Analysis)

* **현재 데이터 스키마 상태**:
  * `state.js` 내의 `students` 데이터베이스 시드 데이터에는 상태(`status`)를 지정하는 필드가 존재하지 않습니다.
  * 기존 구조에서는 모든 원생을 활성 재원생으로 암묵적으로 인지하고 있습니다.
* **기존 원생 필터링 및 관리**:
  * 원장 원생 관리 화면 (`membersView.js`)에서 전체 원생을 단순 노출하고 있으며, 상태에 따른 필터링(예: 휴원생만 보기, 퇴원생 제외하기 등)은 아직 설계되어 있지 않습니다.
  * *비교*: 강사(Staff) 관리의 경우 `employmentStatus === 'resigned'`(퇴사) 상태 구분이 도입되어 있으며, 퇴사한 강사는 선택 목록에서 제외되고 이름 옆에 `(퇴사)` 식별 배지가 부여되는 동작이 존재합니다. 원생 또한 이와 유사하게 도메인별 영향성을 고려한 상태 관리가 요구됩니다.

---

## 2. 상태 정의 후보 (Status Category Candidates)

원생의 상태는 3가지 기본 분류를 우선하며, 확장 후보군은 별도로 분류하여 검토합니다.

### A. 핵심 상태 분류 (Phase 17B 최소 구현 대상)
1. **재원 (`attending` / `active`)**:
  * **의미**: 현재 학원에 등록하여 수업을 듣고 있는 정상 재원생.
  * **기본 기준**: 신규 출결 생성 대상, 수강료 및 교재비 청구 대상, 모든 알림 및 메시지 수신 대상.
2. **휴원 (`on_leave` / `hold`)**:
  * **의미**: 개인 사정(질병, 방학, 장기 여행 등)으로 일정 기간 수업을 일시 중단한 원생.
  * **기본 기준**: 휴원 기간 중 신규 출결 체크 대상 제외 후보, 신규 수업 배정 및 수강료/교재 청구 유보 후보 (단, 과거 미납 이력 추적은 유지).
3. **퇴원 (`withdrawn` / `inactive`)**:
  * **의미**: 정식으로 학원 등록을 해지하고 학업을 종료한 원생.
  * **기본 기준**: 신규 출결 및 수납 청구 대상에서 제외 후보. 단, 과거 기록(기존 출결, 기존 수납 내역)은 소급을 위해 이력으로 보존.

### B. 확장 후보군 (후속 검토 대상)
* **대기/상담중 (`waitlist` / `consulting`)**:
  * 아직 입학하지 않았으나 등록 예정이거나 상담을 진행 중인 예비 원생. 수강료 청구 및 출결 체크에서는 제외되나, 상담 예약 문자나 사전 마케팅 발송 후보군으로 활용 가능.

## 3. 휴원 정책 (Leave of Absence Policy 후보)

* **휴원 스케줄링**:
  * 휴원 등록 시 **휴원 시작일**과 **휴원 종료일**(예정일) 및 휴원 사유를 입력받아 관리하는 방안을 검토합니다.
* **출결 제어 후보**:
  * 휴원 기간에 포함되는 날짜에는 일일 자동 출결 생성 및 체크 대상에서 해당 원생을 제외하는 정책을 후보로 제안합니다. 과거 휴원 전 출결 기록은 손상 없이 그대로 조회/보존됩니다.
* **수업 일정**:
  * 매칭되어 있던 수업 요일 및 시간 정보는 데이터 무결성을 위해 삭제하지 않고 유지하되, 출석부 렌더링 시 "휴원" 표시를 띄우고 신규 체크 동작을 비활성화하는 형태를 검토합니다.
* **수납 및 청구 (운영 정책 조율 필요)**:
  * 휴원 중 정기 수강료 청구 제외 후보 및 부분 월 일할 계산 후보 처리는 학원 운영 방식, 약관 및 환불/이월 정책과 밀접하게 연결되므로, 상세 비즈니스 룰은 후속 Phase에서 조율 및 정의합니다.
  * 휴원 등록 전 발생한 기존 미납액에 대해서는 휴원 중에도 유지되어 조회 가능하도록 설계합니다.
* **메시지 및 학부모 포털**:
  * 메시지 발송 기본 목록에서 제외 후보로 관리하며, 학부모 포털 로그인 시 메인에 휴원 기간 안내 배너를 띄우는 UX를 검토합니다.

## 4. 퇴원 정책 (Withdrawal Policy 후보)

* **퇴원일 및 사유 기록**:
  * 퇴원 처리 일자와 사유(이사, 학원 이동 등)를 기록하여 이탈 통계 구축에 활용할 수 있도록 합니다.
* **이력 데이터 보존 의무**:
  * 원생 데이터를 데이터베이스에서 물리적으로 즉시 삭제(Delete)하지 않습니다. 과거의 회계 내역(수납 완료 기록), 등하원 기록 및 발송 로그와의 참조 무결성을 위해, 원생 정보를 보존한 채 상태값만 전환하는 **논리적 비활성 상태 전환** 정책을 고수합니다.
* **과거 기록 보존 및 신규 생성 제한**:
  * 퇴원 완료 이후 시점부터 발생하는 신규 출결 생성 및 신규 청구서 발행 대상에서 후보 제외 처리합니다.
  * 퇴원 이전에 생성된 과거의 모든 출결 이력, 수납 이력, 기 지급 완료된 교재 이력은 보존 및 조회가 정상 가능해야 합니다.
* **재등록 및 원복**:
  * 퇴원생이 재등록할 경우, 과거 이력을 유지한 채 상태만 `attending`으로 복귀시키고 신규 등록일(`enrollDate`)만 업데이트하여 누적 관리할 수 있도록 설계합니다.

## 6. 메시징 영향 (Messaging System Impact 후보)

* **수신자 리스트 기본 필터**:
  * 메시지 발송 화면의 좌측 수신자 지정 리스트는 기본적으로 **재원생(`status === 'attending'`)**만을 조회 및 선택 타겟으로 지정하는 정책을 제안합니다.
  * 단, 방학 특강 모집이나 재등록 안내 발송을 위해 **"휴원생 포함"** 및 **"퇴원생 포함"** 필터 스위치를 조회 옵션 후보로 배치합니다.
* **상태 식별 배지 및 최종 발송**:
  * 검색을 통해 휴원/퇴원생을 수신자로 임의 추가하는 경우, 최종 발송 검토 모달의 수신인 목록에 `[휴원]`, `[퇴원]` 배지를 명시적으로 노출하여 오발송을 보완합니다.
  * 휴원/퇴원생에 대한 최종 발송 실행 허용 여부는 학원 운영 권한/정책에 따라 차단하거나 경고 후 전송하도록 결정합니다.
* **자동 알림 생성 제외**:
  * 태블릿 등하원 알림, 미납 자동 알림 등 백그라운드 스케줄러를 통한 자동 `parentMessages` 생성 대상에서 휴원/퇴원 원생을 제외하는 정책을 후보로 설정합니다.

## 7. 수납/청구 영향 (Billing & Payment Impact 후보)

* **휴원 중 수강료 처리 후보**:
  * 휴원 기간에 따른 당월 정기 청구 제외 후보 및 부분 월 일할 계산 후보는 학원별 환불/이월 약관 정책에 따라 유연하게 연동되어야 하므로 후속 개발 단계에서 세부 규칙을 구체화합니다.
  * 휴원 전 발생한 기존 미납금에 대해서는 감면/조정 처리 여부를 원장이 수동으로 조율하기 전까지는 채권 상태를 그대로 유지합니다.
* **퇴원생 미납 채권 보존**:
  * 퇴원하더라도 퇴원 전에 미납한 기존 수강료 및 교재비 청구서 정보는 회계 장부상 미수금 통계에 보존되어야 합니다.
  * 퇴원 시점 이후 추가로 발행되는 신규 청구서 자동 발행 대상에서는 제외되도록 차단 필터를 구성합니다.

## 8. 데이터 모델 후보 (Data Model Proposal)

기존 `students` 레코드 구조에 탑재할 상태 변경 영속화 모델 제안입니다.

```json
{
  "status": "attending", // attending (재원), on_leave (휴원), withdrawn (퇴원)
  "statusChangedAt": "2026-06-17T11:00:00.000Z",
  "leaveStartDate": "2026-07-01", // 휴원 시작 예정일 (없으면 null)
  "leaveEndDate": "2026-07-31",   // 휴원 종료 예정일 (없으면 null)
  "withdrawalDate": null,         // 퇴원 처리 일자 (없으면 null)
  "statusReason": "개인 사정 및 병가", // 상태 변경 세부 사유
  "statusHistory": [              // 회계/상담 분쟁 대응을 위해 권장하는 히스토리 로그 배열
    {
      "fromStatus": "attending",
      "toStatus": "on_leave",
      "changedAt": "2026-06-17T11:00:00.000Z",
      "reason": "병가로 인한 7월 휴원 신청",
      "operatorId": "USR_DIR_DEMO"
    }
  ]
}
```

* **`status`**: 원생의 현재 핵심 상태를 나타내는 문자열. (attending / on_leave / withdrawn 3종 우선)
* **Soft Delete 금지 및 비활성 상태 전환**:
  * 물리적인 레코드 삭제는 원천 차단하며, 회원 탈퇴나 퇴원 시 데이터 참조 무결성을 보존하면서 목록 노출을 제한하기 위해 `status` 변경을 통한 논리적 비활성 상태 전환 구조를 적용할 후보로 설정합니다.

## 9. 위험 및 주의사항 (Risks & Precautions)

> [!CAUTION]
> **데이터 참조 결함 예방을 위한 주의사항**
> 
> * **물리적 삭제의 위험성**: 퇴원생 데이터를 DB 테이블에서 `DELETE` 처리할 경우, 과거 출결 통계 및 수납 완료 금액, 발송 히스토리 조인 시 참조 키 오류(Foreign Key Violation 등)가 발생해 전체 통계 보고서가 오작동합니다. 반드시 `status: 'withdrawn'` 상태 기반으로 조절해야 합니다.
> * **이력 관리 유무**: 상태 변경 날짜(`statusChangedAt`) 및 변경 히스토리(`statusHistory`) 없이 현재 단일 상태값만 가지고 제어할 경우, 과거 월(月) 단위 청구액 소급 계산 시점이나 과거 미납금 조회 시에 과거의 상태를 알지 못해 청구 요금이 오계산되는 치명적 회계 버그가 생기므로 상태 전환 히스토리를 추적하는 것이 강력하게 권장됩니다.

## 10. 후속 Phase 제안

* **Phase 17B: 원생 상태 데이터 모델 최소 구현**:
  * 로컬 DB `students` 스키마 마이그레이션 적용 및 `status` 필드 기본값(`attending`) 데이터 적재 로직 구축.
* **Phase 17C: 원장 원생 관리 UI 상태 변경 기능**:
  * `membersView.js` 내 원생 상세 페이지에 휴원/퇴원 처리 버튼 및 사유/기간 입력 폼과 정렬 필터 추가.
* **Phase 17D: 출결/수업 일정 반영**:
  * 휴원/퇴원 상태에 따른 일일 출석부 대상 신규 생성 및 체크 자동 필터링 및 과거 출결 이력 조회 보존 처리.
* **Phase 17E: 수납/청구 반영**:
  * 휴원생 수강료 면제/감면 처리 후보 조율 및 퇴원생 익월 청구 금지 배치 스크립트 모사 구현.
* **Phase 17F: 메시지 보내기/자동 메시지 필터 반영**:
  * 메시지 발송 대상 검색 시 재원/휴원/퇴원 필터 기능 활성화 및 자동 push/parentMessages 대상 제외 후보 구현.
* **Phase 17G: 대시보드/오늘 콘솔 반영**:
