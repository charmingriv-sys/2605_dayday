# Phase 16S 설계 정의서: 모바일 Push 토큰 및 앱 설치 상태 연동 설계

본 문서는 학부모 포털 앱 및 웹앱에서 실시간 모바일 푸시 알림을 발송하기 전 필요한 앱 설치 상태 판별, 푸시 수신 권한 상태 관리, 디바이스 토큰 수집 및 저장 구조, 토큰의 수명 주기(만료/갱신), 그리고 알림 이력 테이블(`parentMessages.pushStatus`)과의 전이 흐름을 규정하는 설계 정의서입니다.

> [!IMPORTANT]
> 본 Phase 16S 단계는 **문서 설계 전용 Phase**입니다. 실제 모바일 하이브리드 앱 패키징/배포, FCM/APNs 연동 라이브러리 탑재, Web Push Service Worker 작성 및 토큰 수집 스크립트 작성 등은 **이번 범위에 포함되지 않으며** 향후 푸시 개발 Phase로 위임합니다.

---

## 1. Phase 16S 범위 정의

### 1) 포함 범위 (In-Scope)
* **학부모 앱 설치 상태 판별 설계:** 단말기 접속 및 권한 수집 상태에 기반한 앱 상태 추론 기준 수립.
* **푸시 권한 상태 설계:** 운영체제(OS) 및 웹 브라우저의 알림 권한 획득 여부 트래킹 구조.
* **디바이스 토큰 저장 구조 설계:** 다중 기기 사용자 대응을 위한 DB 토큰 테이블 구조 정의.
* **연락처/메시징 모델 연동 설계:** `parentContacts` 및 `parentMessages`, `parentMessageSettings`와의 상호 관계 정의.
* **pushStatus 상태 전이 설계:** 알림 발송 결과에 따른 pushStatus 상태 머신 후보 정의.
* **토큰 만료/갱신/무효화 정책:** 토큰 생명 주기 제어 정책 및 실패 누적 기반 토큰 만료 처리 검토.
* **보안/개인정보 고려:** 토큰 암호화 및 알림 내용 내 민감정보 노출 방지(잠금화면 마스킹) 가이드라인.
* **구현 단계 제안:** 향후 개발 단계별 로드맵 제시.

### 2) 제외 범위 (Out-of-Scope)
* **실제 모바일 앱 배포:** 구글 플레이스토어 및 애플 앱스토어 배포 빌드 배제.
* **실제 FCM/APNs 연동 구현:** 백엔드 푸시 서버 연동 및 실물 API 통신 모듈 개발 배제.
* **실제 Web Push Service Worker 구현:** 브라우저 백그라운드 스크립트 작성 배제.
* **실제 Push API 호출:** 실전송 발송 패킷 전송 로직 배제.
* **앱스토어/플레이스토어 설치 여부의 하드웨어 레벨 판별:** 단말 내부 파일 구조 역추적 판별 불가.
* **SMS/카카오 알림톡 채널 연동:** 문자 및 알림톡 API 연동 설계 배제 (Phase 16R 위임).
* **원장 및 강사용 모바일 Push:** 본 설계는 순수 학부모 포털 전송용 푸시(Parent Push)만을 대상으로 함.

---

## 2. 현재 구현 상태 요약

* **parentContacts의 기존 필드:** 현재 스키마 상에 `appInstalled`, `pushEnabled`, `pushTokenStatus`, `linkedUserId` 등의 메타데이터 필드가 정의되어 있으나, 실물 연동 인프라가 없어 정적으로 세팅되는 수준입니다.
* **parentMessages의 기존 필드:** 메시지 전송 시 푸시 필요 여부를 지정하는 `pushRequired`와 푸시 발송 결과를 기록하는 `pushStatus`가 있으나, 현재는 `'pending'`, `'sent'`, `'not_required'` 등 논리 상태 및 Mock 수준으로만 작동합니다.
* **parentMessageSettings:** 학부모 포털의 설정 기능에 따라 메시지함(피드) 저장 여부와 푸시 전송 여부가 개별 필드로 분리 매핑되도록 구현되어 있습니다.
* **실제 앱 설치 및 토큰 정보 부재:** 실제 프로덕션 단말에서 수집된 디바이스 토큰이나 실시간 앱 설치 상태 동기화 아키텍처는 아직 구현되지 않았습니다.

## 3. 앱/웹앱 설치 상태 정의 (App Install Status Candidates)

사용자의 앱 설치 여부를 단순히 참/거짓(Boolean)으로 확정하는 것은 불가능하며, PWA(프로그레시브 웹앱) 및 모바일 하이브리드 앱 환경에 맞추어 아래의 **상태 후보(Status Candidates)**로 추론 관리해야 합니다.

* **unknown (확인되지 않음):** 학부모 계정이 생성되었으나 아직 모바일 웹이나 앱으로 단 한 번도 로그인/접속하지 않은 상태.
* **not_installed (미접속/미설치):** 학부모 포털 웹사이트 주소는 알고 있으나 앱 설치 또는 최초 접속 이력이 감지되지 않은 상태.
* **installed (앱/웹앱 접속 확인):** 하이브리드 앱 패키지 또는 PWA 홈 화면 추가를 통해 접속 이력이 확인된 상태.
* **token_registered (푸시 토큰 등록 상태):** 단말기로부터 고유 디바이스 푸시 토큰이 수집되어 서버 DB에 등록된 상태(후보).
* **token_invalid (토큰 만료/무효화 의심):** 푸시 발송 시 게이트웨이(FCM 등)로부터 토큰 무효화 응답(Bad Device Token)을 수신했거나 장기 미사용 단말로 판정된 상태.
* **permission_denied (푸시 권한 거부):** 사용자가 단말 또는 브라우저의 알림 권한 팝업에서 "허용 안 함"을 명시적으로 선택한 상태.
* **logged_out (장기 미접속/로그아웃):** 사용자가 앱에서 수동 로그아웃을 실행하여 토큰 수집을 중단했거나 토큰이 폐기된 상태.

> [!WARNING]
> **설치 여부 판별의 한계:** "앱 설치" 상태는 실제 앱스토어에서 앱이 다운로드되어 설치된 상태를 100% 실시간으로 보장 판별함을 의미하지 않습니다. 마지막 접속 채널, 푸시 토큰 등록 날짜, 권한 동의 여부를 바탕으로 백엔드에서 **"푸시 알림 도달 가능 상태"를 종합 추론**하는 구조를 검토해야 합니다.

## 4. 데이터 모델 후보 (Data Model Alternatives)

푸시 기기를 효율적으로 저장하고 매핑하기 위해 두 가지 아키텍처 후보를 검토합니다.

### 1) 데이터 보관 방식 비교

* **대안 A: `parentContacts` 테이블에 직접 컬렉션 필드로 통합 보관**
  - *장점:* 스키마 구조가 단순하며, 연락처 조회 쿼리 한 번으로 푸시 관련 정보를 모두 읽을 수 있습니다.
  - *단점:* 한 부모가 다중 기기(예: 스마트폰 + 태블릿 + 회사 PC 브라우저)를 사용하는 경우 기기별 토큰 개별 갱신 및 상태 추적이 어렵습니다.
* **대안 B: 별도 `parentDevices` 1:N 매핑 테이블 분리**
  - *장점:* 여러 단말기 및 플랫폼(iOS, Android, PWA Web)을 독립적으로 관리할 수 있으며, 기기별 로그인/로그아웃 및 토큰 만료를 안전하게 제어합니다.
  - *단점:* 테이블 조인이 필요하여 발송 시 조회 부하가 미세하게 증가합니다.

### 2) 권고 설계안 (최종 추천)
다중 기기 및 웹/앱 하이브리드 접속이 빈번한 학부모 환경을 고려할 때, **`parentDevices` 테이블 분리 방식을 추천**하며, `parentContacts` 테이블에는 발송 성능 향상을 위해 핵심 단말기의 요약 캐시 상태(`appInstalledStatus` 등)만 동기화 보관하는 절충안을 제안합니다.

#### 별도 `parentDevices` 스키마 제안 후보
```sql
CREATE TABLE parentDevices (
    id VARCHAR(36) PRIMARY KEY,
    parentUserId VARCHAR(36) NOT NULL,          -- 학부모 유저 계정 ID
    parentContactId VARCHAR(36) NOT NULL,       -- 학부모 연락처(Slot) 매핑 ID
    platform VARCHAR(15) NOT NULL,             -- 'ios' | 'android' | 'web_pwa'
    deviceName VARCHAR(50),                     -- 예: 'iPhone 15 Pro', 'Galaxy S24'
    pushTokenEncrypted TEXT NOT NULL,           -- 암호화된 기기 푸시 토큰
    tokenProvider VARCHAR(15) NOT NULL,        -- 'fcm' | 'apns' | 'webpush'
    permissionStatus VARCHAR(20) NOT NULL,      -- 'granted' | 'default' | 'denied'
    tokenStatus VARCHAR(15) NOT NULL,           -- 'active' | 'invalid' | 'revoked'
    lastSeenAt DATETIME,                        -- 마지막 기기 접속 시간
    revokedAt DATETIME,                         -- 토큰 수동 취소 시간
    createdAt DATETIME DEFAULT CURRENT_TIMESTAMP,
    updatedAt DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

## 5. `parentMessages.pushStatus` 상태 전이 설계 후보

푸시 알림 처리 시나리오에 따른 알림 이력 레코드의 `pushStatus` 상태 전이 흐름 후보를 다음과 같이 설계합니다.

### 1) pushStatus 상태 후보 (Status Candidates)
* `not_required`: 푸시 알림 조건에 부합하지 않거나, 학부모 설정 상 발송 대상이 아님.
* `pending`: 푸시 발송 큐에 진입하기 전의 초기 준비 상태.
* `queued`: 푸시 발송 서버 백그라운드 큐에 적재되어 전송을 대기 중인 상태.
* `sent`: 푸시 게이트웨이(FCM 등)로 요청이 정상 전달되어 통신사 네트워크로 송출된 상태.
* `failed`: 게이트웨이 전송 중 최종 오류가 발생하였으며 재시도가 만료된 상태.
* `skipped_by_setting`: 학부모 설정(`parentMessageSettings`)에서 해당 이벤트 푸시가 꺼져 있음.
* `skipped_no_token`: 수신 동의는 되어 있으나 등록된 디바이스 푸시 토큰이 전혀 없음.
* `skipped_permission_denied`: 단말기 자체 알림 권한이 차단(Denied)되어 있어 발송을 건너뜀.
* `skipped_invalid_token`: 저장된 토큰이 이미 만료 또는 유효하지 않은 것으로 판명되어 발송을 건너뜀.
* `skipped_parent_not_linked`: 원생에 연결된 학부모 가입 계정(`parentUserId`)이 존재하지 않아 푸시가 불가능함.
* `retry_scheduled`: 전송 일시 오류(네트워크 순연 등)로 인해 재시도 스케줄에 배치된 상태.

### 2) 상태 전이 의사결정 트리 후보 (Decision Tree)
```
[발송 이벤트 발생]
       │
       ├─ (A) 학부모 설정의 '메시지함 저장' = OFF 
       │      ➔ parentMessages 레코드 자체를 생성하지 않음 (프로세스 종료)
       │
       ├─ (B) '메시지함 저장' = ON & '푸시 알림' = OFF
       │      ➔ parentMessages 생성 / pushRequired = false / pushStatus = 'not_required'
       │
       └─ (C) '메시지함 저장' = ON & '푸시 알림' = ON ➔ [pushRequired = true / pushStatus = 'pending']
              │
              ├─ parentUserId 계정 없음 ➔ pushStatus = 'skipped_parent_not_linked'
              ├─ 등록된 pushToken 없음 ➔ pushStatus = 'skipped_no_token'
              ├─ 단말 권한 거부 상태 ➔ pushStatus = 'skipped_permission_denied'
              ├─ 기 등록 토큰 만료/무효 상태 ➔ pushStatus = 'skipped_invalid_token'
              └─ 발송 인프라 통과 ➔ pushStatus = 'queued'
                     │
                     ├─ FCM/APNs 전송 성공 ➔ pushStatus = 'sent'
                     ├─ 일시적 전송 오류 ➔ pushStatus = 'retry_scheduled' ➔ 재시도
                     └─ 최종 전송 실패 ➔ pushStatus = 'failed'
```

## 6. 푸시 토큰의 수명 주기 (Life Cycle)

디바이스 토큰의 안전한 수집, 갱신 및 무효화 처리를 제어하기 위한 생명 주기 후보 정책입니다.

1. **최초 등록:** 학부모 포털 로그인 및 최초 앱 구동 시 OS 알림 팝업 창에 응답하면 브라우저/하이브리드 엔진이 토큰을 발급받아 서버의 `parentDevices`에 신규 등록하는 시나리오를 검토합니다.
2. **토큰 갱신:** 모바일 OS나 브라우저의 정책 변경으로 기기 토큰이 무작위로 재발급되는 이벤트를 감지(FCM 온토큰 리프레시 등)하여 서버의 기존 레코드를 안전하게 갱신하는 방안을 고려합니다.
3. **로그아웃 시 취소:** 보안 및 타인 계정 수신 방지를 위해 로그아웃 실행 즉시 서버에 해당 디바이스 ID를 전달하여 `tokenStatus`를 `'revoked'`로 즉시 비활성화 처리할 것을 설계 권고합니다.
4. **만료 의심 추적 (Silent Pruning):** 수신 단말의 앱 삭제나 알림 차단은 OS가 백엔드에 즉시 알려주지 않으므로, 게이트웨이 발송 실패 에러(`BadDeviceToken`, `Unregistered`)가 발생하거나 90일 이상 단말 접속 이력(`lastSeenAt`)이 없는 경우 해당 토큰을 자동으로 `'invalid'` 상태로 업데이트하는 Pruning 엔진을 검토합니다.
5. **다중 기기 중복 제어:** 한 명의 학부모가 여러 디바이스를 소유한 경우, 스팸성 알림 중복을 막기 위해 '마지막 접속한 주 단말기 1대'에만 전송할 것인지, 혹은 '등록된 모든 활성 기기'에 동시 전송할 것인지에 대한 운영 정책의 후속 검토가 필요합니다.

## 7. 보안 및 개인정보 정책

* **디바이스 토큰 암호화:** 푸시 토큰은 장기 보관 시 민감한 인증성 식별자로 취급하고, 후속 보안 설계 단계에서 KMS 기반 암호화, 토큰화, 접근권한 제한, 주기적 폐기 정책 중 적절한 조합을 확정합니다. 본 Phase에서는 특정 암호화 알고리즘이나 키 관리 방식을 확정하지 않습니다.
* **잠금화면 민감 정보 직접 노출 배제:** 
  - 스마트폰 잠금화면에 직접 노출되는 푸시 알림 본문에는 결석 사유, 수강료 납부 금액 및 결제 수단 등 원생의 예민한 정보를 직접 담지 않는 **마스킹 옵션을 검토**합니다.
  - *예시안:* "[학원명] 알림: 원생 결석 확인 요청 관련 알림이 있습니다. 상세 내용은 보안을 위해 앱 로그인 후 확인해 주세요."
* **원장 및 강사의 접근 제한:** 원장 및 강사는 오늘 콘솔에서 발송 요청 상태만 파악할 뿐, 특정 학부모의 실물 디바이스 토큰 원문을 조회하거나 수정할 수 없도록 권한을 철저히 격리합니다.

## 8. UI 및 운영 화면 제안 후보

향후 구현될 원장용 원생 상세 정보나 학원 설정 화면에서는 다음과 같은 추론된 상태 정보를 제공하여 운영 편의성을 확보할 수 있도록 설계합니다.

* **앱/웹앱 접속 확인:** 사용자가 학부모 포털 앱/웹앱에 최근 접속한 기록(`lastSeenAt` 기준)이 있는지 여부를 표시.
* **푸시 도달 가능 여부:** 토큰 상태가 `active`이고 권한이 `granted`인 경우에만 "푸시 가능"으로 표시하며, 그 외에는 "푸시 불가(문자 발송 권장)" 등의 대체 안내 제공.
* **알림 거부 의심 표시:** OS 상에서 알림 권한을 차단한 상태(`permission_denied`)가 감지된 경우 이를 원장이 파악할 수 있도록 상태 노출 검토.

> [!CAUTION]
> 운영 UI에서는 기술적으로 100% 확정하기 힘든 "앱 설치됨"이라는 명칭 대신, **"웹/앱 접속 이력 있음"** 혹은 **"푸시 발송 가능 상태"**와 같이 오인을 줄일 수 있는 완곡하고 안전한 명칭을 사용할 것을 권장합니다.

## 9. 향후 구현 단계 제안 (Roadmap)

1. **Phase 16S-1 (스키마 빌드):** `parentDevices` 매핑 테이블 빌드 및 `parentContacts` 캐시 요약 필드 추가 마이그레이션.
2. **Phase 16S-2 (단말 등록 Mock):** 모바일 단말기 로그인/웹 접속을 모사하여 가상의 푸시 토큰 및 기기 사양을 데이터베이스에 적재하는 Mock 등록 시스템 구현.
3. **Phase 16S-3 (상태 전이 로직 구현):** 실제 게이트웨이가 없는 환경에서 `pushStatus` 상태 후보군(`skipped_no_token`, `skipped_permission_denied` 등)이 조건에 맞게 정확히 분기 적재되는 논리 상태 머신 개발.
4. **Phase 16S-4 (다중 기기 발송 큐 설계):** 1인 다기기 수신 시 큐 적재 및 순차 전송 처리 로직 구현.
5. **Phase 16S-5 (실 FCM/APNs 연동):** 파이어베이스 SDK 탑재 및 실물 모바일 OS 푸시 게이트웨이 파이프라인 개통.
6. **Phase 16S-6 (Service Worker 배포):** 웹 브라우저 백그라운드 수신용 웹 푸시 인증서 세팅 및 서비스 워커 스크립트 롤아웃.
7. **Phase 16S-7 (모니터링 대시보드):** 푸시 전송 성공률, 토큰 만료율 및 기기별 도달 실패 사유 통계 리포트 개발.

## 10. 수동 확인 가이드라인 (향후 구현 시 점검 포인트)

향후 실제 구현이 완료되는 시점에는 아래 기준들을 토대로 동작 검증을 진행할 것을 제안합니다.

1. **설정값 소급 배제 검증:** 학부모 설정에서 푸시를 OFF로 바꾼 경우, 과거에 이미 발송 대기 중이거나 전송된 `parentMessages`의 `pushStatus`가 소급 변경되지 않는지 여부.
2. **권한 동기화 검증:** 사용자가 브라우저 설정에서 알림 권한을 직접 차단한 뒤 알림을 발송했을 때, 상태코드가 `skipped_permission_denied`로 정확히 전이되는지 여부.
3. **토큰 무효화 검증:** 수동 로그아웃 처리 후 전송 시 토큰 만료 상태가 즉시 반영되어 무리한 발송 시도로 과금이 일어나지 않는지 여부.
4. **잠금화면 마스킹 준수 여부:** 스마트폰 잠금화면 알림 프리뷰에 학생명이나 민감 금액이 평문 노출되지 않는 마스킹 로직이 제대로 탑재되었는지 여부.
