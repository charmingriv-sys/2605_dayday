# Phase 16E 설계 정의서: 메시지 보내기 UI/UX 개편 및 발송 흐름 설계

본 문서는 Phase 16A~16C에서 수립된 학부모 대상 메시징 정책과 parentContacts 모델을 실제 관리자 화면의 UI/UX와 결합하고, 다중 채널(알림톡/문자) 선택 및 발송 흐름을 직관적이고 안정적으로 처리하기 위한 UI/UX 설계서입니다.

> [!IMPORTANT]
> 본 Phase 16E 단계는 **설계 및 정책 정의 문서화 단계**입니다. 실제 소스 코드 구현, UI 적용, 메시지 발송 API 연동 등은 **이번 Phase 범위에 포함되지 않으며** 모두 후속 개발 Phase로 위임합니다.

---

## 1. Phase 16E 범위 정의

### 1) 포함 범위 (In-Scope)
* **메시지 보내기 화면 UX 설계:** 원장의 피로도를 최소화하고 효율을 극대화할 수 있는 화면 구도 및 조작 흐름 설계.
* **수신자 복수 선택 및 필터:** parentContacts와 연계하여 보호자 1/2을 개별/복수 선택할 수 있는 구조.
* **번호 중복 처리:** 자녀 및 보호자 중복에 따른 발송 건수 병합 및 시각화 정책.
* **알림톡/문자 복수 채널 선택:** 알림톡 및 문자의 복수 선택이 가능한 UI 구조 및 대체(Fallback) 모드 UI/UX 설계 (선택지 후보 단계).
* **메시지 템플릿/초안(Draft) 연동:** 다양한 상황별 템플릿 탑재 및 동적 치환 변수 정의.
* **발송 전 미리보기/확인:** 발송 실수 방지를 위한 시각적 오버레이 미리보기 구성.
* **발송 로그 정책:** 기존 `outboundMessageLogs` 스키마 고도화 및 도메인 ID 연결 규격 정의.

### 2) 제외 범위 (Out-of-Scope)
* **실제 API 연동 및 발송 인프라 개발:** 알림톡 및 문자(SMS/LMS/MMS) 발송 API 연동 배제 (이번 Phase에서는 연동되지 않음).
* **자동 Fallback 및 우선순위 자동 발송 연동:** 백엔드 상에서의 실제 Fallback 자동 전환 로직 구현 및 확정 배제.
* **카카오 알림톡 템플릿 승인 및 차단 제어:** 사전에 등록된 템플릿 외의 입력을 코드 상으로 물리적으로 차단하거나 연동하는 제어부 배제.
* **학부모 앱 푸시 구현 및 메시지함 UI 마크업:** 학부모 포털 내의 화면 구현 배제.
* **parentContacts 실제 마이그레이션 코드 실행:** DB 레코드 강제 마이그레이션 실행 배제.
* **운영 권한 세분화 기능 구현:** 등급별 권한 관리 로직 작성 배제.

## 2. 현재 메시지 보내기 화면 분석

기존 코드 `src/js/views/director/messageSendView.js` 및 상태 모듈 `src/js/state/communication.js` 분석에 따른 현황과 한계는 다음과 같습니다.

### 1) 현재 화면 구성 및 입력/발송 방식
* **화면 구도 (3열 레이아웃):**
  * **1열 (좌측):** 원생 리스트 (`studentListPanel`) 및 하단 발송 대상 인원 누적 패널 (`recipientListPanel`).
  * **2열 (중앙):** 보낼 메시지 작성 및 매크로 툴바 (`composePanel`).
  * **3열 (우측):** 템플릿 보관함 (`messageVaultPanel`).
* **수신자 선택 및 입력:**
  * 원생 리스트에서 체크박스로 원생들을 선택한 후, 연락처 타입(본인 `student`, 보호자1 `g1`, 보호자2 `g2`) 단추를 활성화하여 "발송 인원에 추가" 버튼을 누르면 우측 누적 리스트에 번호 기준으로 적재됩니다.
  * 수동 추가 팝업(`directAddModalOverlay`)을 통해 번호를 즉석에서 타이핑하여 추가하는 기능도 지원합니다.
* **발송 및 Confirm:**
  * 하단 글로벌 발송 바의 발송하기 버튼 클릭 시, 화면 중앙에 심플한 얼럿 형식의 `focusConfirmOverlay`가 활성화되어 최종 확인 후 발송합니다.
* **저장 스키마:**
  * 발송 시 `outboundMessageLogs`에 전송 내역을 임시 기록하며, 인앱 메시지함 성격의 `messages` 테이블에도 동시에 적재됩니다.

### 2) 현재 화면의 한계점
1. **학부모 2인 모델 미반영:** 기존 설계는 보호자 1인(`guardian1`)을 기준으로 동작하여, 신규 parentContacts의 보호자 1/2 상세 정보(관계, 성함, 개별 수신 동의 여부)를 세밀하게 분리 선택할 수 없습니다.
2. **채널 선택 UX 부재:** 카카오 알림톡 전송과 일반 문자(SMS/LMS/MMS) 발송 모드가 화면상에서 명확히 분리되지 않으며, 두 채널의 동시 선택이나 대체(Fallback) 발송에 따른 피드백이 불완전합니다.
3. **업무 도메인 데이터 연동 결여:** 결석, 미수납 수강료 등 오늘 원장 콘솔에서 넘어왔을 때 taskId나 paymentId 등의 원본 데이터 외래키를 유기적으로 바인딩하고 로그에 남기는 구조가 없습니다.
4. **발송 전 미리보기 검증 취약:** 치환 변수가 실제로 적용된 텍스트의 최종 모습을 발송 전에 시각적으로 검증하기가 어렵고, 번호가 누락되거나 중복된 대상자에 대한 경고가 상세히 노출되지 않습니다.

## 3. 목표 UX 구조 제안

사용자 조작 동선과 화면 인지 피로도를 고려하여 기존 3열 레이아웃을 계승 및 고도화한 **"한 화면 섹션형 UI (Multi-Section Unified Layout)"**를 제안합니다.

```
┌────────────────────────────────────────────────────────────────────────┐
│ [헤더 영역] 제목 / 마지막 동기화 시간 / 새로고침                                     │
├────────────────────────────────────────────────────────────────────────┤
│ ┌──────────────────┐ ┌──────────────────┐ ┌──────────────────────────┐ │
│ │ 1섹션. 수신자 선택 │ │ 2섹션. 메시지 작성│ │ 3섹션. 템플릿/초안        │ │
│ │ - 원생/학부모 그리드│ │ - 채널 선택      │ │ - 상황별 템플릿 가이드    │ │
│ │ - 검색 및 필터     │ │ - 제목/본문 입력 │ │ - 최근 발송 메시지 이력  │ │
│ │ - 보호자 1/2 개별  │ │ - 매크로 툴바    │ │                          │ │
│ │   체크박스 목록    │ │ - 발신 번호 선택 │ │                          │ │
│ └──────────────────┘ └──────────────────┘ └──────────────────────────┘ │
├────────────────────────────────────────────────────────────────────────┤
│ [하단 발송 바] 선택 대상자 수 요약 | 미리보기 및 발송 버튼                           │
└────────────────────────────────────────────────────────────────────────┘
```

### 단계별 UI 흐름 (Step-by-Step Flow)
1. **1단계 (수신자 지정):** 검색/필터링을 통해 원생을 검색하고, 하단의 보호자 1/2 체크박스를 통해 수신 대상을 지정합니다.
2. **2단계 (발송 채널 지정):** 메시지 작성 영역 상단에서 알림톡 단독, 알림톡+문자(대체), 문자 단독 등의 발송 채널을 선택합니다.
3. **3단계 (콘텐츠 구성):** 직접 작성하거나 우측 템플릿 보관함에서 원하는 서식을 로드하여 본문을 자동 치환 완성시킵니다.
4. **4단계 (미리보기 검증):** 발송 버튼 클릭 시 나타나는 모바일 폰 목업 형태의 최종 팝업에서 치환 결과와 오류 대상을 검출합니다.
5. **5단계 (발송 및 로깅):** 전송을 완료하고 자동 생성되는 전송 결과 로그 화면으로 랜딩됩니다.

## 4. 수신자 선택 정책

Phase 16C에서 정의한 parentContacts 모델을 기반으로 설계한 수신자 선택 UX 정책입니다.

### 1) 수신자 리스트 노출 구조
* **원생-보호자 계층 구조:** 원생 리스트 테이블의 각 원생 행(Row) 하단에 속한 보호자 1과 보호자 2 정보가 들여쓰기된 서브 항목으로 노출됩니다.
* **수신자 카드 요소:** 각 보호자 row에는 `원생명`, `보호자 이름`, `관계(어머니/아버지 등)`, `전화번호`, `수신 동의 여부`, `앱 설치 상태 배지`가 함께 노출됩니다.

### 2) 기본 선택 및 비활성화 정책
* **기본값:** 원생을 선택하거나 특정 그룹 시나리오를 적용하면, 기본적으로 해당 원생의 `isPrimary` 보호자(또는 `parent1` 슬롯)만 자동으로 체크 활성화됩니다.
* **보호자 2 선택:** 부 보호자(`parent2`)에게도 동시 전송이 필요한 경우 원장이 명시적으로 수동 체크를 추가하여 다중 선택할 수 있습니다.
* **비활성화(Disabled) 대상:** 전화번호가 등록되어 있지 않은 보호자(`phone === null`)는 체크박스를 비활성화하고 옆에 `"연락처 없음"` 경고를 회색으로 표기합니다.

### 3) 동일 번호 중복 처리 (Deduplication) 정책
* **자녀 개별 알림 (출결, 수납 청구서 등):** 자녀별로 정보가 상이하므로 중복 번호여도 병합하지 않고 자녀 수만큼 개별 메시지(각각 치환 변수 적용)를 발송합니다.
* **학원 공통 알림 (전체 공지, 휴원 안내 등):** 동일한 전화번호로 다중 선택된 경우, 중복을 제거하여 **최종 번호 기준 1회만 발송**되도록 하여 스팸성 누적 발송과 예산 낭비를 방지합니다. UI 상에는 `"동일 번호 n건 병합 완료"`라는 요약 배지를 표시합니다.

## 5. 채널 선택 정책

메시지 작성 패널 상단에서 알림톡과 문자 채널을 다루는 세부 정책입니다.

### 1) 발송 채널 모드 정의
* **채널 기본값 및 Fallback 정책은 후속 Phase에서 확정한다.** Phase 16E에서는 알림톡/문자 복수 선택이 가능한 UI 구조와, 아래의 Fallback 모드를 선택지 후보로만 설계한다:
  * **[후보 1] 알림톡 우선 + 실패 시 문자 대체 발송:** 카카오 알림톡을 1차 시도하고, 수신자가 카카오톡 미가입자이거나 전송 실패 시 문자(SMS/LMS)로 자동 우회 전송을 검토하는 Fallback 시나리오 후보.
  * **[후보 2] 문자(SMS/LMS/MMS) 단독 발송:** 자유 양식의 본문을 대량 발송할 때의 문자 단독 발송 후보.
  * **[후보 3] 알림톡 단독 발송:** 실패 시 재시도를 수행하지 않고 카카오 알림톡으로만 발송을 제한하는 후보.

### 2) 중복 선택 및 동시 발송 제한 경고
* 원장이 알림톡과 문자를 임의로 동시에 전부 보내도록 체크한 경우, 학부모에게 동일한 내용이 2번 전달되어 혼선을 유발하고 비용이 이중 청구된다는 **[이중 발송 및 중복 과금 경고]** 안내 팝업 경고를 화면상에 설계합니다.

### 3) 알림톡 템플릿 규격 제약 후보
* 알림톡 템플릿은 향후 카카오 승인 템플릿 정책에 맞춰 편집 가능 범위를 제한할 수 있다. (이번 Phase에서는 실제 템플릿 승인 여부의 연동 및 차단 제어는 구현/확정하지 않음)

상황별 행정 업무의 표준화를 위해 제공하는 기본 템플릿과 자동 매칭될 치환 변수의 매핑 구조입니다.

### 1) 기본 제공 템플릿 목록
1. **수강료 청구서 발송 (수납 안내)**
2. **미수납 독촉 안내 (미수납 안내)**
3. **수강료 완납 영수증 (수납 완료)**
4. **교재비 청구 안내 (교재비 수납 안내)**
5. **교재비 미수납 안내 (교재비 미수납 안내)**
6. **교재비 수납 완료 (교재비 수납 완료)**
7. **학원 주요 일정 공지 (주요 일정 안내)**
8. **상담 예약 확인 (상담 예약 안내)**
9. **상담 일정 변경 알림 (상담 변경 안내)**
10. **시간표/보강 변경 안내 (시간표/수업 변경 안내)**

| `#{수업시간}` | 수업 시작 및 종료 시각 | "14:00 ~ 14:50" |

## 7. 초안 자동 생성 (Draft Auto-Generation) 정책

오늘 원장 콘솔이나 다른 화면의 데이터 행에서 메시지 작성 화면으로 진입할 때의 파라미터 연동 규격입니다.

* **수신자 자동 세팅:** 진입 대상 원생 ID(`studentId`)를 조회하여, 해당 원생의 대표 보호자를 수신처에 자동 할당하고 체크합니다.
* **템플릿 및 변수 자동 조립:**
  * **수납 독촉 업무 클릭 시:** 수납 연체 정보(`paymentId`)를 읽어와 수강료 미납 안내 템플릿을 자동 선택하고, `#{청구월}`, `#{금액}`, `#{납부예정일}` 값을 실제 데이터로 즉시 치환 조립하여 편집기에 노출합니다.
  * **교재비 청구 업무 클릭 시:** 교재비 청구 정보(`paymentId` 및 `bookIssueRequestId`)를 조회하여 교재비 수납 안내 템플릿과 치환 본문을 완성합니다.
* **관련 도메인 ID 외래키 연결:**
  * 생성 및 발송되는 메시지와 로그에 원본 업무의 추적성을 심기 위해 **`taskId`**, **`paymentId`**, **`bookIssueRequestId`**, **`scheduleId`**, **`studentId`** 값을 메시지 폼 내부의 숨겨진 메타 필드에 자동으로 매핑합니다.
* **원장의 편집권 보장:** 자동으로 생성된 메시지 초안 본문은 전송 전에 원장이 임의로 문구를 보완하거나 편집할 수 있도록 자유 텍스트 수정을 허용합니다.

## 9. 발송 로그 정책

물리적 전송 결과와 비즈니스 원장 데이터를 정합성 있게 보관하기 위한 로그 적재 규칙입니다.

### 1) outboundMessageLogs 테이블 스키마 고도화 규격
외부 전송 기록 대장인 `outboundMessageLogs` 테이블에 아래 메타 데이터를 포함시킵니다.

* `id`: 로그 고유 식별자 (`msglog_` 접두사 자동 생성 키)
* `senderUserId`: 메시지를 발송한 관리자/직원 ID (`users.id` 참조)
* `recipientPhone`: 실제 발송된 목적지 전화번호 (마스킹 적용 대상)
* `recipientName`: 수신인 성함
* `channel`: 발송 채널 (`kakao_talk`, `sms`, `lms`, `mms`)
* `content`: 실제 치환되어 발송된 본문 원문
* `status`: 전송 결과 상태 (`success`, `failed`, `pending`)
* `errorMessage`: 실패 시 통신사 에러 코드 및 사유
* `parentMessageId`: 매핑된 인앱 메시지함 ID (`parentMessages.id` 참조)
* `taskId`: 발송을 유발한 오늘 콘솔 업무 ID (선택)
* `paymentId`: 연관된 청구/수납 ID (선택)
* `scheduleId`: 연관된 일정 ID (선택)
* `createdAt`: 발송 완료 시각

### 2) 메시지 관련 모델 역할 분리 정의

```
┌──────────────────────────────────────────────────────────────────┐
│ 1. parentMessages (학부모 앱 메시지함 원장부)                       │
│    - 학부모가 앱에서 조회할 인앱 데이터 (읽음/보관함/안읽음 상태 관리)│
└────────────────────────────────┬─────────────────────────────────┘
                                 │ (1:N 연계)
┌────────────────────────────────▼──────────────────────────────────┐
│ 2. outboundMessageLogs (외부 전송 인프라 기록)                     │
│    - 통신사 망이나 카카오를 거쳐 물리적으로 도달한 전송 성공/실패 로그│
└───────────────────────────────────────────────────────────────────┘
```

* **`messages` 테이블:** 원장이 발송 화면에서 명시적으로 작성한 수동 메시지의 텍스트 본문과 마스터 발송 설정 자체를 담는 보관용 테이블로 역할을 재정립합니다.

## 10. 오늘 원장 콘솔 연동 대비 설계

Phase 16F에서 본격 진행할 오늘 원장 콘솔 업무 큐와의 연계 아키텍처 예비 설계입니다.

* **라우팅 파라미터 전달 규격:**
  * 오늘 콘솔 대기 업무 카드 내부의 [메시지 보내기] 클릭 시, 아래 JSON 스키마를 라우터 쿼리 스트링 또는 글로벌 ViewState에 바인딩하여 메시지 작성 화면을 로드합니다.
  ```json
  {
    "originTaskId": "task_billing_S1_06",
    "targetStudentId": "S1",
    "domainType": "payment",
    "domainId": "P101",
    "suggestedTemplateId": "rec2"
  }
  ```
* **발송 완료 후 업무 처리 자동화 정책 후보:**
  * **안 A (자동 완료):** 미리보기 후 [최종 발송 실행] 클릭이 정상 접수되면, 전달된 `originTaskId`를 찾아 오늘 원장 콘솔 상태를 자동으로 `done` 처리 및 큐에서 제거합니다. (원장 행동 최소화)
  * **안 B (수동 완료 유지 - 추천):** 발송 후 학부모의 실제 입금이나 확인 등의 최종 피드백 확인이 필요한 업무 성격이 있으므로, 발송 완료 후 오늘 콘솔로 돌아왔을 때 원장이 업무 카드를 눈으로 확인하고 수동으로 체크 완료 처리하도록 유도합니다. (다만, 발송 화면 하단에 "발송 완료 시 오늘 업무 완료 처리" 체크박스를 제공하여 선택권을 부여하는 것이 최적의 타협안입니다.)

## 11. 오류 및 예외 처리 정책

* **전화번호 부적합:** 
  * 번호 형식이 비표준이거나 공백인 경우, 수신자 추가 단계에서 원천 차단하고 붉은색 글씨로 에러를 경고합니다.
* **수신 대상자 없음 (0명):**
  * 수신자가 한 명도 선택되지 않은 경우 하단 글로벌 발송 바의 발송 버튼 자체를 비활성화(`disabled`) 처리합니다.
* **카카오 알림톡 템플릿 규격 미충족 가능성:**
  * 향후 카카오 승인 템플릿 연동 단계가 적용될 경우, 규격에 부합하지 않는 본문이 알림톡 모드에서 입력될 때 이를 감지하여 문자(LMS) 전송 전환 등을 안내하는 경고 메시지를 피드백하는 구조를 고려합니다.
* **부분 발송 실패 대응:**
  * 100명에게 단체 발송 시 90명 성공, 10명 실패가 발생한 경우, 전체 완료 토스트 대신 `"90건 발송 성공, 10건 실패"` 요약 팝업을 띄우고 실패한 10명의 명단과 실패 사유(결번 등)를 화면에 노출하여 즉시 재전송이나 다른 채널 발송을 시도할 수 있게 제공합니다.

## 12. 보안 및 개인정보 고려사항

* **개인정보 노출 보호:**
  * 메시지 작성 화면의 수신자 선택 행에서 학부모 전화번호는 기본적으로 `010-****-5678`로 마스킹 표시됩니다. 마스킹 해제는 관리자 세션 권한 검증 후에만 지원합니다.
* **민감 금융 정보 송출 주의:**
  * 수강료 금액 등 수납 관련 정보는 알림톡 가이드 규정을 철저히 따르며, 모바일 기기 푸시 알림 제목이나 간략 팝업 본문에는 구체적인 액수 노출을 배제하고 안심 링크 유도를 원칙으로 합니다.
* **로그 원문 보존 정책:**
  * 발송 로그 `outboundMessageLogs`에 전송된 텍스트 원본(`content`)을 저장할 때, 개인정보 유출 방지를 위해 DB 저장 시 암호화(Encryption) 처리를 거치며 원장과 승인된 직원 외에는 접근을 전면 차단합니다.

## 13. 구현 단계 제안

* **Phase 16E-1: 메시지 작성 화면 3섹션 구조 마크업 개편**
  * 기존 3열 구조를 수신자 필터링이 보강된 새로운 섹션형 UI 뼈대로 마크업 교체.
* **Phase 16E-2: parentContacts 기반 다중 수신자 바인딩 및 중복 제거**
  * 원생 리스트 로딩 시 보호자 1/2을 체크박스 트리가 있는 서브 로우로 불러오는 바인딩 로직 구현.
  * 수신 연락처 기준 중복 번호 감지 및 병합 표시 엔진 탑재.
* **Phase 16E-3: 채널 스위처 및 템플릿 엔진 설계 반영**
  * 알림톡/문자 분기 처리 UI 구성 및 카테고리별 동적 치환 변수 매크로 기능 완성.
* **Phase 16E-4: 모바일 폰 뷰 미리보기 오버레이 연동**
  * 발송 시점에 실시간 치환 데이터를 파싱하여 화면 중앙에 전송 시뮬레이션 미리보기를 가시화해 주는 렌더러 탑재.
* **Phase 16E-5: outboundMessageLogs 추적 구조 연결 및 회귀 테스트**
  * 도메인 ID 및 파생 ID 적재 파이프라인 생성 및 대량 선택 발송 기능 검증 E2E 스크립트 보강.

## 14. 최종 권고안 및 결론

1. **화면 UX 타입:** 동선의 연속성과 직관적 콘텐츠 수정을 보장하기 위해 페이지 단계형(Stepper)이 아닌 **"한 화면 섹션형 UI"를 최종 권장**합니다.
2. **기본 채널 및 Fallback 정책:** 이번 Phase에서는 알림톡/문자 API 연동 및 자동 Fallback, 카카오 템플릿 편집 제어를 확정하지 않으며, 단일 화면 내에서 두 채널을 복수 선택하고 Fallback 후보를 원장이 UI 옵션으로 스위칭할 수 있는 뼈대 구조만을 제공합니다. 구체적인 채널 기본값 및 자동 Fallback 상세 구현은 후속 API 연동 단계인 Phase 16F 이후 단계에서 확정할 것을 권고합니다.
3. **동시 발송 제한:** 정보 피로 방지를 위해 동시 발송 체크 시 화면에 노란색의 명확한 **이중 과금/스팸 주의 경고 배지**를 노출하도록 기획합니다.
4. **메시지 이력 연동:** 로그 추적의 완성도를 위해 `outboundMessageLogs` 적재 시 `parentMessageId` 및 콘솔 대기 업무 `taskId` 연관 외래키 기록 공간을 필수로 지원합니다.
