# Phase 8C: 오늘 원장 콘솔 MVP 구현 회고 및 다음 개발 우선순위 재조율 기획서

본 문서는 Phase 8C를 통해 구현된 "오늘 원장 콘솔" MVP의 설계 및 기능 범위를 검토하고, 실제 현장 운영 흐름상 아직 확정되지 않은 미비 구간들과 이를 해결하기 위한 다음 개발 우선순위(후보군 A~H)를 비교 분석하여 최적의 로드맵(Next Phase)을 제안합니다.

---

## 1. Phase 8C 현재 구현 완료 범위

오늘 원장 콘솔 MVP는 영세 학원 원장이 등원 시점부터 마감 시점까지 거쳐야 하는 행정 업무 및 예외 상황(미납, 지연 등)을 한눈에 파악하고 조치할 수 있는 기본적인 ERP 관제 프레임워크를 제공합니다.

* **TodayTask Store / API / Selector**:
  * `stateStore` 내에 `todayTasks` 전용 영속 데이터 모델 및 관리 어댑터 구축.
  * `reopenTodayTask(id)`를 포함한 완료/보류/숨김/복원 상태 전환 전용 Public API 지원.
  * 시간 순 정렬 정책(`startAt` $\rightarrow$ `dueAt` $\rightarrow$ `createdAt` 순) 및 활성/완료 선택 연산자 구현.
* **오늘 원장 콘솔 사이드바 진입**:
  * 원장(Director) 계정 로그인 시 고유 메뉴 항목(` 오늘 원장 콘솔`) 연동 및 화면 전환 가드 장착.
* **수동 운영메모 추가 / 수정 / 삭제 (CRUD)**:
  * 좌측 고정 입력 폼을 통해 운영메모의 제목/본문, 카테고리, 일정을 즉시 추가하는 기능 구축.
  * 등록된 메모 카드를 클릭했을 때 좌측 입력 폼으로 불러와 내용을 갱신하는 수정 모드 통합.
  * 잘못 기입되거나 불필요해진 메모를 영구 삭제하기 위한 컨펌창(`confirm`) 기반 삭제 액션 연동.
* **시작 / 종료 시간 선택 및 연동 UX**:
  * 시작/종료일에 대한 날짜 선택기 및 5분 단위의 시간(오전/오후, 시/분) 선택 드롭다운 통합.
  * 시작 일시 설정 시 종료 일시가 자동으로 1시간 뒤로 조절되는 연동 장치 적용 (`isEndTimeManuallyChanged` 오버라이드 탐지 패턴).
* **운영대기업무 큐 (Queue)**:
  * 최상단 요약 카드(총 업무, 완료 업무, 확인 필요 개수) 제공.
  * 큐 카드별 카테고리 뱃지, 일정 범위, 메모 텍스트 줄바꿈 및 간결한 시간 표시 포맷 연동.
* **완료 업무 보존 및 복원 (Re-open)**:
  * 완료 처리된 메모 카드가 큐에서 즉시 소멸하는 것이 아니라, 완료 상태 데이터로 이력을 보존.
  * 완료 탭에서 복원(되돌리기) 버튼 클릭 시, 스냅샷 타임스탬프를 제거하고 다시 대기 업무 목록으로 귀환시키는 액션 적용.
* **큐 상태 필터 탭 (Filter Tabs) & 스크롤 보존**:
  * `대기` (Open 및 경과된 보류), `완료` (Done), `숨김/보류` (Dismissed 및 대기 중인 Snoozed), `전체` 탭을 지원하여 실시간 개수 카운팅을 지원.
  * 탭 클릭 전환 시 DOM Swap 과정에서 브라우저 스크롤이 리셋되지 않도록 컨테이너의 `minHeight` 잠금/해제 및 `scrollTo` 보존 로직 추가.
* **App Calendar 월간 Grid & 일정 Chip / Popover**:
  * 35칸 / 42칸으로 구성된 월간 가변 캘린더 그리드 제공 (오늘 날짜 강조 및 이전/이후 달 음영 처리).
  * 셀 크기에 맞춘 일정 Chip 배치 및 초과 건수 표시용 `+N` 배지 제공.
  * 날짜 셀 클릭 시 레이어 팝오버를 띄워 상세 시간과 상태, 뱃지를 리스트화하고, 클릭 시 즉시 폼에 로드하는 UI Shell 탑재.
* **추천확인 Local Provider & Opt-in 데모**:
  * 매월 정기 수납일이 경과했으나 미납 상태인 원생을 탐지하는 `수강료 미납 확인 필요` 자동 생성 룰 탑재.
  * 오늘 수업 시작 15분이 경과했으나 출결 처리가 누락된 경우 작동하는 `출결 입력 지연` 자동 생성 룰 탑재.
  * URL 쿼리 파라미터(`?demoRecommendations=1`) 및 로컬스토리지 플래그를 통해서만 검증용 데모 데이터(`김추천(데모)`)가 시딩되도록 하는 Opt-in 안전 격리 장치 연동.
* **Google Calendar 연동 보류**:
  * Google OAuth 및 실서버 API 연동의 복잡도를 감안하여, 현재 로드맵에서 Google Calendar의 실제 연동은 공식적으로 스킵 및 보류 상태로 유지.

## 2. 아직 확정되지 않은 제품 / 운영 흐름 구간

현재 MVP 구현으로 기초적인 데이터 흐름은 완성되었으나, 실사용성 극대화를 위해 제품 기획 단계에서 확정 및 정의가 필요한 구간들이 존재합니다.

* **운영메모 입력 UX의 최종 형태**:
  * 현재는 수동 입력을 위해 "제목"과 "설명"을 textarea의 첫 줄/나머지 줄로 분리하는 형식을 취하고 있으나, 모바일/태블릿 등 좁은 화면에서 가독성을 해치거나 오조작을 유도할 수 있습니다. 제목과 설명을 물리적인 별도 Input 필드로 나눌지, 혹은 단일 텍스트박스의 심플한 TODO 형태로 통일할지 조율이 필요합니다.
* **캘린더의 범위와 화면 비중**:
  * 캘린더가 굳이 월간(Monthly) 단위의 큰 그리드로 원장 콘솔의 절반 이상을 차지할 필요가 있는지 의문입니다. 원장이 하루 동안 콘솔을 띄워놓고 관제할 때 필요한 정보는 "이번 달 전체 흐름"보다는 **"오늘 시간대별 일정(Daily/Weekly Timeline)"**에 가까울 수 있습니다. 월간 캘린더의 크기를 축소하고 주간/일간 타임라인 형태를 부각할지 기획적 결정이 필요합니다.
* **운영대기업무 큐와 캘린더의 정렬 및 상호 관계**:
  * 현재는 캘린더가 캘린더대로 달력 셀에 칩을 뿌리고, 큐는 큐대로 정렬 정책에 따라 세로로 늘어섭니다. 큐에 표시되는 항목과 캘린더에 표시되는 항목이 100% 동치인지, 아니면 큐는 "행정 예외 및 처리할 Task"이고, 캘린더는 "단순 일정 리포트"인지 명확한 성격 격리가 필요합니다.
* **추천확인 룰의 실제 우선순위 및 해소(Auto-Resolve) 조건**:
  * 미납 발생 시점, 출결 지연을 판단하는 15분 경과 시간 등 추천확인 발생 조건이 시스템 설정값과 어떻게 연동되어야 하는지 모호합니다. 또한 수납/출결이 해결되었을 때 카드 상태가 `done`으로 자동으로 갱신되는 트리거가 실시간 연산 부하를 주지 않도록 최적화가 필요합니다.
* **액션 카드와의 실질적인 화면 연결 방식 (Navigate & Action)**:
  * 추천확인 카드 우측에 있는 [확인] 혹은 클릭 시 `actionPayload`에 담긴 페이지 경로(예: `/billing`, `/attendance`)로 원장을 어떻게 부드럽게 이동시킬 것인지(라우팅 및 특정 원생 하이라이트 효과) 구체적인 연동 스펙이 보류되어 있습니다.
* **모바일 및 태블릿 조작계 마감**:
  * 태블릿 거치대나 모바일 크무실에서 원장이 한 손으로 카드를 처리하고 복원할 때, 탭 크기와 터치 타겟 패딩이 충분한지 실제 디바이스 테스트 기반 검증이 필요합니다.
* **카테고리(구분) 분류 및 정책**:
  * 현재는 `메모`, `상담예약`, `확인필요`, `추천확인` 4가지로 뱃지를 구분하고 있으나, 이 카테고리 분류가 원장들의 실제 업무 분류(예: 수납 관리, 출결 관리, 상담 일지, 학원 행정)와 부합하는지 기획적 검토가 필요합니다.
* **완료/숨김/보류 상태의 라이프사이클 정책**:
  * 오늘 숨김(Dismiss) 처리한 태스크나 보류(Snooze)된 업무가 다음 날이 되었을 때 자동으로 만료되어 사라져야 하는지, 혹은 미완료 상태로 계속 이월(Carry-over)되어 쌓여야 하는지 라이프사이클 정책이 미정입니다.

## 3. 다음 개발 후보군 정리 및 우선순위 분석

원장 콘솔 MVP 구현 이후 진행 가능한 다음 마일스톤 후보군들을 평가합니다.

### 후보 A: 오늘 원장 콘솔 추가 고도화
* **목적**: 입력 폼 개선(제목/설명 필드 명확한 분리), 캘린더 뷰를 일간/주간 뷰로 전환할 수 있는 토글 추가, 큐 아이템의 드래그 앤 드롭 정렬 등.
* **기대효과**: 콘솔 내의 조작 완성도를 100%로 끌어올려 단일 화면으로서의 완성도 극대화.
* **선행 조건**: 캘린더 컴포넌트의 시간대별 레이아웃 프레임 설계.
* **위험/주의점**: 캘린더 뷰 고도화는 렌더링 부하 및 레이아웃 깨짐을 유발하기 쉬우며, 공통 스케줄러 라이브러리 없이 순수 JS로 구현할 경우 공수가 매우 큼.
* **판단**: **보류**. 현재 월간 그리드로도 최소한의 시각적 확인은 가능하므로, 핵심 비즈니스 로직(돈, 출결) 개발보다 우선할 이유가 적음.
* **추천 우선순위**: **5순위**

### 후보 B: 추천확인 룰 확장
* **목적**: 수납 만료 3일 전 예보 룰, 최근 3회 연속 무단 결석 원생 경고 룰, 장기 휴원생 복귀 상담 주기 알림 등 실질적인 학원 운영 리스크 탐지 룰 추가.
* **기대효과**: 단순 TODO 리스트를 넘어서 학원 경영의 '리스크 관제 센터'로서 제품의 가치(Value Proposition)를 비약적으로 상승시킴.
* **선행 조건**: 수납 이력 및 출결 데이터 정합성 보장.
* **위험/주의점**: 룰이 너무 많아지면 콘솔 큐가 복잡해져 원장의 피로도를 높일 수 있음. 정교한 중요도(Priority) 분류 필터 필요.
* **판단**: **적극 검토 (지금 바로 수행 가능)**. 시스템이 원장에게 돈과 민원 리스크를 먼저 알려주는 기능은 DayDay의 핵심 차별화 포인트임.
* **추천 우선순위**: **2순위**

### 후보 C: 수납/결제 흐름 강화 (Billing Flow)
* **목적**: 원장 콘솔의 미납 카드 클릭 시 수납 페이지로 즉시 연동, 가상 청구서 생성 및 카카오 알림톡/링크 전송 데모 결합, 정산 비율제(instructor splits) 연계 계산.
* **기대효과**: 학원 원장이 가장 민감하게 반응하는 **"돈이 들어오는 일련의 과정"**을 실제 작동하는 유저 플로우로 완성.
* **선행 조건**: 결제 상태 정보 업데이트 API 완성.
* **위험/주의점**: 결제 및 청구 흐름은 기획적 예외 상황(중도 환불, 할인 적용, 부분 납부 등)이 많아 데이터 아키텍처 설계 단계에서 면밀한 검토가 요구됨.
* **판단**: **최우선 권장**. 학원 ERP 서비스로서 수납 프로세스 정립은 제품의 생존 여부를 결정하는 핵심 기능임.
* **추천 우선순위**: **1순위 (추천 1안)**

### 후보 D: 출결/미등원/알림톡 흐름 강화 (Attendance Alert Flow)
* **목적**: 지연 등원생 발생 시 원장 콘솔에서 [학부모 알림톡 송신] 버튼 즉각 노출, 클릭 시 모의 발송 감사로그 생성, 키오스크 태블릿 등원 핀패드와 콘솔 큐의 실시간 소켓/이벤트 연동 데모.
* **기대효과**: 학원의 일상 민원 중 90%를 차지하는 **"자녀 안심 등하원 확인"**에 대한 운영 자동화 검증.
* **선행 조건**: 출결 상태 변화 구독 모듈 및 소켓 인터페이스 규격 정의.
* **위험/주의점**: 다수의 원생이 동시에 태깅할 때 일어나는 동시성 처리 및 UI 레이턴시 관리 필요.
* **판단**: **검토**. 추천 1안(수납) 완료 후 바로 이어서 진행할 만한 핵심 기능임.
* **추천 우선순위**: **3순위 (추천 2안)**

### 후보 E: 교재 지급/청구 루프 (Inventory & Billing Loop)
* **목적**: 강사가 수업 중 원생에게 교재를 지급하면 원장 콘솔에 `교재비 결제 청구 필요` 추천 카드가 자동으로 올라오고, 이를 수강료와 합산하여 일괄 결제 요청을 보내는 흐름 구현.
* **기대효과**: 일반 과목비 외에 교재비 수납 누락을 방지하는 음악학원 및 일반 학원의 필수적인 틈새 행정 완성.
* **선행 조건**: 교재 재고 및 배분 데이터베이스 스키마 안정화.
* **위험/주의점**: 상대적으로 우선순위가 수납/출결 메인 스트림보다 낮음.
* **판단**: **보류**. 추후 마이너 기능 고도화 시점에 병합 진행 권장.
* **추천 우선순위**: **7순위**

### 후보 F: 강사-원생 시간표 관리 잔여 기능 마감
* **목적**: 강사 검색 input + dropdown 포커스 이탈 완전 방지, 주간/일간 인쇄용 레이아웃 템플릿 최종 정돈, 과거 이력 스냅샷과 미래 기본 시간표의 정교한 동적 생성 로직 마감.
* **기대효과**: 레거시 화면의 QA 잔여 이슈를 클리어하여 제품 전체의 신뢰성 확보.
* **선행 조건**: 없음.
* **위험/주의점**: 행정적 화면들의 디테일 튜닝에 공수가 분산되어, ERP 코어 비즈니스 로직(결제, 관제)으로 진입하는 속도가 지연될 수 있음.
* **판단**: **부분 병행**. 주요 버그나 포커스 이탈 등 실사용 불능 버그만 빠르게 처리하고 큰 레이아웃 개편은 뒤로 미룸.
* **추천 우선순위**: **4순위**

### 후보 G: 모바일/태블릿 UX 마감
* **목적**: 탭 영역의 터치 감도 개선, 캘린더 일정 Chip의 줄바꿈 방지 스타일 적용, 스크롤 보존을 모바일 가상 키보드 오픈 시점까지 감안하여 보정.
* **기대효과**: 현장 태블릿 거치 사용 시 오터치율을 비약적으로 낮춤.
* **선행 조건**: 실제 기기 검증 환경 구축.
* **위험/주의점**: 시뮬레이터만으로는 반응형 CSS의 미세한 스크롤 떨림을 잡기 어려워 직접 확인 주기가 김.
* **판단**: **보류**. 기획 방향이 잡힌 후 다른 핵심 로직과 묶어서 마감 단계에 진행 권장.
* **추천 우선순위**: **6순위**

### 후보 H: 전체 서비스 IA 및 Segment-First 구조 재정리
* **목적**: 음악학원 외에 타 업종(PT 헬스장, 레슨)으로의 공통 코어 재사용을 보장하기 위해 `organizations`, `todayTasks` 상태 엔진 내부의 용어사전 레이어(Terminology Layer) 및 도메인 어댑터 구조를 정립하고 폴더 구조 재조정.
* **기대효과**: 코드의 확장 가능성과 아키텍처 정합성을 극대화하여 멀티 SaaS 프레임워크 베이스라인 구축.
* **선행 조건**: 비즈니스 도메인 범위 확정.
* **위험/주의점**: 과도한 선제 추상화(Over-engineering)로 인해 오히려 현재 구현 속도가 느려지고 코드 가독성이 떨어질 수 있음.
* **판단**: **적극 검토 (추천 3안)**. 더 많은 화면이 쌓이기 전에 뼈대를 재정리하는 것이 장기적으로 기술 부채를 크게 예방함.
* **추천 우선순위**: **2순위 또는 3순위**

## 4. 사용자 관점의 핵심 질문

비즈니스 및 실제 사용자(학원 원장, 매니저) 관점에서 제품 설계를 재점검하기 위한 질문들입니다.

* **질문 1. 원장이 아침에 출근해서 저녁에 퇴근할 때까지 브라우저에 항상 띄워놓고 보아야 하는 단 하나의 화면은 무엇인가?**
  * *해석*: 기존 대시보드(월간 매출 그래프 위주)는 일주일에 한두 번만 봐도 충분합니다. 원장이 매시간 붙잡고 모니터링해야 하는 화면은 결국 **"지금 누가 와야 하고, 누구 출결이 누락되었으며, 오늘 돈을 내야 할 사람이 누구인지"**를 종합 정리해 주는 **'오늘 원장 콘솔'**이어야 합니다. 따라서 이 화면이 DayDay의 홈 화면(Landing Page)으로 기능하도록 정교화해야 합니다.
* **질문 2. '오늘 원장 콘솔'의 본질은 일반 TODO(할 일) 관리인가, 실시간 비즈니스/리스크 관제인가?**
  * *해석*: 단순히 메모를 적고 완료 처리하는 TODO 앱은 시중에 널려 있으며 학원 업무와 격리되어 있습니다. 본질은 **"학원 DB(수납, 출결)에서 발생하는 예외 상태를 실시간 탐지하여 원장에게 즉각 조치를 제안하는 비즈니스 관제 콘솔"**이어야 합니다. 따라서 수동 메모 CRUD보다는 **시스템 추천확인 룰과 액션 연동**이 훨씬 강력한 가치를 제공합니다.
* **질문 3. 수납(Billing), 출결(Attendance), 상담(Consulting), 교재(Books) 중 가장 먼저 실제 학원의 '매출'과 '학부모 민원'에 직결되는 흐름은 무엇인가?**
  * *해석*: **수납(돈)**과 **출결(민원)**입니다. 수납 누락은 곧바로 원장의 금전적 손실로 이어지고, 출결 누락(등원 지연 알림 오발송/미발송)은 학부모의 강력한 신뢰도 하락과 민원으로 연결됩니다. 따라서 다음 단계는 이 두 핵심 도메인의 기능 완성도를 끝까지 밀어붙여야 합니다.
* **질문 4. 다음 Phase는 신규 기능 확장(Feature Building)이어야 하는가, 아키텍처/설계 재정리(Architecture Baseline)여야 하는가?**
  * *해석*: 현재 음악학원 특화 기능이 빠르게 붙으면서 파일 크기가 커지고 있어, 코드 간 결합도가 높아질 위험이 있습니다. 기능 확장을 2~3단계 더 가기 전에, '음악학원 도메인'과 'SaaS 공통 코어'를 정교하게 분리해 주는 설계 재정리 단계를 한 번 거쳐 베이스라인을 확정 짓는 것이 현명합니다.

## 5. 다음 Phase (마일스톤) 추천 경로 제안

현재 완성된 8C 기반 위에 이어질 다음 Phase 배치를 위한 3가지 추천 경로를 제안합니다.

### 🎯 [추천 1안] Phase 8D: 수납/결제 라이프사이클 및 콘솔 액션 완성 (비즈니스 임팩트 우선)
* **내용**:
  1. 원장 콘솔 내 미납 알림 카드의 `actionPayload`를 수납 상세 모달/화면과 실질적으로 연결.
  2. 수납 화면에서 가상 청구서 발행 버튼 클릭 시 학부모용 모의 청구 링크를 생성하고 이를 알림톡(모의)으로 발송 처리하는 모의 루프 완성.
  3. 결제 완료 시 오늘 원장 콘솔의 미납 카드가 실시간으로 해소(`done`) 및 이력 보존 처리되는 트리거 연동.
  4. 강사 비율제 정산 금액 계산 로직 설계 및 결제 완료 건과의 연동 기초 구현.
* **이유**: ERP의 핵심 동력인 "돈의 흐름"을 완전한 하나의 유저 플로우로 묶어 제품의 핵심 비즈니스 가치를 즉시 검증할 수 있습니다.

### 🔔 [추천 2안] Phase 8D: 출결/미등원 관제 및 실시간 키오스크 연동 (민원 차단 우선)
* **내용**:
  1. 오늘 원장 콘솔의 `출결 입력 지연` 카드 클릭 시 출결 관리 화면으로 즉시 연결 및 해당 원생 하이라이트.
  2. 핀패드/Kiosk 화면을 간이 오버레이 형태로 콘솔 내에 띄우고, 가상 핀 코드를 터치했을 때 실시간으로 콘솔의 출결 카드가 자동으로 사라지는 실시간 동기화 데모 구현.
  3. 출결 지연 건에 대해 [즉시 안심 톡 발송] 액션 버튼을 연계하고, 발송 이력을 히스토리 로그에 남기는 마일스톤 완성.
* **이유**: 학원의 일일 행정 중 가장 반복적이고 실시간성이 높은 "아이들의 등하원 통제" 루프를 완성하여 현장 실무자의 피로도 감소를 증명할 수 있습니다.

### 🏗️ [추천 3안] Phase 8D: 서비스 IA 및 Segment-First 구조 재정리 (아키텍처 베이스라인 우선)
* **내용**:
  1. `todayTask.js`, `sessionsView.js`, `billing.js` 등에 산재된 도메인 결합 코드를 분리.
  2. `StateStore`와 화면(View) 레이어 사이에 명시적인 `Domain Adapter`를 구현하여 음악학원 용어와 공통 Task 큐 간의 번역 구조 체계화.
  3. 향후 피트니스/개인레슨 업종 확장을 고려하여 화면 텍스트 사전을 용어사전 레이어로 이관.
* **이유**: 코드가 복잡해지기 전에 설계 기준선(Baseline)을 고정하여 장기적으로 개발 속도를 2배 이상 단축할 수 있는 기초 체력을 다집니다.
