# Phase 16G 설계 정의서: 학부모 메시지/푸시 자동 생성 설정 설계

본 문서는 학원 단위로 학부모 대상 자동 메시지 생성 및 모바일 기기 푸시(Push) 발송 여부를 제어하고, 각 행정 이벤트 발생 시 알림 송출 채널을 체계적으로 통제하기 위한 설정 정책 설계서입니다.

> [!IMPORTANT]
> 본 Phase 16G 단계는 **설계 및 정책 정의 문서화 단계**입니다. 실제 설정 UI 컴포넌트 구현, state/settings 데이터베이스 마이그레이션 및 영속화 코드 작성, parentMessages 실제 연동, 푸시 알림 발송 인프라(FCM/APNS 등) 구축 및 앱 설치 상태 연동 등은 **이번 Phase 범위에 포함되지 않으며** 후속 개발 Phase로 위임합니다.

---

## 1. Phase 16G 범위 정의

### 1) 포함 범위 (In-Scope)
* **학부모 메시지함 저장 ON/OFF 설정:** 특정 이벤트 발생 시 학부모 전용 앱의 인앱 메시지함(`parentMessages` 테이블)에 적재할지 여부 결정.
* **학부모 푸시 발송 ON/OFF 설정:** 메시지함 저장 상태에서 모바일 디바이스에 알림음/진동을 동반한 푸시 알림을 발송할지 여부 결정.
* **이벤트별 설정 항목 세분화:** 출결, 수강료, 교재비 등 세부 이벤트 단위의 설정 스코프 수립.
* **추천 기본값 정의:** 학원 초기 가입 또는 마이그레이션 시 적용될 권장 초기 설정값 제안.
* **설정 간 종속 규칙:** 메시지함 저장 여부와 푸시 발송 여부 사이의 선행 조건 논리 규칙 정의.
* **학원정보관리 UI 배치 제안:** 원장 콘솔 내 설정 화면 레이아웃 및 폼 구조 기획.
* **설정 저장 스키마 후보:** 기존 `settings` 객체 구조 내에 추가될 JSON 필드 정의.
* **후속 구현 단계:** 설계 이후 진행될 개별 태스크 단위 로드맵 수립.
* **구현 단계 사용자 수동 확인 포인트:** 개발 완료 시 기획 의도와 일치하는지 확인할 수 있는 QA 체크리스트.

### 2) 제외 범위 (Out-of-Scope)
* **실제 설정 UI 구현:** 학원 관리 화면 내 설정 섹션 및 비활성화(disabled) UX가 적용된 토글 UI 마크업/코드 작성 배제.
* **실제 state/settings 코드 구현:** 백엔드 API 컨트롤러, DB 스키마 생성 마이그레이션 파일 작성 배제.
* **parentMessages 생성 구현:** 출결 태깅이나 결제 완료 시점에 실제 알림 레코드를 추가하는 Triggers/Hooks 구현 배제.
* **푸시 발송 구현:** 모바일 기기로 네트워크 푸시 패킷을 송출하는 푸시 서비스 연동 배제.
* **알림톡/문자 API 연동:** 카카오톡 비즈메시지 및 SMS/LMS 발송 모듈 연동 배제.
* **앱 설치 여부/푸시 토큰 실제 연동:** 학부모 기기의 FCM/APNS 토큰 수집 및 상태 체크 코드 배제.

## 2. 핵심 정책 정의

학부모 메시징 및 푸시 시스템의 혼선을 막고 자원의 낭비를 방지하기 위해 다음과 같은 종속성 및 라이프사이클 규칙을 확립합니다.

> [!WARNING]
> **본 설정은 "학부모 전용 앱 내 메시지함 저장 및 기기 푸시"에 한한 설정입니다.**
> 유료 발송되는 카카오 알림톡이나 문자(SMS/LMS) 자동 발송 시스템과는 완전히 별개이며, 본 설정의 ON/OFF는 알림톡/문자 발송 여부에 아무런 영향을 주지 않습니다.

* **이원화된 별도 설정:** 메시지함 저장(`messageEnabled`)과 기기 푸시 발송(`pushEnabled`)은 개별 토글로 분리되어 독립적으로 동작할 수 있습니다.
* **종속성 규칙 (Dependency Rule):** 
  * 푸시 알림은 인앱 메시지함에 적재된 물리적 데이터를 바탕으로 모바일 화면에 요약 정보를 띄우는 보조 수단입니다.
  * 따라서 **[메시지함 저장] 설정이 OFF인 경우, [푸시 발송] 설정은 불가능(Disabled 및 강제 OFF)**합니다. 메시지함에 남지 않는데 일회성 기기 푸시만 보낼 수는 없습니다.
  * [메시지함 저장]이 ON인 경우에만 [푸시 발송] 토글을 선택적으로 ON/OFF 할 수 있습니다.
* **설정별 의미 및 영향 범위:**
  * **메시지함 저장 OFF (`messageEnabled: false`):** 해당 행정 이벤트가 발생하더라도 `parentMessages` 레코드 자체를 전혀 생성하지 않습니다. 학부모는 앱의 메시지함에서 이를 볼 수 없으며 푸시도 가지 않습니다.
  * **푸시 발송 OFF (`pushEnabled: false`):** 행정 이벤트 발생 시 `parentMessages` 레코드는 정상적으로 생성되어 학부모 앱의 메시지함 목록에는 영구 적재되지만, 학부모의 모바일 디바이스에 상단 배너 알림, 진동, 알림음 등 기기 푸시는 송출되지 않습니다. (사일런트 메시지 적재)

## 3. 설정 대상 및 제외 이벤트

### 1) 설정 대상 이벤트 (그룹별 정리)

학부모 전용 앱으로의 자동 알림 생성을 제어할 수 있는 대상 항목들입니다.

| 그룹 | 이벤트명 | 설정 필드 (카테고리) | 설명 |
| :--- | :--- | :--- | :--- |
| **출결** | 등원 | `attendanceCheckIn` | 원생이 출결 키패드에 등원 태그를 입력한 시점 |
| | 하원 | `attendanceCheckOut` | 원생이 출결 키패드에 하원 태그를 입력한 시점 |
| **수강료** | 수강료 수납 안내 | `tuitionBilling` | 수강료 청구서가 발행(Unpaid)된 시점 |
| | 수강료 미수납 안내 | `tuitionOverdue` | 수강료 납부 예정일이 경과(Overdue)된 시점 |
| | 수강료 수납 완료 | `tuitionPaid` | 학부모가 수강료를 완납(Paid)하여 영수증이 발행된 시점 |
| **교재비** | 교재비 수납 안내 | `bookBilling` | 원장의 교재 요청 승인에 따라 교재비 청구서가 발행된 시점 |
| | 교재비 미수납 안내 | `bookOverdue` | 교재비 납부 예정일이 경과하여 미수납 상태가 지속된 시점 |
| | 교재비 수납 완료 | `bookPaid` | 교재비 결제가 정상 완료되어 영수증이 발행된 시점 |

### 2) 설정 제외 이벤트 및 제외 사유

아래 항목들은 학원의 일괄적인 ON/OFF 자동 토글 제어 대상에서 명시적으로 제외합니다.

* **결석 확인 (`absent`):**
  * *제외 사유:* 시스템 자동 발송이 아니며, 오늘 원장 콘솔에서 원장이나 직원이 결석 사유를 직접 유선상으로 확인하거나 메시지 보내기 화면을 거쳐 개별적으로 발송을 통제해야 하므로 제외합니다.
* **지각 / 하원누락 (`attendance_warning`):**
  * *제외 사유:* 리더기 인식 오류나 시스템 오인식 확률이 높아 자동 발송 시 행정 민원을 유발하므로 제외합니다.
* **연속결석/출결워닝:**
  * *제외 사유:* 고도의 행정적 판단이 개입되어야 하는 사안이므로 자동 발송하지 않고 수동 처리 범위로 둡니다.
* **강사 근태 (`staff_warning`):**
  * *제외 사유:* 내부 교직원 관리용 정보이므로 학부모 메시징 카테고리와 원천 분리됩니다.
* **운영메모 (`memo`):**
  * *제외 사유:* 학원 내부 기록용이므로 학부모 발송과 무관합니다.
* **주요일정 자동 안내 (`schedule`):**
  * *제외 사유:* 주요일정 등록 시 관리 화면에서 "학부모에게 알림 여부"를 건별로 직접 수동 선택하여 등록하는 구조가 정합성에 부합합니다.
* **공지 자동 안내 / 상담 자동 안내 / 시간표 자동 안내:**
  * *제외 사유:* 정형화된 정기 안내가 아니므로 게시글 작성, 예약 등록 등 해당 수동 프로세스 내부에서 체크박스로 전송 여부를 지정하는 흐름을 준수해야 합니다.

## 5. 설정 UI 배치 및 UX 제안

### 1) 화면 배치
* **메뉴 위치:** **학원 관리 > 학원정보관리** 화면 내의 독립된 세부 탭 또는 하단 단독 섹션으로 편입합니다.
* **섹션명:** `학부모 메시지/푸시 설정`

### 2) UI 레이아웃 구조안
```
[학부모 메시지/푸시 설정]
학부모 전용 앱의 메시지함 적재 및 스마트폰 기기 푸시 알림 발송 여부를 제어합니다.
(※ 본 설정은 비용이 발생하는 SMS/알림톡 발송 여부에는 영향을 주지 않습니다.)

■ 그룹 1: 출결 설정
--------------------------------------------------------------
* 등원 안내   [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]
* 하원 안내   [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]

■ 그룹 2: 수강료 설정
--------------------------------------------------------------
* 수납 안내   [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]
* 미수납 안내 [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]
* 수납 완료   [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]

■ 그룹 3: 교재비 설정
--------------------------------------------------------------
* 수납 안내   [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]
* 미수납 안내 [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]
* 수납 완료   [메시지함 저장 토글 (ON)]  [푸시 발송 토글 (ON)]

[설정 저장하기]
```

### 3) 주요 UX 제어 규칙
* **상태 비활성화 및 툴팁 제공:**
  * 특정 행의 `[메시지함 저장 토글]`을 `OFF`로 전환하면, 우측의 `[푸시 발송 토글]`은 즉시 강제로 `OFF` 처리되며 클릭할 수 없도록 **비활성화(Disabled) 상태**로 변경됩니다.
  * 비활성화된 푸시 토글 위에 마우스를 올리거나 하단에 문구로 설명 가이드를 노출합니다.
    * *설명 문구:* `"학부모 앱 메시지함 저장을 활성화해야 기기 푸시를 발송할 수 있습니다."`
* **사일런트 모드 안내 문구:**
  * `[메시지함 저장 토글]`은 `ON`이고 `[푸시 발송 토글]`이 `OFF`인 경우, 하단에 팁을 제공합니다.
    * *설명 문구:* `"푸시가 비활성화되어도 학부모는 앱 내 메시지함에서 내역을 언제든 조회할 수 있습니다."`
* **저장 전 변경 요약 기능 (후보 요구사항):**
  * 원장이 다수의 토글을 변경한 후 `[설정 저장하기]` 버튼을 누를 때, 변경 사항으로 인해 발생할 알림의 변화를 한눈에 인지할 수 있도록 요약 팝업을 제공하는 시나리오를 제안합니다.
    * *예:* `"등원 알림의 기기 푸시 발송이 비활성화되며, 수강료 미수납 안내 메시지가 완전히 비활성화됩니다. 이대로 저장하시겠습니까?"`

## 6. 설정 저장 스키마 후보

기존 `settings` 모델과의 하방 호환성을 유지하면서 유연하게 쿼리할 수 있도록 설계된 JSON 형식의 데이터 후보입니다.

```json
{
  "academyId": "ACADEMY_001",
  "settings": {
    "theme": "dark",
    "useAttendanceKeypad": true,
    "parentMessageSettings": {
      "attendanceCheckIn": {
        "messageEnabled": true,
        "pushEnabled": true
      },
      "attendanceCheckOut": {
        "messageEnabled": true,
        "pushEnabled": true
      },
      "tuitionBilling": {
        "messageEnabled": true,
        "pushEnabled": true
      },
      "tuitionOverdue": {
        "messageEnabled": true,
        "pushEnabled": true
      },
      "tuitionPaid": {
        "messageEnabled": true,
        "pushEnabled": true
      },
      "bookBilling": {
        "messageEnabled": true,
        "pushEnabled": true
      },
      "bookOverdue": {
        "messageEnabled": true,
        "pushEnabled": true
      },
      "bookPaid": {
        "messageEnabled": true,
        "pushEnabled": true
      }
    }
  }
}
```

### 관계성 및 적합성 제안
* **기존 settings 모델에 병합:** 학원 설정을 담는 엔티티(예: `Academy` 테이블의 `settings` JSON 컬럼 또는 별도의 `AcademySetting` 테이블) 내에 `parentMessageSettings` 오브젝트 필드로 병합합니다.
* **조회 최적화:** 알림이 대량으로 생성되는 출결 이벤트 발생 시 데이터베이스를 매번 스캔하지 않도록, 학원 인스턴스 로딩 시 설정 캐시를 구성하여 메모리 단에서 빠르게 분기 처리를 진행하는 구조를 제안합니다.

## 7. 이벤트별 세부 동작 시나리오 예시

### 1) 등원 이벤트 발생 시
* **시나리오 A (`messageEnabled: true`, `pushEnabled: true`):**
  * 원생이 입구 키패드에 출결 번호를 태깅합니다.
  * 시스템은 학원의 설정을 조회하여 둘 다 `true` 임을 확인합니다.
  * 학부모 대상 메시지 데이터(`parentMessages`) 레코드를 생성하고, 모바일 기기 푸시 발송 큐에 적재합니다. (학부모에게 푸시 팝업이 뜸)
* **시나리오 B (`messageEnabled: true`, `pushEnabled: false`):**
  * 원생이 번호를 태깅합니다.
  * `parentMessages` 레코드는 정상적으로 디비에 생성되지만, 푸시는 발송하지 않습니다.
  * 학부모가 앱을 열어 메시지함을 확인하면 등원 확인 글이 리스트에 존재하나, 폰이 울리거나 푸시 팝업은 뜨지 않았습니다.
* **시나리오 C (`messageEnabled: false`, `pushEnabled: false`):**
  * 원생이 번호를 태깅합니다.
  * `parentMessages` 레코드도 생성하지 않고, 푸시도 생략합니다. 디비 및 네트워크 부하가 전혀 발생하지 않습니다.

### 2) 교재비 수납 안내 이벤트 발생 시 (원장의 교재 확인 승인)
* **흐름:**
  * 강사가 교재 지급을 요청하고, 원장이 오늘 원장 콘솔에서 [교재 확인] 승인을 누릅니다.
  * `studentBook` 이력 및 `book payment` (status = `unpaid`)가 즉시 발행됩니다.
  * 학원의 `parentMessageSettings.bookBilling` 설정을 확인합니다.
  * **설정이 ON/ON일 때:** `parentMessages` 레코드를 만들고 푸시 알림 대상에 추가합니다.
  * **설정이 OFF일 때:** 어떠한 알림 데이터도 생성하지 않습니다.

### 3) 수강료 미수납 이벤트 발생 시 (기한 경과)
* **흐름:**
  * 매일 자정 배치 스케줄러가 미수납 수강료(payment의 `dueDate`가 어제 날짜인 것)를 스캔합니다.
  * 학원의 `parentMessageSettings.tuitionOverdue` 설정을 확인합니다.
  * **설정이 ON/ON일 때:** `parentMessages` 독촉 레코드를 생성하고 푸시 알림 대상에 추가합니다.
  * **설정이 OFF일 때:** 알림 데이터를 생성하지 않습니다.

## 8. parentMessages 및 푸시 상태(pushStatus)와의 연동 관계 (Phase 16B 계승)

Phase 16B에서 설계한 학부모 메시지 데이터 모델과의 필드 매핑 및 상태 기록 규칙입니다.

* **메시지 저장 OFF (`messageEnabled: false`):**
  * `parentMessages` 테이블에 행을 삽입(Insert)하는 단계 자체를 생략합니다.
* **푸시 발송 OFF (`pushEnabled: false`):**
  * `parentMessages` 테이블의 `pushRequired` 플래그 값을 `false`로 설정하여 저장합니다.
  * `parentMessages.pushStatus`에 `skipped_by_setting` 상태를 기록하거나, 혹은 후속 구현에서 별도의 push log 구조가 도입될 경우 해당 로그에 기록하여, 시스템 및 학원 환경 설정에 의해 기기 푸시가 고의로 제외되었음을 디버깅 단계에서 추적할 수 있도록 제안합니다.
* **푸시 발송 ON (`pushEnabled: true`):**
  * `pushRequired = true`로 레코드를 삽입하며, 실제 푸시 발송 워커가 이를 픽업하여 처리를 시도합니다.

## 9. 중복 방지 및 설정 변경의 소급 적용 정책

* **과거 이벤트를 소급하지 않는 원칙:**
  * 학원이 특정 시점에 학부모 메시지 및 푸시 설정을 `OFF`에서 `ON`으로 변경하더라도, **과거 설정이 꺼져 있을 때 생성되었던 출결 로그나 납부 완료 건에 대해 알림을 소급하여 생성 및 발송하지 않습니다.**
  * **정책 문구:** `"설정 변경은 변경 시점 이후 발생하는 이벤트에만 적용한다."`
  * *이유:* 소급 발송 시 수십 수백 건의 알림이 학부모 기기로 일시에 쏟아지는 스팸 폭탄 장애와 인프라 병목을 방지하기 위함입니다.
* **미결제 수납 건에 대한 수동 조치 (후속 후보):**
  * 단, 수강료 및 교재비 연체 등 현재 진행형(`open` 상태)인 결제 건에 대해서는 원장이 필요 시 "수동 재생성" 하거나 오늘 콘솔의 Handoff 기능을 통해 직접 보낼 수 있으므로 자동 소급을 배제하더라도 행정 구멍은 발생하지 않습니다.

## 10. 앱 설치 여부 및 푸시 가능 상태와의 종속 구조

모바일 푸시가 실제로 발송 및 수신되려면 학원의 관리 설정 외에도 사용자의 스마트폰 인프라 조건이 일치해야 합니다.

* **실제 Push 발송 트리거 조건 (AND 연산):**
  1. 학원 환경 설정의 `messageEnabled === true` (메시지함 적재 허용)
  2. 학원 환경 설정의 `pushEnabled === true` (기기 푸시 전송 허용)
  3. 타겟 보호자(`parentContact`)의 모바일 디바이스에 학부모 전용 앱이 1회 이상 설치되어 유효한 기기 토큰(Token)이 DB에 등록된 상태.
  4. 학부모 모바일 기기 OS 자체 설정에서 앱 알림 수신이 차단되지 않은 상태.
* **본 Phase의 논리적 범위:**
  * Phase 16G에서는 학원 환경 설정인 1번과 2번의 정책 구조를 설계하는 데 집중합니다.
  * 실제 사용자의 기기 토큰 상태(3번, 4번)를 체크하여 발송 성공/실패 상태를 핸들링하는 로직은 향후 앱 배포 및 토큰 수집 모듈이 구비되는 후속 Phase에서 연동을 구축합니다.

## 11. 비용 기반 알림 채널(알림톡/문자)과의 관계 규정

* **학부모 앱 알림과 알림톡/문자의 완전 독립:**
  * 본 `학부모 메시지/푸시 설정`은 통신료가 발생하지 않는 **학부모 전용 스마트폰 앱 내 메시지함 및 인앱 푸시**에 한정한 설정입니다.
  * 학원 환경 설정에서 등/하원 푸시를 OFF로 두었더라도, 외부 SMS/카카오 알림톡 서비스와 연동된 자동 발송 시스템은 비용 정책 및 해당 연동 설정에 따라 별개로 동작합니다.
  * **경고 안내 문구 제안:** 설정 UI 최상단에 `"이 설정은 학부모 앱의 메시지함 및 기기 푸시에만 적용되며, 문자 및 카카오 알림톡 자동 발송은 별개로 제어됩니다."` 라는 경고 문구를 삽입하여 사용자의 혼선을 예방합니다.

## 12. 보안 및 운영 주의사항

* **푸시 메시지의 평문 노출 제한:**
  * 스마트폰 잠금화면 등에 표출되는 기기 푸시 페이로드(Payload)에는 학생의 결석 여부, 민감한 미수납 액수 등 보안이 필요한 민감한 수치를 노출하지 않고 요약 형태로만 구성합니다.
  * *예시:*
    * *부적절:* `[평화음악학원] 홍길동 원생의 수강료 150,000원이 연체되어 6월 20일까지 입금해 주셔야 합니다.`
    * *적절:* `[평화음악학원] 수강료 납부 안내문이 발행되었습니다. 상세 내용은 앱의 메시지함에서 확인하세요.`
* **메시지함 내 상세 정보 봉인:**
  * 학부모가 앱에 로그인해야만 볼 수 있는 인앱 메시지함(`parentMessages`) 안에는 청구액, 기한, 계좌번호 등 상세 명세를 모두 포함하여 영속 보관합니다.
* **권한 통제 (Authorization Guard):**
  * 본 알림 제어 환경 설정을 수정할 수 있는 사용자는 학원의 `원장(Director)` 또는 `최고 관리자(Admin)` 등급으로 한정합니다.
  * `강사(Staff)` 및 일반 직원은 설정을 조회만 가능하고 수정 단추는 비활성화 처리하여 내부 인원의 임의 조작을 차단합니다.
* **설정 변경 이력 보존 (Audit Log 후보):**
  * 향후 설정 변경 시 변경 주체(누가), 변경 시간(언제), 변경 전후의 값(어떻게)을 기록하는 로그 시스템을 구현하여 설정 분쟁을 방지하도록 백로그를 추가해 둡니다.

## 13. 구현 완료 후 수동 확인 포인트 (QA Checklist)

기획안 구현 완료 단계에서 원활한 검수를 위해 검증해야 하는 포인트입니다.

* [ ] **메뉴 접근 및 권한 통제:** 원장 계정으로는 설정 수정이 가능하고, 강사 계정으로 접속했을 때는 수정 기능이 비활성화되거나 경고 팝업이 노출되는지 확인합니다.
* [ ] **토글 간 종속성 작동:** `[메시지함 저장]`을 OFF로 변경했을 때 우측의 `[푸시 발송]` 토글이 연동되어 자동으로 비활성화(Disabled) 및 OFF 처리되는지 점검합니다.
* [ ] **설정 저장 및 영속화:** 다양한 ON/OFF 조합으로 설정값을 저장한 후 페이지를 새로고침했을 때 설정 상태가 데이터베이스로부터 정확히 재로드되는지 검증합니다.
* [ ] **실행 훅 설정 분기 (B형):** `messageEnabled: true`, `pushEnabled: false`인 상태에서 원생 등원 태깅을 진행하고, `parentMessages` 데이터가 메시지함에는 정상적으로 쌓였으나 푸시 전송은 완전히 차단(`pushRequired = false` 또는 `pushStatus`에 `'skipped_by_setting'` 기록 확인)되었는지 데이터베이스 또는 로그를 검증합니다.
* [ ] **사일런트 차단 분기 (C형):** `messageEnabled: false`인 상태에서 수강료 미수납 배치 작업을 강제로 트리거하여, `parentMessages`에 새로운 로우가 일절 삽입되지 않고 푸시 발송도 완전히 일어나지 않았는지 검사합니다.
* [ ] **안내 헬퍼 가이드 가시성:** 설정 UI 내부에 "문자/알림톡 발송과는 무관하다"는 정보 가이드 텍스트와 "메시지함 저장을 켜야 푸시를 활성화할 수 있다"는 안내 툴팁이 명시적으로 노출되어 직관적으로 이해되는지 원장 관점에서 검토합니다.

## 14. 후속 구현 단계 제안

* **Phase 16G-1: settings 스키마 및 기본값 추가**
  * 기존 데이터베이스 설정 모델(Settings 스키마) 내에 `parentMessageSettings` 필드를 추가하고 기본 데이터셋 마이그레이션 스크립트를 작성합니다.
* **Phase 16G-2: 학원정보관리 UI 섹션 추가**
  * 학원정보관리 내 UI 설정 섹션 및 비활성화(disabled) UX가 적용된 토글 UI 구현.
* **Phase 16G-3: parentMessages 생성 훅에서 설정값 참조**
  * 등하원 출결 이벤트 및 billing/overdue 처리 트랜잭션 훅에서 학원의 설정을 먼저 읽어 레코드 생성 여부를 제어하는 데코레이터/미들웨어를 연계합니다.
* **Phase 16G-4: pushRequired 및 푸시 상태 정책 반영**
  * `pushEnabled` 값에 따라 `pushRequired` 플래그 처리 및 `parentMessages.pushStatus` 또는 별도 로그에 `'skipped_by_setting'` 상태를 바인딩하는 코드를 구현합니다.
* **Phase 16G-5: E2E 테스트 보강**
  * Playwright E2E 시나리오를 구성하여 토글 변경 행위 및 실제 메시지함/푸시 큐 적재 분기를 시스템적으로 검증하는 테스트 코드를 구축합니다.

## 15. 최종 권고안 및 요약 결론

1. **메시지함과 푸시의 물리적 분리:** 메시지함은 데이터의 '생성 및 적재'를, 푸시는 스마트폰으로의 '알림 송출'을 담당하며 두 기능의 ON/OFF 스위치를 분리하여 운영의 유연성을 극대화합니다.
2. **엄격한 하향식 종속 관계:** 메시지함 저장을 꺼두는 것은 알림 서비스 자체를 받지 않겠다는 뜻이므로, 기기 푸시 역시 강제로 disabled 및 OFF 처리하여 정합성 오류를 미연에 방지합니다.
3. **영향 범위 격리:** 이 설정은 학부모 전용 스마트폰 앱의 알림 영역에만 국한되며, 학원 비용과 연동되는 수동 메시지 보내기(SMS/알림톡) 채널과는 완전히 독립적으로 운영되어 학원의 불필요한 행정 혼선과 비용 지출을 예방합니다.
4. **소급 적용 배제:** 설정값의 변경은 오직 변경을 실행한 시점 이후 새로 생성되는 행정 이벤트부터 순차 적용하여 시스템 과부하 및 학부모 알림 폭탄 민원을 원천 차단합니다.
5. **안전한 보안 구조 설계:** 외부 화면에 단순 송출되는 푸시 페이로드에는 수납 금액 등의 민감 정보를 제외하고 요약 문구만 전송하며, 상세 명세는 로그인 기반의 보안이 적용된 메시지함 내부에만 보관하도록 통제합니다.
