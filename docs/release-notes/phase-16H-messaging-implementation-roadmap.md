# Phase 16H 설계 정의서: 메시징 설계 통합 구현 로드맵

본 문서는 Phase 16A부터 Phase 16G까지 기획 및 설계된 학부모 메시징 정책, 수신자 모델, 메시지함 스키마, 메시지 작성 UX, 오늘 원장 콘솔 Handoff 및 수신 설정 정책을 단일한 마스터 로드맵으로 통합하고, 실제 시스템 구축을 위한 순서, 기술적 의존성, 보류 항목, 핵심 리스크 완화안 및 E2E 테스트 전략을 정의하는 최종 구현 로드맵서입니다.

> [!IMPORTANT]
> 본 Phase 16H 단계는 **설계 및 정책 정의 문서화 단계**입니다. 실제 소스 코드 수정, DB 마이그레이션 쿼리 실행, UI 컴포넌트 마크업 작성, 푸시 인프라 및 SMS/알림톡 API 연동 등은 **이번 Phase 범위에 포함되지 않으며** 후속 개발 Phase로 위임합니다.

---

## 1. Phase 16 전체 목표 요약

Phase 16의 궁극적 지향점은 학원의 수동/자동 행정 메시지 송출 구조를 체계화하여 **학원의 통신 비용을 최소화하고, 행정 누락을 방지하며, 학부모 알림의 도달율을 극대화**하는 것입니다.

* **학부모 메시지함 및 parentMessages 모델:** 비용이 들지 않는 인앱 메시지함을 구축하여 행정 알림의 주 채널로 활용합니다.
* **parentContacts 모델:** 원생 1명당 최대 2명의 보호자(대표/부 보호자)를 수렴할 수 있는 연락처 구조를 확립하여 수신처 관리의 무결성을 제공합니다.
* **메시지 보내기 UX 개편:** 복수 수신자 선택, 템플릿 로드, 안전 발송 가드레일이 탑재된 통합 작성기 뷰를 구축합니다.
* **오늘 원장 콘솔 Handoff:** 오늘 업무 큐에서 메시지 작성기로의 Payload 직렬화 전달 및 처리 대기 상태 유지를 통해 원장의 행정 흐름을 동기화합니다.
* **메시지함/푸시 설정 (parentMessageSettings):** 행정 이벤트별로 학부모 알림 생성 및 모바일 푸시 발송 여부를 학원 환경 설정에 종속시킵니다.
* **통신 채널 경계선 명확화:** 알림톡 및 문자(SMS/LMS) 발송 모듈은 비용 발생 채널로서 본 인앱 알림/푸시 설정과 완전히 분리되어 관리되며, 실제 API 연동 및 학부모 기기 토큰 수집 등은 후속 Phase에서 연차적으로 진행합니다.

## 3. 핵심 데이터 모델 요약

### 1) parentMessages (학부모 인앱 메시지함)
* **역할:** 학부모 전용 스마트폰 앱의 메시지 리스트에 표출될 메시지의 원천 데이터를 담는 테이블.
* **핵심 필드:**
  * `id` (UUID, PK)
  * `academyId` (FK, 학원 식별자)
  * `studentId` (FK, 원생 식별자)
  * `parentContactId` (FK, 수신 보호자 식별자)
  * `category` (Enum: `attendance`, `billing`, `book`, `notice`, `consult`)
  * `type` (String, 상세 이벤트 코드: `check_in`, `tuition_overdue`, `book_billing` 등)
  * `title` / `body` (String, 발송 시점 치환 완료된 메시지 원문)
  * `pushRequired` (Boolean, 모바일 기기 푸시 발송 필요 여부)
  * `pushStatus` (필요 시 parentMessages.pushStatus 또는 후속 push log 구조에 `pending`, `sent`, `failed`, `skipped_by_setting` 상태를 기록하는 방안을 검토)
  * `readAt` (DateTime, 학부모의 메시지 읽음 일시 - null 이면 안읽음)
  * `dedupeKey` (String, Unique 제약: 중복 발송 방지를 위한 `studentId_type_date` 또는 `paymentId_type` 결합 키)
  * `relatedDomainType` / `relatedDomainId` (외래 바인딩용 도메인 매핑 정보)

### 2) parentContacts (보호자 연락처 및 수신자 모델)
* **역할:** 원생 1명에 매핑되는 보호자 연락처 엔티티로, 수신 권한 및 대표 보호자 설정을 통제.
* **핵심 필드:**
  * `id` (UUID, PK)
  * `studentId` (FK, 원생 식별자)
  * `relation` (Enum: `mother`, `father`, `grandma`, `grandpa`, `etc`)
  * `phone` / `normalizedPhone` (String, 하이픈이 제거되고 010으로 표준화된 휴대폰 번호)
  * `isPrimary` (Boolean, 대표 보호자 여부. 원생당 오직 1명만 `true` 보장)
  * `linkedUserId` (FK, 학부모 전용 앱 회원 가입 시 연계되는 User ID)
  * `snapshot` (JSON, 메시지 발송 시점의 보호자 명명 및 관계를 parentMessages 내에 문자열로 캡처 보존하기 위한 복사본 정보)
  * *※ 실제 앱 설치 여부 및 디바이스 푸시 토큰 관리 필드는 후속 앱 배포 단계에서 추가 설계 및 구축.*

### 3) settings.parentMessageSettings (학원별 알림 발송 제어)
* **역할:** 학원 단위의 알림 송출 정책 통제 설정.
* **핵심 필드 구조:**
  * `messageEnabled` (Boolean, 인앱 메시지함 적재 허용 여부)
  * `pushEnabled` (Boolean, 스마트폰 배너 푸시 발송 허용 여부)
* **논리 종속 규칙:** `messageEnabled === false` 이면 `pushEnabled`는 강제 `false` 처리 및 비활성화(disabled).

## 4. 통합 구현 순서 및 로드맵 제안

현실적인 개발 리소스와 컴포넌트 간 의존성 정합성을 고려하여 최적의 마일스톤 순서를 수립합니다.

```
[데이터 기초 구축] ➔ [UI 데이터 소스] ➔ [핵심 제어판] ➔ [메시지 생성 훅] ➔ [학부모 뷰 구현] ➔ [원장 작성기 개편] ➔ [콘솔 연결]
  (Phase 16I)        (Phase 16J)        (Phase 16K)        (Phase 16L~M)       (Phase 16N)         (Phase 16O)        (Phase 16P)
```

### 1) 단계별 세부 로드맵

* **Phase 16I: 데이터베이스 스키마 구축 및 데이터 마이그레이션**
  * **내용:** `parentMessages`, `parentContacts` 테이블 생성 및 `settings.parentMessageSettings` 스키마 확장. 기존 원생 데이터 내 보호자 연락처 정보를 신규 `parentContacts` 테이블로 이관하는 마이그레이션 스크립트 작성.
* **Phase 16J: 원생 정보 관리 화면 내 보호자 연락처 UI 반영**
  * **내용:** 원생 등록, 수정 및 상세 정보 화면에 보호자 1, 보호자 2 정보 입력 양식과 대표 보호자(`isPrimary`) 지정 라디오 버튼 기능 구축.
* **Phase 16K: 학원 환경 설정 내 메시지/푸시 설정 화면 구현**
  * **내용:** 학원정보관리 화면 하단에 `학부모 메시지/푸시 설정` 섹션을 추가하고, [메시지함 저장] OFF 시 [푸시 발송] 토글이 자동으로 비활성화(disabled)되는 UX 흐름 및 API 영속화 구현.
* **Phase 16L: 출결 이벤트 트리거 연동 (등원/하원)**
  * **내용:** 출결 키패드 태깅 시점에 학원의 설정을 읽어 `parentMessages` 레코드와 푸시 대기 행을 자동 생성/스킵하는 비즈니스 엔진 구축.
* **Phase 16M: 결제 및 교재 승인 이벤트 트리거 연동 (수강료/교재비)**
  * **내용:** 청구서 발행, 연체 배치 작업, 완납 처리 및 원장 교재 요청 승인 시점에 `dedupeKey` 기반 중복 삽입 방지가 가미된 자동 메시지 생성 로직 반영.
* **Phase 16N: 학부모 전용 앱/포털 내 메시지함 화면 구현**
  * **내용:** 학부모가 직접 로그인하여 수신된 알림을 시간순으로 확인하고 읽음(`readAt` 업데이트) 처리할 수 있는 리스트/상세 뷰 구축.
* **Phase 16O: 원장용 메시지 보내기 UI 개편**
  * **내용:** 수신 보호자 복수 선택 스위치, 기본 템플릿 머지(Merge) 기능, 발송 전 확인 팝업을 포함하는 개편된 메시지 작성 화면 구현.
* **Phase 16P: 오늘 원장 콘솔 → 메시지 보내기 Handoff 구현**
  * **내용:** 오늘 업무 큐 중 5개 핵심 업무(결석, 수강료 수납, 수강료 미수납, 교재비 미수납, 상담) 옆에 [메시지 보내기] 아이콘을 가시화하고, 뷰 전환 시 Payload 전달 및 발송 완료 후에도 대기(open) 상태를 수동으로 완료하도록 하는 콘솔 연계 구현.

### 2) 제안 사유 및 선행 의존성 배경
* **메시지 작성기 개편(16O)의 선행 필수성:** 오늘 원장 콘솔 Handoff(16P)는 메시지 작성 화면으로 파라미터를 넘겨주어 본문 및 수신처를 채우는 구조입니다. 따라서 작성기 UI 개편이 완료되지 않은 상태에서 옛날 메시지 화면으로 Handoff 연동을 먼저 개발하면, 작성기 개편 시 중복 구현 및 라우팅 브릿지 수정 비용이 발생하므로 **반드시 16O를 완성한 후 16P를 결합**해야 합니다.
* **설정 UI(16K)의 선행 필요성:** 자동 메시지함 생성 로직(16L, 16M)을 개발하기 전, 설정 UI 및 DB 영속화가 완성되어 있어야만 개발 단계에서 ON/OFF 조건에 따른 다양한 분기 테스트를 정합성 있게 검증할 수 있습니다.

## 5. 구현 보류 및 유보 항목

프로젝트의 점진적 릴리즈 및 복잡도 통제를 위해 아래의 기능들은 본 Phase 16 전체 통합 구현 과정에서 명시적으로 제외하고 후속 Phase로 연기합니다.

1. **카카오 알림톡 API 연동:** 실시간 비즈메시지 템플릿 승인 및 API 통신 모듈 연동 보류.
2. **문자(SMS/LMS) 게이트웨이 연동:** 유료 이동통신사 게이트웨이 연동 및 잔액 차감 로직 보류.
3. **실제 모바일 기기 푸시 토큰 수집:** 학부모 기기(iOS/Android)의 FCM/APNS 푸시 토큰 등록 및 수신 수락 권한 처리 보류.
4. **학부모 스마트폰 앱 정식 배포:** 인앱 메시지함 렌더링용 프로덕션 패키징 및 스토어 등록 프로세스 보류.
5. **원장 및 학원 교직원 전용 알림 푸시:** 내부 운영용 디바이스 푸시 알림 보류.
6. **운영 상세 권한 세분화:** 강사별 수신자 수정 제한 등의 디테일한 ACL(Access Control List) 보안 미들웨어 구현 보류.
7. **원생 휴원/퇴원 시 자동 수납 정산 알림:** 정산 취소 및 이력 보존의 정합성이 까다로우므로 정책 유보.
8. **알림톡 실패 시 문자 Fallback 자동 발송:** API 인프라 구축 완료 후 비용 최적화 단계로 이관하여 보류.

## 6. 구성 요소 간 의존성 및 제약 사항

* **[제약 1] parentContacts ➔ 복수 수신자 선택:** `parentContacts` 수신처 스키마가 데이터베이스에 존재하고 데이터 마이그레이션이 완료되지 않으면, 메시지 작성 화면의 보호자 1/2 그리드 노출 및 다중 선택 로직을 구현할 수 없습니다.
* **[제약 2] parentMessages ➔ 학부모 메시지함:** 학부모 앱 내 인앱 알림 리스트 화면은 `parentMessages` 테이블의 CRUD 쿼리에 전적으로 의존하므로, 스키마 생성이 선행되어야 합니다.
* **[제약 3] parentMessageSettings ➔ 메시지 및 푸시 생성 엔진:** 등하원 및 결제 트랜잭션 훅에서 학원의 환경 설정을 정상적으로 조회할 수 있어야만, `messageEnabled` 및 `pushEnabled` 플래그에 따라 알림 생성을 차단하는 스위치 로직을 심을 수 있습니다.
* **[제약 4] 모바일 푸시 토큰 ➔ 기기 푸시 발송:** 학부모 연락처(`parentContacts`) 테이블과 디바이스 푸시 토큰 테이블의 1:N 관계 맵이 정립되지 않으면, 설정이 ON이더라도 실제 스마트폰 배너 알림을 쏘아 올릴 수 없습니다.

## 8. E2E 및 유닛 테스트 전략

설계 내용의 안전한 작동을 보장하기 위해 빌드 파이프라인에 추가될 자동화 테스트 커버리지 기준입니다.

* **parentContacts 마이그레이션 Smoke Test:**
  * 기존 `students` 테이블의 보호자 전화번호 정보가 `parentContacts` 신규 레코드로 단 한 건의 누락 없이 올바르게 복사 및 정규화(`normalizedPhone`)되었는지 마이그레이션 전후의 row 수를 교차 검증.
* **parentMessages dedupeKey 중복 차단 테스트:**
  * 동일한 결제 ID(`paymentId`)로 `tuitionOverdue` 타입의 메시지를 2회 연속 생성 시도할 경우, dedupeKey 기반 중복 차단 로직에 의해 생성 시도가 무시되거나 데이터베이스 레벨에서 예외를 던지고 차단되는지 유닛 테스트로 검증.
* **설정 상태별 분기 차단 E2E Test (Settings Integration):**
  * `tuitionBilling` 설정을 `messageEnabled = false`로 변경 저장한 뒤, 가상의 청구서 발행 API를 호출하여 `parentMessages` 테이블에 데이터가 추가되지 않고 완전히 조용한(Silent) 상태가 유지되는지 검증.
* **출결 등하원 자동 메시지 적재 테스트:**
  * 출결 키패드 모킹 API를 통해 등원 신호를 송신한 후, `parentMessages`에 해당 원생의 대표 보호자 아이디로 등원 알림 문자열 본문이 성공적으로 빌딩 및 적재되는지 E2E 검증.
* **완납 및 교재 승인 연동 테스트:**
  * 수납 처리 완료(`payment.status = 'paid'`) 트랜잭션 종료 시점에 `tuitionPaid` 메시지함 데이터가 1건 자동 생성되는지 파이프라인 E2E 시나리오 구성.
* **메시지 보내기 수신자 다중 체크 UI 테스트:**
  * Playwright 브라우저를 띄워 메시지 작성 화면 진입 시, 보호자 목록 그리드에서 부 보호자를 추가 체크했을 때 발송 대상 수신처 배열에 전화번호가 동적으로 실시간 추가/제외되는지 컴포넌트 이벤트 테스트 수행.
* **오늘 원장 콘솔 Handoff 및 복귀 테스트:**
  * 결석 Row 옆의 [메시지 보내기]를 클릭하여 작성 화면으로의 화면 전환이 정상 발생하고, 작성 취소 클릭 시 `returnTo` 쿼리 파라미터를 읽어 기존 보던 오늘 콘솔의 필터 탭 그대로 복귀하는지 브라우저 플로우 확인.

## 9. 사용자 수동 확인 포인트 (QA Checklist)

기획 및 개발 완료 후, 원장이 시스템을 사용할 때 느끼는 편의성과 정합성을 사람이 직접 검수하는 항목입니다.

* [ ] **보호자 입력 양식의 조화성:** 원생 등록 및 수정 페이지에서 보호자 1, 보호자 2 휴대폰 번호와 관계를 기입하고 대표 보호자 1인을 지정하는 과정이 자연스러운지 원장 관점에서 검수합니다.
* [ ] **메시지함 구성의 가독성:** 학부모 포털 앱에서 메시지함 탭을 눌렀을 때, 안읽은 알림의 뱃지(Badge) 표시가 명확히 보이고 읽음 처리 시 뱃지가 즉각 소멸하는지 확인합니다.
* [ ] **설정 섹션의 직관성:** 학원 설정 화면의 토글 단추들이 무엇을 의미하는지 한눈에 파악되는지, [메시지함] 토글을 껐을 때 우측의 [푸시] 토글이 막히는 disabled 동작이 사용자 가이드 없이 자연스럽게 납득되는지 평가합니다.
* [ ] **작성 화면의 수신처 인지성:** 원장이 수동으로 메시지를 보낼 때, 수신 보호자의 이름과 연락처가 올바르게 표출되며 대표 보호자가 기본적으로 먼저 선택되어 있어 실수로 인한 전체 스팸 오발송 위험이 최소화되었는지 검토합니다.
* [ ] **오늘 콘솔 화면의 가독성 유지:** [메시지 보내기] 바로가기 아이콘들이 오늘 원장 콘솔의 텍스트 레이아웃을 무너뜨리거나 모바일 화면에서 너무 밀집되어 오작동을 유발하지 않는지 디바이스 뷰포트별로 직접 점검합니다.
* [ ] **안내 본문 문구의 톤앤매너:** 시스템이 발행한 수강료 독촉 및 교재비 수납 안내 문구의 말투가 학부모에게 불쾌감을 주지 않고 학원의 신뢰감을 높일 수 있는 정중한 표현으로 구성되었는지 점검합니다.
