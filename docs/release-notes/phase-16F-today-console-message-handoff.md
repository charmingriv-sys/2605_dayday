# Phase 16F 설계 정의서: 오늘 원장 콘솔 → 메시지 보내기 연결 설계

본 문서는 오늘 원장 콘솔(Today Director Console)의 운영 대기 업무 큐(Row)에서 학부모 대상 메시지 발송이 필요한 핵심 업무들을 필터링하고, 원장 및 직원이 메시지 보내기 화면으로 부드럽게 이동하여 초안 상태의 메시지를 전송할 수 있는 데이터 연동(Handoff) 및 동작 정책 설계서입니다.

> [!IMPORTANT]
> 본 Phase 16F 단계는 **설계 및 정책 정의 문서화 단계**입니다. 실제 라우팅 구현, 메시지 작성 UI 구현, SMS/알림톡 API 연동, parentContacts 마이그레이션 및 parentMessages/푸시 발송 등은 **이번 Phase 범위에 포함되지 않으며** 후속 개발 Phase로 위임합니다.

---

## 1. Phase 16F 범위 정의

### 1) 포함 범위 (In-Scope)
* **메시지 보내기 버튼 노출 기준 수립:** 운영 대기 업무 중 학부모 연락이 필요한 업무와 불필요한(내부용) 업무의 명확한 필터링 정책.
* **Payload 전달 규격 정의:** 업무 큐에서 메시지 작성 화면으로 이동할 때 필요한 정보(taskId, studentId, paymentId 등)의 직렬화(Serialization) 규격.
* **수신자 기본 선택 정책:** Handoff 시 보호자 1/2 중 기본값 설정 규칙.
* **템플릿/초안(Draft) 자동 완성 정책:** 콘솔에서 진입 시 상황별 템플릿의 자동 치환 및 생성 규칙.
* **발송 후 Task 상태 처리 정책:** 메시지 발송 후 원래의 오늘 업무(Task) 상태를 어떻게 종결할 것인가에 대한 처리 표준.
* **설정 의존성 정책 정의:** 교재 지급 승인 등 특정 액션으로 생성되는 자동 알림이 학부모의 메시지/푸시 수신 설정에 귀속되도록 설계하는 구조.
* **구현 단계 사용자 수동 확인 가이드:** 구현 완료 후 기획과의 일치 여부를 검증하기 위한 상세 QA 체크리스트.

### 2) 제외 범위 (Out-of-Scope)
* **실제 웹 라우팅 및 쿼리 스트링 파싱 구현:** 라우터 코드 수정 배제.
* **메시지 보내기 화면 마크업 및 스타일링:** CSS/HTML 작성 배제.
* **SMS, 카카오 알림톡, 모바일 푸시 실시간 전송 인프라 연동:** 외부 통신 모듈 연동 배제.
* **parentContacts 마이그레이션 실행 및 parentMessages 테이블 실제 갱신:** DB 가공 코드 배제.
* **학원 설정 내 "학부모 메시지/푸시 수신 동의 설정" UI 구현:** 설정 화면의 실물 개발 배제 (Phase 16G 이관).

## 2. 메시지 보내기 버튼 노출 기준

오늘 원장 콘솔의 복잡도를 낮추고 행정 효율을 높이기 위해, **대상이 학부모로 명확한 업무에 한해서만** 메시지 보내기 단추를 노출하는 엄격한 가드레일을 적용합니다.

### 1) 노출 대상 업무 (학부모 대상 명확)
* **결석 확인 (`category = 'absent'`):** 당일 미출석 원생으로, 보호자 확인 연락이 최우선이므로 노출.
* **수강료 수납확인 (`category = 'billing'`, status = 'paid'):** 결제 감사 및 감사를 위한 완납 안내장 발송을 위해 노출.
* **수강료 미수납 확인 (`category = 'overdue'`, status = 'unpaid'):** 수강료 납부 기한 경과에 따른 독촉을 위해 노출.
* **교재비 미수납 확인 (`category = 'book_billing'`):** 교재비 납부 연체건 독촉을 위해 노출.
* **상담예약 (`category = 'consult'`):** 상담 일정 리마인드나 예약 확인 문자 발송을 위해 보호자 정보가 명확한 경우 노출.

### 2) 비노출 대상 업무 (내부용 또는 비대상)
* **지각 / 하원누락 (`category = 'attendance_warning'`):** 
  * *비노출 사유:* 원생 지각 및 하원 태그 누락은 시스템의 오인식(기기 장애, 태그 까먹음 등)일 확률이 매우 높으므로, 원장이 별도 수동 확인 없이 바로 반자동 메시지를 보내면 오발송으로 인한 민원이나 오해를 유발할 수 있어 제외합니다.
* **특이근태 / 강사 근태 (`category = 'staff_warning'`):**
  * *비노출 사유:* 강사 지각, 미출근, 퇴근누락 등은 철저히 학원 내부 인적 자원 관리 정보이므로 학부모 대상 메시징 버튼을 차단합니다.
* **주요일정 (`category = 'schedule'`):**
  * *비노출 사유:* 주요일정은 개별 큐 Row에서 즉시 발송하는 구조가 아니라, 주요일정 관리 화면에서 원장이 등록/수정할 때 "학부모 알림 등록 여부"를 직접 설정하는 아키텍처 흐름이 정합성에 맞으므로 제외합니다.
* **운영메모 (`category = 'memo'`):**
  * *비노출 사유:* 원장 전용 메모장이므로 학부모 발송과 무관합니다.
* **교재 확인 (`category = 'book_check'`):**
  * *비노출 사유:* 강사가 청구한 교재를 승인하는 원장의 액션 자체가 핵심이며, 승인 전 교재 요청 단계에서는 별도로 학부모에게 연락할 비즈니스 가치가 없으므로 버튼을 노출하지 않습니다.

## 3. 결석 확인 Handoff 정책

결석 확인 업무는 출결 키패드 마감 후 시스템에서 자동 생성되는 핵심 업무 큐입니다.

* **동작 시나리오:**
  * 당일 출결 태그 마감 기준 결석인 원생이 발견되면 큐에 생성됩니다.
  * 원장은 이 Row 옆의 **[메시지 보내기]** 단추를 클릭해 handoff를 실행할 수 있습니다.
* **메시지 초안 기본 텍스트:**
  > "[#{학원명}] #{원생명} 원생의 오늘 #{수업시간} 수업 출석 기록이 확인되지 않아 안내드립니다. 확인 부탁드립니다."
* **업무 큐 종결 조건:**
  * 메시지 발송 완료 후에도 **오늘 콘솔의 결석 확인 Task는 자동으로 'done' 처리되지 않고 그대로 유지**됩니다.
  * **사유:** 메시지 전송은 단순 안내일 뿐이며, 원생이 실제로 아파서 결석했는지, 무단결석인지 등의 정확한 결석 사유 파악이 원장에 의해 유선상 또는 대면으로 완료된 시점에 원장이 직접 [완료]를 클릭해 큐에서 제거하도록 통제해야 행정 누락이 생기지 않습니다.

## 4. 교재 확인 플로우 정책

강사의 교재 요청부터 교재비 수납까지의 유기적인 비즈니스 흐름을 정의합니다.

```
[강사 교재 요청] ➔ 오늘 콘솔에 category = 'book_check' 태스크 생성 (메시지 버튼 미노출)
       │
       ▼ 원장이 오늘 콘솔에서 [교재 확인] 승인 클릭
[요청 승인 처리]
  1. 원생의 지급 교재 이력 (studentBook) 생성
  2. 교재비 청구서 (payment, unpaid 상태) 즉시 발행 (이 시점에는 미수납 확인 row를 생성하지 않음)
  3. 기존 'book_check' 태스크 큐에서 즉시 소멸 (done 처리)
  4. 후속 Phase 16G 설정 정책에 따라 (ON으로 설정 시) [교재비 수납 안내] parentMessage/푸시 발생
       │
       ▼ 납부 예정일이 지난 뒤에도 unpaid 상태인 경우
[교재비 미수납 발생] ➔ 오늘 콘솔에 category = 'book_billing' 태스크 신규 생성 (메시지 버튼 노출)
       │
       ▼ 원장이 [메시지 보내기] 클릭 ➔ 교재비 독촉 초안 조립 발송
[독촉 메시지 발송] ➔ 태스크는 자동으로 완료되지 않으며, 최종 수납 확인(payment = paid) 처리 시 완료 처리
```

### ⚠ 핵심 정책 규칙
* **교재비 미수납 확인 row 생성 시점 명확화:** 
  * 교재 확인 직후에는 book payment가 unpaid 상태로 즉시 생성됩니다.
  * 이때 교재비 수납 안내 메시지함/푸시 발송은 학부모 메시지/푸시 설정값(후속 Phase 16G에서 정의)에 따라 처리될 수 있습니다.
  * **단, 교재비 미수납 확인 row는 즉시 생성하지 않습니다.** 
  * 교재비 미수납 확인 row는 오직 **납부 예정일이 지난 뒤에도 unpaid 상태일 때** 비로소 오늘 원장 콘솔에 생성됩니다.
* **단일 청구 아키텍처:** 별도의 불필요한 "교재비 청구 전용 row"는 큐에 중복 생성하지 않고, 결제 데이터인 `payment` 발행으로만 처리합니다.
* **교재비 미수납 확인 row의 성격:** 해당 큐의 [완료] 액션은 오늘 큐에서 업무를 확인했다는 체크일 뿐이며, 실제 수납이 완료되어 돈이 들어온 것을 의미하지 않습니다. 실제 수납 완료는 오직 `payment` 엔티티의 상태를 `paid`로 업데이트하는 수납창구(Billing)에서만 결정됩니다.

## 5. 학부모 메시지/푸시 설정 의존성

교재 확인 이후 메시지함 저장/푸시 발송 여부는 후속 Phase 16G에서 정의될 학부모 메시지/푸시 설정값을 참조해야 합니다. 본 Phase 16F에서는 해당 설정 UI 및 스키마를 직접 구현하지 않으며, 향후 구현될 기능과의 논리적 의존성 규칙만을 다음과 같이 기획합니다.

### 1) 설정 매트릭스 구성안 (후속 Phase 16G 설계 대상)
원장은 **학원 설정 > 알림 발송 제어** 메뉴를 통해 다음 이벤트별로 알림의 저장 및 송출 여부를 ON/OFF 할 수 있는 설정을 미래에 제공할 예정입니다.

* **등원**
* **하원**
* **수강료 수납 안내 (수강료 청구)**
* **수강료 미수납 안내 (수강료 연체)**
* **수강료 수납 완료 (수강료 영수증)**
* **교재비 수납 안내 (교재비 청구)**
* **교재비 미수납 안내 (교재비 연체)**
* **교재비 수납 완료 (교재비 영수증)**

### 2) 설정 간 종속 관계 (Dependency Rule)
> [!IMPORTANT]
> **푸시 알림은 인앱 메시지함 저장을 필수 보조하는 채널입니다.**
> 1. 특정 이벤트의 **[메시지함 저장] 설정이 OFF** 상태라면, **[푸시 발송] 설정은 자동으로 비활성화(Disabled) 및 OFF 강제 처리**해야 합니다. (메시지 데이터가 저장되지 않는데 기기 푸시만 단독으로 쏠 수는 없습니다.)
> 2. [메시지함 저장]이 ON일 때에만 [푸시 발송]을 선택적으로 ON/OFF 할 수 있습니다.

### 3) 교재비 청구(승인 시점) 연동 예시 (설정값 도입 이후 동작 시나리오)
향후 설정 기능이 구축된 뒤, 원장이 콘솔에서 [교재 확인]을 클릭할 시의 동작 예측 모델입니다:
* `메시지함 저장 = ON, 푸시 = ON 설정인 경우` ➔ `parentMessages` 레코드(`type = book_billing`) 생성 및 `pushRequired = true` 설정 후 발송 큐 적재.
* `메시지함 저장 = ON, 푸시 = OFF 설정인 경우` ➔ `parentMessages` 레코드 생성하되 `pushRequired = false` 처리하여 사일런트 저장.
* `메시지함 저장 = OFF 설정인 경우` ➔ `parentMessages` 및 모바일 푸시 둘 다 생성하지 않음 (알림 미발송).

## 6. row별 연결 정책 표

오늘 원장 콘솔의 큐 행(Row) 분류별 메시지 버튼 노출 정책 및 세부 규격 요약표입니다.

| 카테고리 (`category`) | 업무 유형 | 메시지 버튼 노출 | 수신 대상 | 기본 템플릿 | 전달 Payload 구성 | 비노출 사유 / 비고 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `memo` | 운영메모 | **N** | - | - | - | 내부 전용 메모 업무 |
| `absent` | 결석 확인 | **Y** | 보호자 1 (`parent1`) | 결석 안내 | `studentId`, `classDate`, `classStartTime`, `classEndTime`, `teacherId`, `subjectOrInstrument` | - |
| `attendance_warning` | 지각 / 누락 | **N** | - | - | - | 오인식으로 인한 잘못된 연락 방지 가드 |
| `staff_warning` | 강사 근태 | **N** | - | - | - | 내부 인사/행정 운영 정보 격리 |
| `billing` (paid) | 수강료 수납확인 | **Y** | 보호자 1 (`parent1`) | 수강료 수납 완료 | `paymentId`, `studentId`, `amount`, `billingMonth`, `dueDate`, `paymentType: tuition` | 수강료 수납 완료 영수증 알림 |
| `overdue` (unpaid) | 수강료 미수납 확인 | **Y** | 보호자 1 (`parent1`) | 수강료 미수납 안내 | `paymentId`, `studentId`, `amount`, `billingMonth`, `dueDate`, `paymentType: tuition` | 수강료 연체 독촉 알림 |
| `schedule` | 일정확인 | **N** | - | - | - | 주요일정 관리 내 등록 제어 정책 준수 |
| `book_check` | 교재 확인 | **N** | - | - | - | 원장 승인이 메인 액션인 단계 |
| `book_billing` | 교재비 미수납 | **Y** | 보호자 1 (`parent1`) | 교재 독촉 | `paymentId`, `bookIssueRequestId`, `studentId`, `bookName`, `amount`, `paymentType: book` | 교재비 납기 경과 독촉 |
| `consult` | 상담예약 | **Y** | 보호자 1 (`parent1`) | 상담 안내 | `taskId`, `studentId`, `consultAt`, `consultMemo` | 보호자가 매핑되어 있을 때만 노출 |

## 7. Payload 전달 규격

업무 큐에서 [메시지 보내기]를 클릭했을 때 로드되는 ViewState 파라미터 구조입니다.

### 1) 공통 매핑 구조
```json
{
  "source": "today_console",
  "taskId": "task_absent_S1_0615",
  "taskType": "system_warning",
  "taskCategory": "absent",
  "studentId": "S1",
  "relatedDomainType": "attendance",
  "relatedDomainId": "ATT_LOG_0091",
  "suggestedTemplateType": "attendance_absent",
```

## 11. 발송 후 Task 상태 처리 정책

> [!IMPORTANT]
> **메시지 전송 성공이 곧 업무의 실질적인 조치 완료를 의미하지 않습니다.**

* **상태 완료의 수동화 원칙:**
  * 결석, 미수납, 상담 등의 업무는 메시지 발송이 끝났더라도 학부모가 확인 및 입금 등의 후속 액션을 취하거나 원장이 직접 내용을 한 번 더 정리해야 업무가 완전히 완결됩니다.
  * 따라서 발송이 성공하더라도 오늘 콘솔의 Task 상태를 **자동으로 `done` 처리하지 않고 대기(`open`) 상태로 노존**합니다.
  * 원장은 원래의 오늘 콘솔 화면으로 복귀하여 업무를 최종 확인한 뒤, **수동으로 [완료] 버튼을 클릭**하여 큐에서 처리해야 합니다. (이로써 행정 관리 상의 누락 사고를 차단합니다.)
* **추적 링크 제공:**
  * 대기 태스크의 description 또는 상세 레이어 우측에 "방금 전송한 메시지 발송 로그 확인하기" 링크를 연결하여, 원장이 자신이 보낸 이력을 신속하게 검토할 수 있도록 연계 공간을 열어둡니다.

## 17. 최종 권고안 및 요약 결론

1. **메시지 버튼 노출:** 학부모와 관련된 명확한 5가지 업무(결석, 수강료 수납, 수강료 미수납, 교재비 미수납, 상담)에만 메시지 버튼을 제한 노출합니다.
2. **연동 예외 대상:** 지각/하원누락은 오인식 우려로 연동에서 배제하며, 교재 확인은 원장의 승인 액션 자체가 완료 목적이므로 메시지 버튼을 표시하지 않습니다.
3. **수신처 지정:** 무분별한 전송 방지를 위해 `parent1`(대표 보호자)만 기본 자동 선택 처리합니다.
4. **Task 상태 관리:** 메시지 발송이 업무 확인의 물리적 종결이 아니므로, 발송 후에도 Task를 자동으로 완료하지 않고 원장이 직접 오늘 콘솔에서 확인 후 수동으로 완료하도록 통제합니다.
5. **설정값 종속성:** 교재 확인 등으로 파생되는 자동 알림은 (후속 Phase 16G에서 도입될) 메시지함 저장 설정이 ON일 때에만 생성하며, 메시지함 저장이 OFF되면 푸시도 함께 꺼지는 엄격한 종속성 규칙을 수립하고 이에 귀속되도록 설계합니다.
