DayDay Product Strategy · Music Academy Deep Dive

음악학원 기준 추가 기능 기획

현재 DayDay는 음악학원 운영 MVP로 충분한 표면적을 갖추기 시작했다. 다음 단계의 핵심은 단순히 메뉴를 더 붙이는 것이 아니라, 음악학원에서 실제로 돈과 시간을 잡아먹는 수강권, 회차, 보강, 강사 정산, 진도, 행사의 예외를 제품 구조 안으로 끌어오는 것이다.

작성일: 2026-05-30 · 기준 프로젝트: Phase 4B 이후 director view 모듈 분리 완료 상태

1. 핵심 판단

음악학원 운영의 본질은 “학생이 주 몇 회 수업을 듣는다”가 아니라 학생이 어떤 레슨 권리를 구매했고, 언제 어떻게 소비하며, 예외 상황을 어떻게 처리하는가에 가깝다.

따라서 다음 제품 기획의 중심은 시간표가 아니라 수강권/회차권/보강 엔진이어야 한다. 이 엔진이 있어야 주 몇 회, 월 몇 회, 타임제, 회차권, 입시 특강, 연습실 이용권, 그룹 레슨까지 하나의 구조로 처리할 수 있다.

2. 음악학원에서 실제로 존재하는 수강 형태

수강 형태 예시 필요한 제품 기능 주의할 운영 예외
고정 요일제 매주 화/목 17:00 피아노 반복 시간표, 고정 강사, 고정 방 배정 공휴일, 학원 휴강, 선생님 사정 취소
월 회차제 월 4회, 월 8회, 월 12회 월별 회차 생성, 잔여 회차, 이월 여부 중도 등록, 결석 차감 여부, 보강권 만료
타임제 월 240분, 600분 패키지 분 단위 차감, 회당 수업시간 기록 30분/40분/50분 혼합 수업, 분 단위 잔여 처리
자유 예약제 가능한 시간 중 예약 예약 슬롯, 취소 정책, 대기자 당일 취소, 노쇼, 선생님별 예약 가능 시간
입시/콩쿠르 특강 시험 전 10회 집중 레슨 단기 패키지, 추가 청구, 집중 일정 정규 수업과 특강 수업의 회차/정산 분리
그룹/앙상블 바이올린 앙상블, 합창 다인 수업, 개별 출결, 수업별 명단 한 명 결석 시 전체 수업 유지, 개별 보강 여부
연습실 이용권 월 연습실 10시간 공간 예약, 이용 시간 차감 레슨실과 연습실 충돌, 악기/장비 상태
가족/형제 묶음 형제 2명 할인 가족 청구, 할인 규칙, 보호자 기준 통합 고지 한 명만 퇴원, 한 명만 미납, 자녀별 과목 분리

3. 최우선으로 설계해야 할 5개 도메인

1. Plan

판매 가능한 수강 상품이다. 월 4회, 240분권, 입시 특강 10회, 연습실 10시간 같은 정의를 담는다.

공통 코어

2. Enrollment

학생이 특정 Plan에 등록한 기록이다. 시작일, 종료일, 담당 강사, 과목, 할인, 청구 방식을 연결한다.

공통 코어

3. Session

실제로 예정되었거나 진행된 수업 단위다. 고정 수업, 예약 수업, 보강, 특강을 모두 포함한다.

공통 코어

4. Usage Ledger

회차 또는 시간이 어떻게 차감되었는지 기록하는 장부다. 환불, 이월, 정산의 근거가 된다.

핵심 신규 엔진

5. Makeup Credit

결석, 휴강, 선생님 사정으로 발생한 보강권이다. 만료일, 사용 여부, 생성 사유를 기록한다.

음악학원 핵심

운영 질문

학생은 “수업을 듣는 사람”이 아니라 “어떤 권리를 구매했고, 어떤 방식으로 소비하는 사람”으로 모델링해야 한다.

제품 관점

4. 보강/결석 정책 엔진

음악학원에서 가장 큰 운영 피로는 보강이다. 출석, 지각, 결석만으로는 부족하고, 결석 사유별 정책이 달라야 한다.

상황 권장 기본 처리 제품 기능
학생 사전 취소 정책에 따라 보강권 생성 또는 회차 미차감 취소 마감 시간, 보강권 자동 생성
당일 취소 기본 회차 차감, 원장 재량으로 보강 가능 당일 취소 표시, 예외 승인
무단 결석 회차 차감 노쇼 기록, 학부모 자동 알림
선생님 사정 취소 보강권 자동 생성 또는 회차 미차감 강사 사유 기록, 대체 강사 배정
학원 휴강/공휴일 전체 회차 미차감 또는 일괄 보강 휴강일 캘린더, 일괄 정책 적용

환불/반환은 실제 운영과 법적 고지에 연결된다. 학원 교습비와 반환 관련 사항은 국가법령정보센터와 생활법령정보의 최신 내용을 확인해 배포 전 별도 검토 항목으로 관리해야 한다.

5. 강사 정산 기능

음악학원은 강사 정산 방식이 단순하지 않다. 고정급, 회당 정산, 매출 비율, 특강 별도 정산이 섞일 수 있다. DayDay가 원장의 ERP가 되려면 출석 기록이 자연스럽게 강사 정산 근거로 이어져야 한다.

정산 방식

  • 고정 월급
  • 수업 회당 정산
  • 학생 수 기준 정산
  • 매출 비율 정산
  • 입시/특강 별도 정산
  • 그룹수업 분배 정산

대시보드 지표

  • 강사별 실제 수업 횟수
  • 강사별 매출 기여
  • 보강으로 추가 발생한 수업
  • 결석인데 정산해야 하는 수업
  • 미납 학생의 강사 정산 포함 여부

6. 음악학원다운 차별 기능

진도/곡/교재

학생별 현재 교재, 연습곡, 완료 곡, 다음 과제, 선생님 코멘트, 영상 링크를 기록한다.

발표회/콩쿠르

참가자, 곡명, 작곡가, 반주자, 참가비, 리허설, 순서표, 학부모 공지를 관리한다.

연습실/방/악기

피아노실, 드럼실, 보컬룸, 앙상블실, 대여 악기, 조율/수리 일정을 관리한다.

7. 상담/전환/이탈 관리

원장 입장에서 매출을 지키는 기능은 “출석 기록”만이 아니다. 신규 문의, 체험수업, 퇴원 위험, 미납과 결석이 같이 발생하는 학생을 빨리 잡아내는 기능이 필요하다.

필요 기능

  • 신규 상담 문의 기록
  • 체험수업 예약
  • 체험 후 등록 전환율
  • 미등록 사유
  • 학부모 불만/요청 히스토리

위험 신호

  • 최근 2회 연속 결석
  • 미납과 결석 동시 발생
  • 보강권 장기 미사용
  • 수강권 만료 임박
  • 상담 후 미등록 장기 방치

8. 우선순위 로드맵

Phase P1

수강권/회차권/보강 엔진 설계

Plan, Enrollment, Session, Usage Ledger, Makeup Credit의 데이터 모델과 정책 테이블을 설계한다.

Phase P2

현재 주 몇 회 구조와의 호환 레이어

기존 학생/수업 데이터를 새 수강권 구조로 해석할 수 있는 migration-safe mapping을 만든다.

Phase P3

운영 화면 설계

원장 화면에는 잔여 회차, 만료 예정, 보강 대기, 미차감 수업을 보여주고, 강사 화면에는 오늘 수업과 과제를 중심으로 단순화한다.

Phase P4

수납/정산 연결

수강권 판매, 청구, 결제, 회차 차감, 강사 정산이 하나의 흐름으로 이어지게 만든다.

Phase P5

음악학원 특화 확장

진도/곡/교재, 발표회/콩쿠르, 연습실/악기 자원 관리, 상담/이탈 관리를 순차 추가한다.

9. 다음 Phase용 실행 프롬프트

아래 프롬프트는 다음 LLM에게 그대로 전달할 수 있도록 작성했다.

# Phase P1 프롬프트: 음악학원 수강권/회차권/보강 엔진 설계

너는 DayDay 음악학원 MVP의 다음 제품 기획 및 데이터 설계 작업을 수행한다.

현재 DayDay는 원장/강사/학부모 화면, 출결, 수납, 교재, 공지, 설정 등을 갖춘 음악학원 관리 시스템이다.
하지만 현재 구조는 주 몇 회 수업 중심에 가깝고, 실제 음악학원에서 사용하는 월 몇 회, 회차권, 타임제, 보강권, 특강, 연습실 이용권을 충분히 표현하지 못한다.

이번 Phase P1의 목표는 기능 구현이 아니라, 다음 제품 구조를 설계하는 것이다.

핵심 질문:
학생은 단순히 수업을 듣는 사람이 아니라, 어떤 수강 권리를 구매했고 언제 어떻게 소비하는가?

반드시 설계할 도메인:
1. Plan: 판매 가능한 수강 상품
2. Enrollment: 학생의 수강 등록
3. Session: 실제 예정/진행 수업
4. Usage Ledger: 회차/시간 차감 기록
5. Makeup Credit: 보강권

설계 대상 수강 형태:
- 주 몇 회 고정 요일제
- 월 4회/8회 같은 월 회차제
- 240분/600분 같은 타임제
- 자유 예약제
- 입시/콩쿠르 특강
- 그룹/앙상블 수업
- 연습실 이용권
- 가족/형제 할인

반드시 포함할 내용:
- 데이터 모델 초안
- 기존 StateStore 구조와 연결 방식
- localStorage 단계에서의 최소 구현 방식
- 추후 Supabase/PostgreSQL 전환을 고려한 테이블 후보
- 보강/결석 정책 테이블
- 수납/청구와 연결되는 방식
- 강사 정산과 연결되는 방식
- 기존 학생/수업 데이터와의 마이그레이션 전략
- UI 화면 초안: 원장, 강사, 학부모 각각
- MVP에서 먼저 만들 기능과 나중에 미룰 기능

주의:
- 지금 바로 대규모 구현하지 말고 설계 문서부터 작성한다.
- 기존 주 몇 회 구조를 깨지 않는 호환 전략을 포함한다.
- 업종 공통으로 재사용 가능한 내용은 `pj_daday_skill.md`에 반영할 후보로 정리한다.
- 환불/교습비 반환은 배포 전 법규 확인 항목으로 분리하고, 최신 법령은 별도 검토가 필요하다고 명시한다.

결과물:
- `docs/music-academy-lesson-credit-engine.md` 신규 작성
- 필요 시 `docs/state-store-map.md`에 향후 데이터 도메인 후보 추가
- 작업 완료 후 Phase P2 진행 가능 여부 판단

10. 참고 및 배포 전 확인

  • 학원 교습비와 반환 관련 사항은 국가법령정보센터의 학원의 설립ㆍ운영 및 과외교습에 관한 법률 및 시행령/시행규칙을 배포 전 다시 확인해야 한다.
  • 생활법령정보의 교습비 등 징수 안내와 교습비 등의 산정 및 반환 안내를 운영 정책 검토 자료로 활용한다.
  • 이 문서는 제품 기획 자료이며 법률 자문 문서가 아니다. 실제 배포 전에는 지역 교육청 기준, 표시/고지 의무, 환불 정책을 별도로 확인한다.
