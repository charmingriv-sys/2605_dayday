# Phase 16C 설계 정의서: 학부모 연락처 및 수신자 모델 확장 설계

본 문서는 원생정보에서 학부모 연락처를 최대 2개까지 저장 및 관리하고, 이를 메시지 보내기, 학부모 메시지함(`parentMessages`), 기기 모바일 푸시 알림 상태와 유기적으로 연결할 수 있도록 지원하는 수신자 모델 확장 설계서입니다.

> [!IMPORTANT]
> 본 Phase 16C 단계는 **설계 및 정책 정의 문서화 단계**입니다. 실제 소스 코드 구현, 데이터베이스 마이그레이션 스크립트 작성 및 실행, UI 적용, 메시지 발송 API 연동 등은 **이번 Phase 범위에 포함되지 않으며** 모두 후속 개발 Phase로 위임합니다.

---

## 1. Phase 16C 범위 정의

### 1) 포함 범위 (In-Scope)
* **학부모 연락처 2개 저장 정책:** 원생별 주 보호자(`parent1`) 및 부 보호자(`parent2`)의 이름, 연락처, 관계 및 개별 알림 수신 설정 설계.
* **수신자 모델 설계:** 앱 설치 상태, 푸시 동의 여부, 계정 ID(`linkedUserId`) 등을 결합한 확장 수신자 엔티티 설계.
* **기존 데이터 마이그레이션 설계:** 기존 `students` 테이블 내 단일 학부모 연락처 데이터를 신규 구조로 유실 없이 안전하게 이전하기 위한 시나리오 및 매핑 규칙.
* **메시지 보내기 수신자 선택 정책:** 발송 화면 내 보호자 1/2 개별 및 복수 노출 정책, 기본 선택 동작 정의.
* **중복 번호 처리 및 병합 정책:** 동일한 전화번호가 중복 등록되어 있거나 다중 선택되었을 때의 병합(Deduplication) 기준.
* **parentMessages와의 연동:** 메시지함 엔티티와 수신자 엔티티의 연결 및 메시지 발송 시점의 데이터 스냅샷(Snapshot) 저장 규칙.
* **앱 설치/푸시 가능 상태와의 연결 준비:** 후속 Phase 16D와의 정렬을 위한 상태 필드 및 UI 배지 노출 설계.

### 2) 제외 범위 (Out-of-Scope)
* **실제 코드 구현:** JavaScript 및 CSS 소스 코드의 실시간 변경이나 API 엔드포인트 작성은 제외.
* **실제 DB 마이그레이션 실행:** LocalStorage 및 Mock DB 내의 실제 데이터 변환 스크립트 실행은 제외.
* **UI 구현 및 마크업 반영:** 원생 상세 모달, 등록 폼, 메시지 발송 화면 등의 실제 마크업/스타일 변경은 제외.
* **메시지 발송 기능 구현:** 알림톡, SMS, 모바일 푸시 알림의 실제 API 연동 및 전송 로직 구현은 제외.

## 2. 현재 원생/학부모 연락처 구조 분석

기존 코드(`src/js/state.js`, `src/js/views/director/membersView.js`, `src/js/views/director/messageSendView.js`)를 바탕으로 분석한 현재의 연락처 데이터 구조와 한계점은 다음과 같습니다.

### 1) 기존 데이터 구조 및 필드
* **`students` 객체 내 연락처 관련 필드:**
  * `phone`: 수강생(원생) 본인의 연락처.
  * `parentName`: 학부모(보호자)의 성함.
  * `parentPhone`: 학부모(보호자)의 연락처.
  * *기타 방어 코드:* `messageSendView.js:L276`에서 하위 호환 및 방어적 설계를 위해 `parentPhone2`, `guardian2Phone`, `secondParentPhone` 필드 조회를 시도하고 있으나, 실제 `students` 데이터 모델 공식 스키마에는 정의되어 있지 않음.
* **`parentStudentLinks` 객체:**
  * `parentUserId`: 가입된 학부모 계정의 고유 ID.
  * `studentId`: 원생 고유 ID.
  * *한계:* 학부모 계정 1개와 원생 1개를 연결해 주는 역할만 담당하며, 비회원 보호자의 연락처나 상세 관계(부, 모 등) 및 수신 설정 등을 담기 어렵습니다.

### 2) 뷰(View) 레이어에서의 연락처 활용 현황
* **메시지 보내기 화면 (`messageSendView.js`):**
  * 수신 후보 추출 시 원생의 `phone`은 `studentPhone`(본인)으로, `parentPhone`은 `guardian1`(label: "모")로 설정하여 불러옵니다.
  * `g2Phone`으로 추정되는 필드들을 방어적으로 조회하여 존재할 경우 `guardian2`(label: "보호자2")로 노출합니다.
  * 원장이 `본인`, `보호자1(g1)`, `보호자2(g2)` 체크박스 버튼을 토글하여 선택한 수신 타입에 따라 번호 목록을 메시지 발송 대상(`viewState.recipients`)으로 적재합니다.
* **원생 상세 및 수정 화면 (`membersView.js`):**
  * 원생 등록/수정 모달에서 본인 연락처와 학부모 연락처를 각각 1개씩 입력받습니다.
  * `PhoneNumberInput` 모듈을 통해 포맷팅 검증을 수행하며, 번호가 없을 때를 대비해 `없음` 상태 선택 옵션을 제공합니다.

### 3) 기존 연락처 구조의 한계 및 이전 정책

| 항목 | 기존 필드명 | 현재의 한계점 | 신규 모델 이전/대체 정책 |
| :--- | :--- | :--- | :--- |
| **원생 본인 연락처** | `phone` | 초등학생 등 본인 휴대폰이 없는 경우 `없음`으로 방치되거나 보호자 번호와 중복 기입됨. | `phone` 필드 유지 (본인 휴대폰 소지 시에만 저장). |
| **학부모 성함** | `parentName` | 단 한 명의 보호자 이름만 저장이 가능하여 맞벌이 가정 등 다중 보호자(부/모) 개별 관리가 불가능함. | 신규 `parentContacts` 모델의 주 보호자(`parent1`) 이름 필드로 이전. |
| **학부모 연락처** | `parentPhone` | 단 하나의 번호만 제공되어 비상시 부/모 동시 연락이나 개별 메시지 수신 설정(청구서/출결 분리)이 원천 불가능함. | 신규 `parentContacts` 모델의 주 보호자(`parent1`) 연락처 필드로 이전. |
| **보호자 관계** | 없음 | 관계 정보가 테이블에 존재하지 않아, 발송 시스템 및 UI 상에서 임의로 `"모"` 또는 `"보호자"`로 가정하여 표기함. | 신규 `parentContacts` 내 `relation` 필드를 신설하여 명시적으로 지정 (`mother`, `father`, `guardian` 등). |

## 3. 신규 parentContacts 모델 제안

원생(Student)과 보호자 연락처(Parent Contact)의 관계를 시스템에 반영하기 위해 다음 두 가지 아키텍처 방안을 검토하였습니다.

### 안 A: students 내부에 parentContacts 배열로 포함
```json
// students 객체 내부
{
  "id": "S1",
  "name": "최다은",
  "parentContacts": [
    {
      "slot": "parent1",
      "name": "최수원",
      "relation": "mother",
      "phone": "010-8888-2222",
      "isPrimary": true,
      "canReceiveMessage": true,
      "linkedUserId": "USR_PAR_DEMO",
      "appInstalled": true
    },
    {
      "slot": "parent2",
      "name": "최진철",
      "relation": "father",
      "phone": "010-2222-3333",
      "isPrimary": false,
      "canReceiveMessage": true,
      "linkedUserId": null,
      "appInstalled": false
    }
  ]
}
```

### 안 B: 별도 parentContacts 컬렉션으로 분리 (추천안)
```json
// parentContacts 컬렉션 (독립 테이블)
[
  {
    "id": "PCON_001",
    "studentId": "S1",
    "slot": "parent1",
    "name": "최수원",
    "relation": "mother",
    "phone": "010-8888-2222",
    "normalizedPhone": "01088882222",
    "isPrimary": true,
    "canReceiveMessage": true,
    "canReceivePaymentMessage": true,
    "canReceiveAttendanceMessage": true,
    "canReceiveNoticeMessage": true,
    "linkedUserId": "USR_PAR_DEMO",
    "appInstalled": true,
    "pushEnabled": true,
    "pushTokenStatus": "active",
    "lastAppLoginAt": "2026-06-15T12:00:00Z",
    "createdAt": "2026-05-12T00:00:00Z",
    "updatedAt": "2026-06-15T12:00:00Z"
  },
  {
    "id": "PCON_002",
    "studentId": "S1",
    "slot": "parent2",
    ...
  }

```

### 두 방안의 비교 분석

| 비교 기준 | 안 A (students 내부 배열) | 안 B (별도 독립 컬렉션 - 추천) |
| :--- | :--- | :--- |
| **구현 난이도** | **낮음** (students 객체 CRUD 로직 수정 시 배열 데이터만 같이 밀어 넣으면 되므로 단순함) | **보통** (신규 스키마 정의 및 학생 상세 조회 시 Join 처리가 필요함) |
| **현재 DB 구조와의 적합성** | **보통** (localStorage 기반 JSON 저장 구조에서는 직관적이나 데이터가 무거워짐) | **우수** (정규화된 RDBMS 지향형 구조로, state.js 내의 타 모듈 구조와 정렬됨) |
| **향후 다자녀 / 다중 자녀 학부모 연결성** | **취약** (한 학부모가 다자녀인 경우 동일인의 이름, 전화번호, 앱로그인이 각 자녀 배열에 중복 저장되어 불일치 유발) | **매우 우수** (`linkedUserId` 또는 `normalizedPhone`을 매개로 다른 자녀 관계를 단일 보호자 정보와 결합 가능) |
| **parentMessages와의 연결성** | **보통** (`studentId + slot`을 조합해 식별해야 하므로 외래키 제약 및 조회 쿼리가 복잡함) | **우수** (`parentContactId` 단일 외래키 연결로 메시지 발송 이력과 수신자를 1:1로 깨끗하게 추적 가능) |
| **권한 및 로그인 계정 관리** | **복잡** (학부모 회원가입 시 여러 자녀 내부의 linkedUserId를 일일이 찾아 갱신해주어야 함) | **간결** (보호자 연락처 레코드 1개만 특정 `linkedUserId`에 연결해주면 연동 완료) |

### 💡 최종 추천안: 안 B (별도 parentContacts 컬렉션)
* **이유:** 단기적으로는 students 객체 내에 배열로 넣는 것이 간단해 보일 수 있으나, **다자녀 가정(1명의 학부모가 2명 이상의 원생을 학원에 보내는 경우)** 학부모 앱 설치 상태(`appInstalled`), 알림 설정, 가입 계정 ID(`linkedUserId`) 정보가 동기화되지 않고 파편화되는 결함이 생깁니다. 따라서 데이터 무결성을 보장하고 추후 다자녀 확장을 매끄럽게 처리하기 위해 **독립 컬렉션(테이블)으로 분리하는 안 B를 최종 추천**합니다.

## 5. 기존 데이터 마이그레이션 설계

기존 `students` 테이블에 존재하는 단일 연락처 정보를 안정적으로 이전하기 위한 마이그레이션 원칙 및 방법론입니다.

### 1) 마이그레이션 기본 원칙
* **기존 데이터 보존:** 마이그레이션 중 오동작으로 인한 연락처 데이터 유실을 절대 금지합니다.
* **하위 호환성 및 과도기 대응 정책:** 기존 코드 및 E2E 테스트 시나리오에서 `student.parentPhone`이나 `student.parentName`을 직접 참조하는 부분을 지원하기 위해, 기존 필드들은 하위 호환을 위한 **읽기 전용 Fallback**으로 유지합니다. 신규 데이터의 등록/수정/삭제 시 모든 원장 정보(Source of Truth)는 새롭게 개편된 `parentContacts` 독립 모델로 전환하여 관리합니다. 과도기 상태의 데이터 참조 흐름은 다음과 같습니다:
  * **원장 데이터(Source of Truth):** 신규 생성/수정의 원장부는 `parentContacts` 독립 테이블로 전환합니다.
  * **읽기 Fallback:** 필요한 화면이나 조회 로직에서는 `parentContacts`를 우선적으로 조회하며, 해당 컬렉션에 정보가 없는 과도기/구형 데이터의 경우 기존 `students` 객체의 `parentPhone` / `parentName` 필드를 Fallback으로 읽어 들여 렌더링 호환성을 유지합니다.
  * **양방향 동기화 배제:** 신규 시스템은 `parentContacts`만을 주 데이터 저장소로 바라보며, 데이터 정합성 혼선을 줄이기 위해 기존 필드로의 양방향 쓰기 동기화는 진행하지 않습니다.
* **E2E 테스트 안정성:** 테스트 환경의 시드 데이터 로딩 흐름에 영향이 가지 않도록 기본값 할당 로직을 세심하게 처리합니다.

### 2) 데이터 매핑 및 이전 시나리오

```
[기존 students 레코드]
  - parentName: "최수원"
  - parentPhone: "010-8888-2222"
       │
       ▼ 마이그레이션 스크립트 실행
[신규 parentContacts 레코드 생성]
  - id: "PCON_S1_1"
  - studentId: "S1"
  - slot: "parent1"
  - name: "최수원"
  - relation: "guardian" (이름/관계 정보가 불확실할 때 기본값 처리)
  - phone: "010-8888-2222"
  - normalizedPhone: "01088882222"
  - isPrimary: true
  - canReceiveMessage: true
```

* **보호자2 (`parent2`) 처리:**
  * 기존 데이터에 세컨드 보호자 정보가 없으므로 마이그레이션 시 `parent2`용 레코드는 생성하지 않거나 빈 슬롯 상태로 둡니다. (불필요한 빈 행 적재 방지)
* **이름/관계 정보 누락 시 기본값 처리 정책:**
  * **이름(`parentName`)이 비어있는 경우:** `"보호자"`를 기본값으로 입력합니다.
  * **관계(`relation`) 정보가 없는 경우:** 기본값으로 `"guardian"` (일반 보호자)을 적용합니다.
* **잘못된 전화번호 처리 정책:**
  * `parentPhone` 필드값이 숫자가 아니거나 유효하지 않은 경우(예: `"없음"`, `"010-0000-0000"`, 공백 등), 마이그레이션 대상에서 제외하지 않고 원본 그대로 `phone`에 이전하되 `normalizedPhone`을 `null`로 세팅하고 `canReceiveMessage = false`로 지정하여 오발송을 원천 차단합니다.

## 6. 메시지 보내기 수신자 선택 정책

수신자가 다중화됨에 따라 메시지 작성 화면(`messageSendView.js`)에서 발송 대상을 지정하는 정책을 고도화합니다.

### 1) 수신자 후보 노출 및 멀티 선택 정책
* **개별 후보 노출:** 원생 1명을 발송 대상에 올리면 해당 원생 하위에 속한 `parent1`과 `parent2`가 각각 독립된 수신 후보(체크박스 제공)로 노출됩니다.
* **기본 선택 값:** 원생 선택 시 기본적으로 `isPrimary: true`인 대표 보호자(`parent1`)만 자동으로 체크 상태가 되며, 필요시 원장이 `parent2`도 명시적으로 다중 체크하여 복수 번호로 동시에 보낼 수 있습니다.
* **연락처 없는 보호자 비활성화:** 전화번호 정보가 존재하지 않는 보호자는 리스트에서 선택 불가능(`disabled`) 처리하고 옆에 `"연락처 없음"` 상태 메시지를 노출합니다.

### 2) 수신자 노출 표기 양식
학원 운영 과정에서 식별이 용이하도록 수신자 이름 옆에 관계와 전화번호를 조합해 명확하게 표기합니다.
* 예: `최다은 / 어머니 / 010-8888-2222`
* 예: `최다은 / 아버지 / 010-2222-3333`

### 3) 여러 원생 대상 발송 시 중복 번호 제거 (Deduplication) 정책
여러 자녀를 가진 학부모에게 메시지를 보낼 때 발생하는 스팸 피로도를 줄이기 위한 중복 제거 기준입니다.
* **등하원 및 결제 알림 (자녀 맞춤형 메시지):**
  * 두 자녀의 메시지 본문(`#{원생명}`)과 결제 내역이 서로 다르기 때문에, 비록 부모 전화번호가 동일하더라도 **중복 제거를 하지 않고 두 자녀 각각에 대해 개별 메시지(2통)를 발송**합니다.
* **학원 공지사항 및 이벤트 안내 (공통 전체 메시지):**
  * 동일한 본문을 수신하는 경우이므로, 수신 전화번호(`normalizedPhone`) 기준 **중복을 제거하여 단 1통의 메시지만 발송**되도록 제어합니다. (비용 절감 및 스팸 피로 방지)

## 7. 메시지 채널 선택과의 관계

후속 Phase 16E(복수 메시지 채널 도입)를 대비하여 채널 발송 가능 상태를 판별하는 기준을 정립합니다.

* **문자(SMS/LMS/MMS) 가능 여부:** 
  * 보호자 연락처의 유효성(`normalizedPhone` 존재 여부) 및 `canReceiveMessage` 동의 상태에 따라 활성화됩니다.
* **카카오 알림톡 가능 여부:**
  * 수신자의 전화번호를 기반으로 판단하되, 향후 카카오 알림톡 API 연동 모듈을 통해 해당 번호의 카카오톡 가입 여부 검증 후 발송 실패 시 문자로 전환하도록 연동합니다.
* **모바일 기기 푸시(Push) 가능 여부:**
  * `linkedUserId !== null` 이고 `appInstalled === true` 이며 `pushEnabled === true` 인 경우에만 모바일 푸시 발송 대상 기기로 인정합니다.
* **메시지함(인앱) 생성 기준 추천:**
  * **추천 정책:** 메시지함(`parentMessages`)은 학부모의 가입 계정 ID(`linkedUserId`)가 아닌 **`parentContactId`를 기준으로 생성하고 적재**할 것을 권장합니다.
  * **이유:** 학부모가 아직 앱을 설치하지 않았거나 계정을 만들지 않은 비가입 보호자 상태이더라도, 학원에서 보낸 중요 결제 정보나 출결 안내 히스토리가 인앱 데이터베이스(`parentMessages`)에 유실 없이 누적되어야 합니다. 추후 학부모가 가입하여 본인의 휴대폰 번호 인증을 완료하는 시점에 해당 전화번호를 소유한 `parentContactId`와 `linkedUserId`를 맵핑하면, **가입 이전의 과거 알림 기록까지 온전하게 소거되지 않고 한눈에 조회**할 수 있는 긍정적인 UX를 제공할 수 있습니다.

## 8. parentMessages와의 연결 설계

Phase 16B에서 정의된 학부모 메시지함(`parentMessages`) 테이블과 신규 수신자 모델(`parentContacts`) 간의 유기적 관계성 설계입니다.

### 1) 외래키 및 스냅샷 필드 구조
`parentMessages` 레코드 생성 시, 수신자 엔티티의 ID를 연결함과 동시에 메시지 발송 시점의 수신인 상세 정보를 **스냅샷(Snapshot)** 형태로 복제하여 저장하는 구조를 제안합니다.

* `parentContactId`: 발송 대상 수신자 고유 ID (`parentContacts.id` 참조)
* `parentSlot`: 수신 위치 구분 (`parent1` / `parent2` 복제)
* `recipientName`: 수신인 성함 스냅샷
* `recipientRelation`: 수신인 관계 스냅샷
* `recipientPhone`: 수신인 연락처 스냅샷
* `recipientUserId`: 가입된 학부모 계정 ID 스냅샷

### 2) 데이터 스냅샷 저장의 필요성 및 추천 사유
> [!IMPORTANT]
> **데이터 스냅샷 저장은 메시징 이력 관리의 필수 요건입니다.**
> 학부모 연락처나 관계 정보는 수시로 변경될 수 있습니다. 예를 들어, 어머니의 전화번호가 도중에 바뀌거나 보호자 자체가 다른 친척으로 변경될 수 있습니다. 
> 만약 스냅샷을 저장하지 않고 `parentContactId` 조인에만 의존하여 화면을 렌더링하면, 과거에 발송했던 청구서나 출결 정보 속의 학부모 성함 및 발송 번호 정보가 현재 시점의 새로운 보호자 정보로 오염되는 치명적인 데이터 무결성 결함이 발생합니다. 따라서 과거 발송 사실의 완벽한 감사를 위해 **발송 시점의 수신 정보를 스냅샷 필드에 기록 보존**해야 합니다.

## 9. 앱 설치/푸시 가능 상태와의 연결 준비

후속 개발을 위해 학부모 기기 상태를 나타내는 지표들을 화면 곳곳에 배치할 수 있도록 기획합니다.

### 1) 상태 판별 로직 기준
* **앱 설치 완료:** `appInstalled === true`
* **푸시 수신 대기:** `appInstalled === true && pushEnabled === true && pushTokenStatus === 'active'`
* **푸시 수신 불가:** `appInstalled === false` 또는 `pushEnabled === false` 또는 `pushTokenStatus`가 `revoked`/`expired`인 상태.

### 2) 시각적 정보 노출 위치 및 디자인 아이디어

```
[원생 상세 화면 - 보호자 정보 영역 Mock]
┌─────────────────────────────────────────────────────────────────┐
│  보호자 1: 최수원 (어머니)  [010-8888-2222]   [앱설치] [푸시가능]  │
│  보호자 2: 최진철 (아버지)  [010-2222-3333]   [미설치] [SMS전송]   │
└─────────────────────────────────────────────────────────────────┘
```

* **원생 상세 페이지:** 보호자 성함 및 번호 우측에 실시간 앱 연결 상태 배지(`앱설치 완료` / `미설치`, `푸시 수신가능` / `푸시 차단됨`)를 칩 형태로 노출합니다.
* **학부모 소통 관리 화면:** 보호자 그리드 테이블에 앱 로그인 이력(`lastAppLoginAt`) 및 최종 푸시 성공 여부를 아이콘으로 통합 노출합니다.
* **메시지 보내기 수신자 목록:** 원장이 발송 대상자를 선택할 때 각 보호자의 이름 우측에 `[PUSH]` 또는 `[SMS]` 아이콘을 노출하여, 이 보호자가 푸시로 즉시 새 알림을 인지할 수 있는 대상인지 아니면 알림톡/문자 비용을 소모해야 하는 대상인지 발송 전에 직관적으로 인지하도록 돕습니다.

## 10. UI 변경 범위 제안

실제 코드 작성 없이 설계 단계에서 예측한 컴포넌트별 화면 영향 범위 및 UI 요구사항 명세입니다.

### 1) 원생 등록 및 수정 모달 (`membersView.js`)
* **보호자 입력 폼의 2중화 확장:**
  * 기존 단일 "학부모 성함", "학부모 연락처" 입력 영역을 **"보호자 1 (대표)"**과 **"보호자 2"**의 두 개 영역으로 나누어 배치합니다.
  * 각 영역에는 이름(Text), 관계(Select: 부/모/조부모/기타), 연락처(Tel), 그리고 알림별 수신 체크박스(`canReceivePaymentMessage`, `canReceiveAttendanceMessage` 등) 목록을 집어넣습니다.
* **대표 설정 토글:** 라디오 버튼 형식으로 두 보호자 중 누가 주 연락처(`isPrimary`)인지 상호 배타적으로 선택할 수 있게 합니다.

### 2) 원생 상세 모달 (`membersView.js`)
* **보호자 정보 영역 분할:** 
  * 상세 정보 탭 내에서 보호자 1과 보호자 2의 연락처 정보를 명확히 구분하여 보여줍니다.
  * 각 보호자 옆에 앱 설치 및 푸시 상태 배지를 제공하여 원장이 학부모의 수신 준비도를 체크할 수 있도록 합니다.

### 3) 메시지 보내기 화면 (`messageSendView.js`)
* **수신자 리스트 선택 필터 개편:**
  * 좌측 원생 리스트에서 원생을 체크했을 때, 우측 "발송 대상 추가" 팝업이나 테이블 내부에 본인, 보호자1, 보호자2를 선택하는 토글 버블을 고도화합니다.
  * 중복 번호가 있는 경우 회색 배지로 `[중복 번호]` 표시를 띄워 원장이 미리 확인할 수 있게 지원합니다.

### 4) 학부모 소통 관리 화면 (`communicationView.js`)
* 학부모 연결 상태를 일괄 확인할 수 있는 요약 카드 및 테이블 뷰를 추가하여, 전체 원생 대비 앱 설치 비율 및 푸시 수신율 지표를 대시보드 형태로 제공합니다.

## 11. 유효성 검증 정책

데이터 정합성을 유지하기 위해 입력 및 저장 단계에서 수행해야 할 유효성 검증 규칙입니다.

* **한국 휴대폰 번호 검증:**
  * 국가 번호를 제외한 표준 규격(`010-XXXX-XXXX` 또는 `01X-XXX-XXXX`) 정규식 필터링을 거칩니다.
  * 사용자가 하이픈 없이 숫자로만 입력하더라도 뷰 단에서 자동으로 하이픈을 붙여주는 포매터 바인더를 유지합니다.
* **번호 정규화 (`normalizedPhone`):**
  * 데이터 저장 시 하이픈 및 공백을 제거한 순수 숫자 문자열(예: `01088882222`)을 자동 계산하여 데이터베이스에 함께 영속화합니다.
* **보호자간 중복 차단 검증:**
  * 동일 원생 내부에서 `parent1`과 `parent2`가 동일한 전화번호를 등록하려고 하면, 저장을 차단하고 `"동일한 전화번호는 보호자 1과 2에 중복하여 등록할 수 없습니다."`라는 오류 피드백을 노출합니다.
* **연락처 필수 입력 검증:**
  * 학원 행정 및 비상 대피, 청구서 발송을 위해 원생 등록 시 **최소 1개 이상의 유효한 학부모 연락처(`parent1`)는 반드시 기입하도록 강제**합니다. (둘 다 `없음`으로 저장하는 것은 원천 금지하며, 대표 보호자는 반드시 필수로 존재해야 합니다.)

## 14. 최종 권고안 및 요약 결론

1. **DB 모델 설계:** 다자녀 가정 및 회원 계정 결합의 유연성을 완벽히 확보하기 위해, 학생 객체 내부 배열 형식이 아닌 **독립 컬렉션인 `parentContacts` 모델로 구현할 것을 강력히 권장**합니다.
2. **기본 수신 관계:** 보호자는 원생당 최대 2명(`parent1`, `parent2`)까지 관리하며, `parent1`을 대표 보호자로 명시적으로 강제 설정합니다.
3. **기존 데이터 마이그레이션:** 기존 `parentName`과 `parentPhone` 정보는 `parent1`의 대표 보호자로 자동 이전되며 관계는 `guardian`으로 초기 지정합니다. 기존 필드는 하위 호환을 위한 읽기 Fallback으로만 활용하며 양방향 쓰기 동기화는 배제하고 점진적으로 Deprecated 처리합니다.
4. **수신자 선택 및 중복 제거:** 메시지 보내기 화면에서는 두 보호자 모두를 체크박스 후보로 개별 노출하되, 동일 번호 및 동일 학원 전체 공지 발송 시에는 수신 번호 기준으로 중복을 병합하여 스팸성 중복 발송을 방지합니다.
5. **메시지 이력 보존:** 연락처의 미래 변경에 대비하여, `parentMessages`를 생성 및 전송할 때는 발송 당시의 이름, 번호, 관계 데이터 **스냅샷 형태로 반드시 중복 보관**하여 데이터의 감사 무결성을 확보합니다.
