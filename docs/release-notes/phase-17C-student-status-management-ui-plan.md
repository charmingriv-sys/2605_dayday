## 2. 상태 표시 정책 후보 (Status Display Policy)

원장의 피로도를 줄이고 시각적 노이즈를 최소화하기 위해 아래와 같은 상태 표시 정책 후보를 비교 검토합니다.

| 원생 상태 | 목록 화면 표시 후보 | 상세 화면 표시 후보 | 검색 결과 표시 후보 | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| **재원 (`attending`)** | 배지 미표시 (텍스트만 렌더링) | 타이틀 옆 배지 미표시 혹은 `[재원]` 표시 | 일반 렌더링 | 기본 상태이므로 색상 노이즈를 줄이기 위해 배지를 표시하지 않는 방안 검토. |
| **휴원 (`on_leave`)** | 지정 색상 배지 (`[휴원]`) 표시 후보 | 타이틀 옆 `[휴원]` 배지 표시 후보 | 이름 옆 `[휴원]` 표시 후보 | 기존 디자인 토큰 테마를 연동하여 시각적 인지성 부여 검토. |
| **퇴원 (`withdrawn`)** | 지정 색상 배지 (`[퇴원]`) 표시 후보 | 타이틀 옆 `[퇴원]` 배지 표시 후보 | 이름 옆 `[퇴원]` 표시 후보 | 비활성화 상태를 나타내도록 기존 스타일 가이드 연동 검토. |

* **17C 디자인 목표**: Phase 17C 최소 구현에서는 상태 배지 표시 자체를 목표로 삼고, 배지의 색상 및 스타일 세부 요소는 시스템의 기존 디자인 토큰에 연동하여 후속 조정 가능하도록 구성합니다.

## 3. 상태 변경 UI 후보 비교 및 추천안

### A. UI 구조 후보군
1. **후보 1: 원생 수정 모달 내의 status select 드롭다운 (Phase 17C 최소 구현안)**
   - **장점**: 기존 정보 수정 흐름에 자연스럽게 녹아들며 변경 범위가 적음.
   - **단점**: 사용자가 스크롤 중 오클릭할 수 있으므로 간단한 confirm 팝업 등의 최소 안전 장치 추가 필요.
2. **후보 2: 상세 모달 내 독립적인 "상태 변경" 퀵 버튼 제공 (후속 후보)**
   - **장점**: 수정 모달을 거치지 않고 상태만 단독으로 빠르게 스위칭 가능.
   - **단점**: 오클릭으로 인한 변경 실수를 예방하기 위한 추가 로직 필요.
3. **후보 3: 위험 상태 변경 전용 모달 다이얼로그 (후속 후보)**
   - **장점**: 휴원/퇴원 사유 및 날짜 지정을 별도로 확실하게 받아 저장 가능.
   - **단점**: 화면 뎁스가 깊어져 조작이 번거로울 수 있음.

### B. Phase 17C 최종 추천안
* **정보 수정 모달 내 학원 행정 섹션**에 `상태(status)` 셀렉트박스를 탑재하여 관리자가 상태를 지정하고 변경할 수 있도록 제한합니다.
* 사용자가 상태값을 변경하고 저장하려 할 때, 간단한 브라우저 `confirm` 메시지를 띄워 오작동을 예방하는 최소한의 보완 장치를 적용합니다. (전용 안내 모달 및 2차 인증 구조는 후속 후보로 이관)
* 목록 화면에서의 1클릭 빠른 상태 변경은 오작동 예방을 위해 목록상에서는 표시되지 않는 방향을 지향합니다.

## 4. 휴원 변경 UX 후보 (Leave Management UX Candidates)

* **휴원 입력 메타데이터 (후속 Phase 반영 후보)**:
  - 휴원 시작일, 휴원 종료 예정일, 휴원 사유, 세부 메모 등
  - **주의**: Phase 17C 최소 구현에서는 위의 상세 메타데이터 입력 폼 및 저장을 수행하지 않으며, status 필드의 상태값 변경만 지원합니다. 날짜/사유 등의 상세 저장 기능은 17D 이후 후보로 설계합니다.
* **저장 전 최종 확인(Confirm) 문구 후보**:
  - "원생을 [휴원] 상태로 변경하시겠습니까? 휴원 처리하더라도 기존의 미납 요금 및 출결 기록은 사라지지 않고 보존됩니다."
* **휴원 해제 및 재원 복귀 후보**:
  - 관리자가 상태 셀렉트박스를 다시 `'attending'`(재원)으로 변경하여 저장하면 간편하게 재원 상태로 복원하는 형태를 검토합니다.

## 5. 퇴원 변경 UX 후보 (Withdrawal Management UX Candidates)

* **퇴원 입력 메타데이터 (후속 Phase 반영 후보)**:
  - 퇴원일, 퇴원 사유 등 (17C 최소 구현 범위에서는 구현하지 않으며 17D 이후 후보로 분리)
* **사전 체크 및 위험 경고 노출 후보 (후속 Phase 반영 후보)**:
  - 퇴원 처리 전, 해당 원생의 미납 수강료가 남아있거나, 미완료 교재 배정 건이 있는 경우 경고 메시지를 노출하는 방안.
* **이력 보존 및 삭제와의 명확한 분리 원칙**:
  - **퇴원은 데이터의 '삭제'가 아니며 단순 status 전환입니다.** 
  - 원생 정보는 시스템에서 물리적으로 지워지지 않으며, 과거의 출결, 수납, 메시지 발송 등의 전체 이력은 그대로 보존되어 조회할 수 있어야 함을 기본 원칙으로 삼습니다.
* **퇴원 후 재등록 (재원 복귀 후보)**:
  - 퇴원한 원생은 상단 필터에서 `'퇴원생 전체'`를 선택해 조회할 수 있으며, 수정 폼에 들어가 상태를 다시 `'attending'`으로 변경하면 재등록되어 정상 재원생으로 전환되는 복원 방안을 후보로 둡니다.

## 6. 실수 방지 및 정합성 정책 후보

1. **상태 변경과 데이터 삭제의 분리**:
   - 물리/논리 삭제 버튼(DB의 `isDeleted` 플래그 설정)은 기존대로 '정보 수정' 모달 하단에 작게 유지하거나 별도의 비밀번호 인증을 거치도록 격리하고, 일반적인 상태 변경 셀렉트박스와 시각적/기능적으로 철저히 분리합니다.
2. **다단계 확인 및 안내 팝업 (후속 Phase 반영 후보)**:
   - 퇴원 상태로 변경 시, 단순 브라우저 `confirm` 창 외에 전용 안내 모달을 노출하여 경고하는 2단계 확인 UX는 17D 이후 구현 후보로 이관합니다.
3. **상태 변경 직후 Undo 제공 여부 (후속 Phase 반영 후보)**:
   - 상태 변경이 완료된 직후 실행 취소(Undo) 토스트를 띄우는 방안은 상태 변경 이력(`statusHistory`) 및 이력 복원 설계와 결합되어야 하므로 구현 복잡성을 낮추기 위해 17C 구현 범위에서 제외하고 후속 후보로 분리합니다.
4. **변경 이력(`statusHistory`) 관리 보류**:
   - 변경된 일시, 상태, 사유를 데이터베이스에 적재하는 이력 배열(`statusHistory`)은 설계 후보로만 남겨두고, 본 Phase 17C 구현 단계에서는 별도로 생성/저장하지 않습니다.

## 7. Phase 17C 구현 범위 추천 (최소 구현안)

* **17C 반영 범위 (Minimal Scope)**:
  - 원생 목록 표(`renderTableBody`)의 원생 이름 옆에 상태 배지(`[휴원]`, `[퇴원]`) 표시.
  - 원생 상세 정보 모달(`openStudentDetailModal`) 상단 헤더에 원생 상태 배지 표시.
  - 원생 등록/수정 모달(`openStudentModal`) 폼 내에 `상태` 필드(기본값: 재원)를 select 박스로 추가하여 상태 저장 및 수정 기능 제공.
  - 상태 변경 시 저장 전 간단한 브라우저 `confirm` 팝업을 통한 경고 노출.
* **후속 Phase 반영 범위 (Postposed Scope)**:
  - 상세 날짜(leaveDate 등), 상세 사유, 상담 메모 등 개별 입력 폼 구현 및 저장 로직.
  - 2단계 전용 확인 모달 UI 적용.
  - 실행 취소(Undo) 기능 구현.

## 8. 도메인 로직 제외 범위 명시 (Exclusion Check)

시스템의 복잡성 전이와 부작용을 방지하기 위해 다음 기능은 Phase 17C 개발 범위에서 명시적으로 **제외**합니다.

1. **출결 도메인**: 휴원/퇴원 원생의 등하원 키오스크 및 출석부 체크 대상 제외 처리 미적용.
2. **회계 도메인**: 휴원/퇴원 원생의 자동 수강료 청구 대상 제외 및 일할 계산 로직 미적용.
3. **메시징 도메인**: 메시지 발송 시 수신자 목록에서 휴원/퇴원생 자동 필터링 및 제외 처리 미적용.
4. **콘솔/태스크 도메인**: `todayTask`에서 비활성 원생 경고 알림 생성 제외 처리 미적용.
5. **학부모 포털**: 퇴원/휴원 자녀 정보 노출 및 이력 조회 차단 미적용.
6. **대시보드**: 대시보드 통계 카드 내 재원생 수 집계 로직 변경 미적용.

## 9. 테스트 / QA 계획

1. **기본 원생 상태 검증**:
   - 신규 추가 폼에서 원생 생성 시 자동으로 `'attending'` 상태가 부여되고 UI 상에 별도의 배지가 표시되지 않는지 확인.
2. **상태 변경 UI 동작**:
   - 원생 수정 폼에서 상태를 `'on_leave'` 또는 `'withdrawn'`으로 바꾼 뒤 저장했을 때, 목록 및 상세 모달에서 각각 `[휴원]`, `[퇴원]` 배지가 올바르게 렌더링되는지 검증.
3. **상태값 영속성 검증**:
   - 상태 변경 후 브라우저 새로고침을 실행해도 `localStorage`를 통해 저장된 상태가 안전하게 로드되어 유지되는지 확인.
4. **과거 데이터 보존 검증**:
   - 원생의 상태를 `'withdrawn'`(퇴원)으로 변경하더라도, 기존에 쌓여 있던 출결 로그 및 청구/수납 이력이 소실되지 않고 그대로 유지되는지 데이터 단위 검증.
5. **잘못된 상태 저장 차단**:
   - 수동 조작 등으로 허용되지 않은 상태값을 저장하려고 할 때 `'attending'`으로 자동 fallback 처리되는 안전 장치 작동 검사.

## 10. 후속 로드맵 제안 (Candidate Roadmap)

* **Phase 17C**: 원장 원생 관리 상태 표시 및 상태 변경 UX 최소 구현
* **Phase 17D**: 출결 키오스크 및 일일 출석부 화면 연동 (휴원/퇴원생 기본 필터링 후보 적용)
* **Phase 17E**: 수납/회계 도메인 연동 (자동 청구 보류 및 정기 수강료 정지 후보 적용)
* **Phase 17F**: 메시지 발송 화면 연동 (기본 수신인 제외 및 Focus Confirm 배지 알림 후보 적용)
* **Phase 17G**: 오늘 콘솔 및 대시보드 통계 카드 연동
