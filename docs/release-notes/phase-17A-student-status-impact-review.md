# Phase 17A-Review: 원생 상태 도입 전 영향 범위 코드 조사 보고서

본 문서는 Phase 17B에서 원생 상태(`student.status`: `attending` / `on_leave` / `withdrawn`) 속성을 데이터베이스 및 비즈니스 로직에 추가하기 전, 현재 코드에서 원생 정보(`students` 데이터 배열 및 관련 헬퍼)를 활용하는 모든 주요 영역의 의존성을 조사하고 영향도를 평가한 기술 분석 리뷰서입니다.

## 2. 우선 구현 순서 제안 (Implementation Roadmap)

### 1단계: Phase 17B (최소 데이터 모델 구현 - 안전성 위주)
* **목표**: 기존 시스템 동작을 100% 보존하면서 상태 필드 스키마 및 마이그레이션 안전 장치 구축.
* **제한 범위**: 
  * `students` 레코드에 `status` 필드 및 상태 정보 기본값(`'attending'`) 탑재.
  * `getStudents()` 및 `getStudentsForParent()`에 데이터 마이그레이션용 Fallback 로직 추가 (기존 DB 데이터 로드 시 `status` 필드가 없으면 `'attending'`으로 가상 매핑하여 전달).
  * **미구현 항목**: Phase 17B에서는 **화면 필터링, 청구 제외, 메시지 제외, 출결 제외를 구현하지 않음**.
  * **이유**: 원생 상태 필드의 추가 영향 범위가 매우 넓으므로, `status` 필드 도입(데이터 모델 레이어)과 구체적인 도메인 비즈니스 동작 변경(로직 레이어)을 분리하여 안정성을 확보하기 위함.
  * 기존 E2E 테스트 및 모의 DB에 악영향을 주지 않도록 마이그레이션 호환 검증에 주력.

### 2단계: Phase 17C & 17D (UI 기능 및 출결 도메인 보정 후보)
* **목표**: 원장 화면에서 상태를 변경할 수 있게 하고, 출결 및 콘솔 큐에 예외 적용하는 방안 검토.
* **범위**:
  * `membersView.js` 원생 상세 폼에 상태 토글(재원/휴원/퇴원) 연동 검토.
  * 출결 키오스크 및 출석부 렌더링 시 휴원생 신규 출결 체크 대상 보류 후보 및 퇴원생 기본 필터 후보 검토.

### 3단계: Phase 17E & 17F (수납/메시징 도메인 예외 처리 후보)
* **목표**: 회계 청구서 및 단체 문자 발송 시 불필요한 비용이 발생하지 않도록 필터링 연동 후보 검토.
* **범위**:
  * 퇴원생 대상 신규 청구 보류 후보 및 휴원생 정기 청구 보류 후보 규칙 검토.
  * 문자 발송 수신 대상 검색 시 기본 재원생 필터 후보 및 수동 지정 시 상태 알림 배지 노출 검토.

## 3. 필터 및 화면 노출 정책 후보 (Proposed Filtering Policies)

1. **원생 관리 메인 리스트 필터링 후보**:
   * **후보 정책**: 기본 조회 시 **재원생(`status === 'attending'`)**만 기본 리스트에 노출하는 필터 설정 검토.
   * **UI 구성 후보**: `[재원생]`, `[휴원생]`, `[퇴원생]` 탭 분리 또는 필터 드롭다운을 통해 원장이 의도한 경우에만 조회할 수 있는 구조 제안 (후속 Phase 반영 후보).
2. **메시지 보내기 수신자 목록 필터링 후보**:
   * **후보 정책**: 기본적으로 재원생 위주로 표시하며, 특강 모집이나 안부 문자 목적 등을 위해 "휴원생/퇴원생 포함" 토글 스위치를 원장이 활성화한 경우에만 검색 결과에 포함하는 방안 검토.
3. **학부모 포털 자녀 선택 후보 비교**:
   * 학부모가 과거 수납/출결 이력을 확인해야 할 수 있으므로, 퇴원한 자녀를 완전히 숨기는 것은 정합성 확인 차원에서 위험할 수 있습니다. 이에 따라 아래 세 가지 정책 후보를 비교 검토합니다.
     * **후보 A (완전 숨김)**: 퇴원 자녀를 드롭다운에서 완전히 숨김. (과거 이력 조회 불가로 인해 CS 유발 위험 높음)
     * **후보 B (이력 조회 전용)**: 드롭다운에는 유지하되, 신규 신청/예약 등은 불가능하고 과거 출결 및 납부 기록만 읽기 전용으로 노출. (비교적 안전한 후보)
     * **후보 C (상태 배지 표시)**: 드롭다운 이름 옆에 `[퇴원]` 배지를 붙여 상태만 인지시키고 기존 뷰를 동일하게 유지하는 방안.

## 4. 데이터 마이그레이션 및 테스트 영향도 (Migration & Test Impact)

### A. 마이그레이션 위험 요인
* **기존 데이터 정합성**: 현재 `localStorage`에 저장된 사용자의 로컬 DB 인스턴스에는 `status` 필드가 없습니다.
* **해결 방안**: 데이터 로더(`members.js`의 `getStudents`) 단에서 데이터 반환 시 `status` 필드가 정의되지 않았을 경우 `'attending'` 객체로 매핑해 반환하여 기존 기능과의 하위 호환성을 유지합니다.
* **상태 변경 이력(`statusHistory`)**: 최소 구현 단계인 17B에서는 `statusHistory` 이력 적재 로직을 필수 구현 범위로 지정하기보다, 우선 비어 있는 배열(`[]`)로 기본 초기화해 둔 뒤 후속 Phase에서 연동하는 정책을 검토합니다.

### B. 테스트 영향 분석
* **S1(최다은) 의존성**:
  * `attendance-control-flow.spec.js`, `attendance-parent-flow.spec.js` 등의 거의 모든 E2E 테스트가 기본 시드 원생인 `S1`(최다은)의 데이터(출결 기록, 미납 기록)에 크게 의존하고 있습니다.
  * 만약 마이그레이션 과정에서 `status` 속성이 제대로 주입되지 않거나 비활성 상태로 잡힐 경우, `S1` 관련 출결 검증, 미납 검증, 배지 합산 E2E 시나리오가 연달아 깨지는 연쇄 결함이 발생할 우려가 있습니다.
  * 따라서 17B의 최소 구현 작업 및 마이그레이션 헬퍼 테스트 시, 기존 시드 데이터에 들어 있는 모든 원생이 정상적으로 `'attending'` 상태로 인식되는지를 최우선으로 검증해야 합니다.

## 5. 미구현 범위 (Out of Scope for Phase 17B)

* **코드 구현 없음**: 본 Phase는 설계 검토 문서 작성으로 한정하며, 실제 소스 코드(`.js`) 수정은 진행하지 않습니다.
* **테스트 코드 수정 금지 및 검증 명령 실행 없음**: 기존 테스트 파일을 변경하지 않습니다.
* **데이터 모델 변경의 실제 반영 금지**: `localStorage` 데이터 스키마의 실제 업데이트는 Phase 17B에서 다루며, 17A에서는 설계로만 논의합니다.
* **Mock HTML 및 `DAYDAY_PENDING_ROADMAP.md` 등의 파일 수정 미포함**: `docs/superpowers/` 및 docs mockup HTML 파일은 수정하지 않고 유지합니다.
