# Phase 16R 설계 정의서: 실제 SMS/알림톡 채널 연동 설계

본 문서는 현재까지 구현된 원장 메시지 보내기 화면, 발송 전 확인 모달, 템플릿 초안, 오늘 콘솔 handoff 연동 흐름을 바탕으로 실제 유료 통신 채널(문자/알림톡)과의 연동을 진행하기 전 필요한 설계 정책, 스키마, 그리고 발생 가능한 예외 처리를 규정하는 설계 정의서입니다.

> [!IMPORTANT]
> 본 Phase 16R 단계는 **문서 설계 전용 Phase**입니다. 실제 소스 코드 수정, API Key/외부 연동 설정 추가, 실물 API 호출 로직 구현 등은 **이번 범위에 포함되지 않으며** 향후 연동 개발 단계로 위임합니다.

---

## 1. Phase 16R 범위 정의

### 1) 포함 범위 (In-Scope)
* **SMS/LMS 채널 연동 설계:** 단문/장문 메시지 분기 기준 및 유료 게이트웨이 연동 아키텍처.
* **카카오 알림톡 채널 연동 설계:** 카카오 비즈니스 알림톡 연동을 위한 규격 및 가이드라인.
* **채널 선택 UI 정책:** 발송 방식 설정 UI 설계 및 발송 방식 조합 후보 검토.
* **알림톡 템플릿 승인 정책:** 원장 작성 보조 초안과 카카오 실제 승인 템플릿의 관계 정립 및 예외 제어.
* **실패 시 Fallback 정책 후보:** 전송 실패 시 타 채널 전환 정책 후보군 제시.
* **과금/중복 발송 방지 정책:** 이중 전송, 중복 요청 및 오발송으로 인한 과금을 원천 차단하기 위한 통제 기준.
* **로그/개인정보 정책:** 발송 이력 저장 시 민감 정보(전화번호 등) 마스킹 및 암호화 아키텍처.
* **구현 단계 제안:** 향후 개발 단계 로드맵 제시.

### 2) 제외 범위 (Out-of-Scope)
* **실제 SMS/LMS API 호출 구현:** 외부 문자 게이트웨이 연동 코드 배제.
* **실제 카카오 알림톡 API 호출 구현:** 알림톡 발송 모듈 코드 배제.
* **실제 발송 게이트웨이 계약/벤더 확정:** 특정 문자 유통사(SKT, KT, LGU+, 알리고 등) 선정 배제.
* **모바일 Push API 연동:** 모바일 디바이스 FCM/APNS 인프라 구축 배제.
* **학부모 앱 설치 여부 판별:** 하이브리드 앱 클라이언트와의 모바일 기기 설치 판별 연동 배제.
* **카카오 템플릿 실제 등록/승인 자동화:** 카카오 비즈니스 템플릿의 자동 등록/수정 API 연동 설계 배제.

## 2. 현재 구현 상태 요약

* **메시지 보내기 수신자 선택:** 원생 목록 클릭 시 우측에 보호자1, 보호자2, 원생 본인의 연락처가 연계되어 동적으로 활성화되며, 주보호자(보호자1)는 정보가 정상적일 때 기본 선택되도록 구현되었습니다.
* **발송 전 확인 모달 (Focus Confirm):** 전송 전 최종 타겟 수와 제외 사유가 있는 제외자 명단, 그리고 실제 이름이 치환된 완성형 본문 미리보기를 스크롤 형태로 제공합니다.
* **템플릿 초안 적용:** 결석 알림 등 기본 4가지 템플릿 보관함이 있어 원장이 빠르게 본문 초안을 채울 수 있습니다.
* **오늘 콘솔 Handoff:** 오늘 원장 콘솔의 미납/결석 Row에서 [메시지 보내기]를 누르면 대상 원생 정보 및 템플릿, 그리고 수업시간 정보 등이 브라우저 스토리지 페이로드(1회 소비)를 거쳐 자동으로 초안창에 로드됩니다.
* **outboundMessageLogs의 기존 역할:** 단순 발송 성공 후 로그 데이터(`stateStore.db.outboundMessageLogs`)를 가공하여 프론트엔드의 최근 발송 이력 탭에 누적시키는 Stub 데이터 성격입니다.
* **parentMessages와의 분리 원칙:** `parentMessages`는 학부모 포털의 피드에 표시되는 전용 데이터이며, 실제 문자/알림톡 발송 이력(`outboundMessageLogs`)은 원장 측의 통신 발송 내역으로 **서로 물리적으로 분리된 아키텍처**를 유지하고 있습니다.

## 3. 채널 분리 원칙 (Channel Separation Principles)

시스템의 유기적 흐름과 행정 신뢰성을 높이기 위해 아래 채널 간 역할을 명확히 분리하고, **자동 동일시 현상을 차단**합니다.

```
┌──────────────────────────────────────────────────────────────────┐
│                           발송 요청 발생                         │
└────────────────┬────────────────────────────────┬────────────────┘
                 │                                │
                 ▼ (독립 작동)                     ▼ (독립 작동)
┌────────────────────────────────┐┌────────────────────────────────┐
│   학부모 포털 피드 데이터      ││     실제 유료 통신 발송        │
│    (parentMessages 저장)       ││   (문자 / 카카오 알림톡 발송)   │
└────────────────────────────────┘└────────────────────────────────┘
                 │                                │
                 ▼ (독립 작동)                     ▼ (독립 작동)
┌────────────────────────────────┐┌────────────────────────────────┐
│  학부모 앱 내 배지/알림 카운트 ││      오늘 원장 콘솔 Task       │
│      (Red Dot 및 실시간 배지)  ││    (수동으로 완료 버튼 클릭)   │
└────────────────────────────────┘└────────────────────────────────┘
```

1. **유료 발송과 parentMessages의 분리:** 문자/알림톡 발송이 성공했더라도 이것이 `parentMessages` 레코드의 생성과 자동으로 동일시되지 않습니다. `parentMessages`는 학부모 포털 전용 알림함 피드 데이터입니다.
2. **유료 발송과 오늘 콘솔 Task의 분리:** 문자/알림톡 발송이 완료되었다 하더라도, 오늘 원장 콘솔의 미납/결석 Task가 자동으로 'done' 처리되지 않습니다. 실제 사유 파악 및 행정 처리가 완결된 것을 원장이 직접 판단하여 [완료] 단추를 눌러야 행정 누락이 방지됩니다.
3. **학부모 알림 설정과의 독립성:** 학부모 포털 설정의 "메시지함/푸시 수신 설정"은 자동 알림 시스템에 기여하는 파라미터일 뿐이며, 원장이 필요에 의해 "메시지 보내기"에서 수동으로 문자를 발송하는 행위는 이와 별개로 강제 집행이 가능합니다.

## 4. 채널 선택 UI 정책 (Channel Selection UI Options)

과금 위험과 전송 보장률을 종합 평가하기 위해 네 가지 발송 옵션 후보를 비교 검토합니다.

| 발송 옵션 후보 | 이점 (Pros) | 한계 (Cons) | 추천 및 적용 가이드라인 |
| :--- | :--- | :--- | :--- |
| **1. 문자만 발송 (SMS/LMS)** | 도달률이 가장 보장되며 별도 템플릿 사전 승인 없이 자유 작성 가능. | 글자 수에 따라 비용이 비쌈 (특히 LMS 전환 시 단가 상승). | **선택 가능 후보** (가장 안정적인 기본 발송 방식) |
| **2. 알림톡만 발송** | 문자 대비 발송 단가가 매우 저렴하고 브랜드 로고 및 템플릿 신뢰도 높음. | 카카오톡 미사용자 또는 친구톡 차단 고객 대상 전송 실패 가능. | **선택 가능 후보** (비용 절감 효과가 우수함) |
| **3. 알림톡 우선 + 실패 시 문자 대체 (Fallback)** | 비용이 저렴한 알림톡을 먼저 찌르고, 실패 시 문자로 전송하여 도달률 100% 보장. | 템플릿 사전 승인 필수 및 실패/재시도 정책 설계 복잡도 매우 높음. | **유력 후보 (기본값 설정 유예):** 템플릿 승인 및 실패 상태기반 Fallback 엔진이 완성된 시점에만 도입 가능. |
| **4. 문자와 알림톡 동시 발송** | 알림 속도가 가장 빠르며 두 채널 모두로 안내하여 누락 최소화. | **이중 과금 발생** 및 학부모에게 중복 스팸성 피로감 유발. | **기본값으로 추천하지 않음** (이중 청구 및 민원 유발 방지) |

> [!WARNING]
> 이중 과금 및 스팸 피로도 위험이 매우 높기 때문에 **"문자와 알림톡 동시 발송"은 절대 기본값으로 권고하지 않습니다.** 알림톡 Fallback 방식은 매력적이나, 향후 템플릿 승인 상태 머신과 대체 발송 큐 로직이 완비된 후에 제한적으로 롤아웃해야 합니다.

## 5. 카카오 알림톡 템플릿 승인 정책

알림톡 채널은 문자(SMS)처럼 본문을 자유롭게 작성하여 보낼 수 없으며, 사전에 카카오가 심사하여 승인한 **정형화된 템플릿 본문 및 변수 파라미터**를 통해서만 발송이 가능합니다.

1. **개념적 분리:** 현재 Phase 16O에 구현된 템플릿(결석/수강료 등)은 "원장의 본문 작성을 도와주는 로컬 편집 보조 초안(Draft Template)"일 뿐이며, 카카오 채널에서 승인받은 "실물 카카오 알림톡 승인 템플릿"이 아닙니다.
2. **템플릿 레지스트리 구성 요소:** 향후 알림톡 도입 시 필요한 데이터 구조는 다음과 같습니다.
   - `templateCode`: 카카오에 등록된 고유 템플릿 코드
   - `templateName`: 템플릿 관리 명칭
   - `approvedContent`: 카카오가 승인한 고유 본문 스켈레톤 (예: `[#{학원명}] #{이름} 원생의...`)
   - `approvedVariables`: 템플릿에 사용할 치환 가능한 변수 목록 (`['학원명', '이름', '수업시간']`)
   - `channel`: 등록된 카카오 비즈니스 채널 ID
   - `status`: 템플릿 상태 (`'pending'` | `'approved'` | `'rejected'`)
3. **미승인 템플릿 예외 처리 후보:** 카카오 알림톡은 승인된 템플릿 규격 안에서만 발송 가능하므로, 향후 구현 단계에서는 미승인/변조 가능성이 있는 본문을 알림톡으로 발송하지 않도록 사전 경고 또는 차단하는 구조를 검토합니다. 문자(SMS/LMS) 대체 전송은 운영 정책, 비용 정책, 벤더 실패 코드, 원장 확인 UX가 확정된 이후 선택 가능한 fallback 후보로만 둡니다.

## 6. 메시지 데이터/로그 모델 설계

발송 요청 단위와 수신자별 전송 결과를 1:N으로 관리하여 대량 발송 및 추적성, 그리고 실패 데이터 분석을 완벽하게 처리할 수 있도록 설계합니다.

### 1) 구조 분리 권고
- **`outboundMessageRequests` (1):** 발송 마스터 테이블 (원장이 작성한 원천 발송 요청)
- **`outboundMessageDeliveries` (N):** 수신자별 개별 통신사 발송 및 Fallback 결과 이력 테이블

### 2) `outboundMessageDeliveries` 테이블 스키마 권고안
```sql
CREATE TABLE outboundMessageDeliveries (
    id VARCHAR(36) PRIMARY KEY,
    requestId VARCHAR(36) NOT NULL,            -- outboundMessageRequests 외래키
    relatedTaskId VARCHAR(36),                 -- 오늘 원장 콘솔 Task 연동 ID
    relatedDomainType VARCHAR(20),             -- 'attendance' | 'billing' | 'book'
    relatedDomainId VARCHAR(36),               -- 결제 내역 ID 또는 출결 기록 ID
    channel VARCHAR(10) NOT NULL,              -- 'sms' | 'lms' | 'alimtalk'
    provider VARCHAR(20),                      -- 외부 발송 벤더명
    providerMessageId VARCHAR(50),             -- 벤더 측 고유 전송 트랜잭션 ID
    requestPayloadHash VARCHAR(64),            -- 중복 발송 방지용 페이로드 해시
    status VARCHAR(20) NOT NULL,               -- 'queued' | 'sending' | 'sent' | 'failed' | 'fallback_sent' | 'skipped'
    failureCode VARCHAR(30),                   -- 실패 오류 코드
    failureReason TEXT,                        -- 실패 상세 사유
    fallbackFrom VARCHAR(10),                  -- 대체 발송 전 채널 (예: 'alimtalk')
    fallbackTo VARCHAR(10),                    -- 대체 발송 후 채널 (예: 'lms')
    costEstimate DECIMAL(10, 2),               -- 발송 비용 추정액 (원)
    recipientPhoneMasked VARCHAR(20) NOT NULL, -- 마스킹된 전화번호 (로그 노출용: '010-****-1234')
    recipientPhoneEncrypted TEXT NOT NULL,     -- 암호화된 실제 전화번호 (개인정보 보호용)
    sentAt DATETIME,                           -- 실제 발송 시작 시각
    failedAt DATETIME,                         -- 최종 실패 확인 시각
    createdAt DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

> [!IMPORTANT]
> **개인정보 보호 원칙:** 감사 로그나 일반 DB 조회 시 수신인의 실제 전화번호 평문 노출을 원천 배제합니다. 화면이나 감사 로그에 표시할 `recipientPhoneMasked`를 별도로 관리하고, 발송 재시도 등에 필요한 실번호는 암호화하여 저장(또는 별도 토큰 참조 테이블로 격리)하도록 설계해야 합니다.

## 7. 중복 발송 및 과금 방지 정책

사용자 실수나 네트워크 순연으로 인한 불필요한 발송 실패 및 이중 과금을 차단하기 위해 아래 안전장치를 적용합니다.

1. **수신자 통계 불일치 차단:** 발송 전 확인 모달(Focus Confirm)에서 연산된 `dedupe` 수신자 명단 수와 최종적으로 큐에 삽입되는 전송 대상 목록이 일치하도록 통제합니다.
2. **멱등성 키 (Idempotency Key) 제안:** 
   - 동일한 업무 건에 대해 중복 실행되는 것을 막기 위해 `relatedTaskId` + `recipientPhone` + `bodyHash` + `channel` 조합으로 전송 고유 해시 키를 생성합니다.
   - 발송 프로세스 시작 전 이 고유 키의 생존 여부를 캐시(Redis 또는 세션 DB)에서 확인하여, 3분 이내 동일 요청 유입 시 프로세스를 자동 반려합니다.
3. **더블 클릭 방지 (Double-Submit Guard):** 최종 '발송' 버튼 클릭 즉시 버튼을 `disabled` 상태로 변경하고 Spinner 처리를 수행하여 물리적인 중복 클릭을 원천 차단합니다.
4. **대체 발송(Fallback) 추적:** 실패하여 문자로 대체 전송 시, 원본 `alimtalk` 전송 로그를 'failed' 및 'fallback_sent'로 마크하고 대체 전송 로그에 `fallbackFrom: 'alimtalk'` 정보를 엮어 데이터 추적성을 확보합니다.

## 8. 실패 / 재시도 / Fallback 정책 후보 (Case-by-Case)

각 전송 오류 상황에 따른 사용자 UI 표시 상태와 후속 처리 모델을 정의합니다.

| 발생 케이스 | 원장 화면 상태 표시 | 로그 상태 (`status`) | 자동 재시도 여부 | Fallback 실행 여부 |
| :--- | :--- | :--- | :--- | :--- |
| **SMS 발송 실패** | "전송 실패 (통신사 오류)" | `failed` | 없음 (수동 재시도 유도) | 불가 (최종 채널) |
| **LMS 발송 실패** | "전송 실패 (규격/용량 초과)" | `failed` | 없음 | 불가 (최종 채널) |
| **알림톡 템플릿 미승인** | "발송 제한 (미승인 본문)" | `skipped` | 불가 | **SMS/LMS 대체 전환 후보 검토** |
| **알림톡 수신 불가 (카카오톡 미설치 등)** | "알림톡 불가 (문자 전환 검토)" | `failed` -> `fallback_sent` | 불가 | **SMS/LMS로 Fallback 대체 발송 후보 검토** |
| **알림톡 발송 실패 (시스템 에러)** | "알림톡 실패 (문자 전환 검토)" | `failed` -> `fallback_sent` | 1회 재시도 후 실패 시 | **SMS/LMS로 Fallback 대체 발송 후보 검토** |
| **네트워크 오류 / Timeout** | "연결 시간 초과 (대기 중)" | `queued` | 최대 3회 자동 재시도 | 3회 실패 시 최종 `failed` 처리 검토 |
| **일부 성공 / 일부 실패** | "부분 발송 (실패 건 존재)" | 수신자별 `sent` / `failed` 기록 | 실패 수신자만 필터링 | 실패 수신자에 한해 문자 Fallback 후보 검토 |
| **중복 요청 감지** | "중복 발송 취소됨" | `skipped` (사유: 중복) | 불가 | 불가 |
| **수신거부 / 번호 오류** | "발송 대상 제외 (오류 번호)" | `skipped` (사유: 차단) | 불가 | 불가 |

## 9. 보안 및 권한 정책

* **유료 발송 권한 통제:** 메시지 발송은 실제 학원의 비용 지출을 수반하므로, 오직 **'원장(Director)' 권한을 가진 계정**에만 최종 발송 기능을 활성화합니다.
* **강사 권한 제어 정책:** 강사(Teacher) 권한은 결석 확인이나 교재 요청 등 시스템 태스크 생성까지만 가능하며, 학부모 대상 유료 문자 직접 전송은 불가능하도록 차단하거나 원장의 승인 하에 전송이 대기되도록 제한합니다.
* **감사 로그(Audit Trail) 보존:** 모든 유료 발송 건에 대해 어떤 원장/직원 계정이, 언제, 어떤 카테고리의 업무로 몇 명에게 전송하여 얼마의 예상 비용이 부과되었는지를 추적하는 감사 로그 시스템을 구축합니다.
* **예약 발송 취소 검토 분리:** 예약 발송에 대한 등록 취소 및 즉시 발송 전환 비즈니스 룰은 복잡도를 고려하여 다음 후속 구현 검토 범위로 분리합니다.

## 10. 향후 구현 단계 제안 (Roadmap)

1. **Phase 16R-1 (인터페이스 설계):** 유료 발송 인터페이스 및 추상화 벤더 라이브러리(`MessageProviderInterface`) 정의.
2. **Phase 16R-2 (데이터베이스 고도화):** `outboundMessageRequests` 및 `outboundMessageDeliveries` 스키마 빌드 및 마이그레이션.
3. **Phase 16R-3 (Mock 프로바이더 구현):** 로컬 검증용 가상 발송 모듈 구현 및 로깅 기반의 샌드박스 환경 수립.
4. **Phase 16R-4 (템플릿 레지스트리 구축):** 카카오 비즈니스 템플릿 코드 매핑 구조 및 초안 치환 호환성 검증 모듈 추가.
5. **Phase 16R-5 (Fallback 상태 머신 구축):** 알림톡 실패 이벤트를 감지하여 설계된 fallback 후보 정책에 따라 문자 큐에 적재 검토 및 이력을 매핑하는 상태 머신 엔진 개발.
6. **Phase 16R-6 (실 벤더 연동):** 선정된 통신 대행사 API 연동 및 샌드박스 테스팅.
7. **Phase 16R-7 (운영 도구 개발):** 원장 대시보드 내 월별/일별 발송량 통계, 과금 예측치 및 충전 잔액 조회 기능 연동.

## 11. 수동 확인 가이드라인 (향후 구현 시 점검 포인트)

향후 개발 단계 완료 시 아래 포인트들을 기준으로 검증을 진행해야 합니다.

1. **UI 경고 메시지:** 발송 방식 선택에서 "동시 발송" 선택 시 "이중 과금 위험" 경고 툴팁이 제대로 노출되는지 여부.
2. **비용 체감성:** 문자 발송(단문 SMS vs 장문 LMS) 및 알림톡 발송 단가 차이가 UI 화면에 예상 금액으로 직관적으로 합산 표기되는지 여부.
3. **통계 정합성:** Focus Confirm 확인 모달의 발송 가능 수와 실제 통신사 게이트웨이로 나가는 트랜잭션 개수가 정확히 일치하는지 여부.
4. **대체 전송(Fallback) 검증:** 임의로 알림톡 전송 에러를 발생시켰을 때, 설계된 정책에 따라 문자로 Fallback 대체 발송 프로세스가 작동하고 관련 상태 로그가 정상 전이되는지 여부.
5. **개인정보 안전성:** DB 원천 로그나 `outboundMessageDeliveries` 테이블을 임의 쿼리했을 때 수신자 전화번호가 평문으로 남지 않고 암호화되어 있는지 여부.
