# Phase 16Q 통합 검증 및 릴리즈 노트: 학부모 메시징/소통 흐름 통합 점검

본 문서는 Phase 16I부터 16P까지 구현된 학부모 연락처, 메시지함 데이터, 학부모 포털, 원장 메시지 보내기, 오늘 원장 콘솔 handoff 연동 흐름을 통합 관점에서 종합 검증하고 정리한 릴리즈 노트입니다.

> [!IMPORTANT]
> 본 Phase 16Q 단계는 **기능 추가가 없는 정리/검증/문서화 전용 Phase**입니다. 기 구현된 정책의 무결성을 검증하고, 미충돌 여부를 확인하며, 명시적 제외 범위를 명확히 규정하여 안전한 릴리즈를 준비합니다.

---

## 1. Phase 16I ~ 16P 구현 요약

* **Phase 16I:** 학부모 포털 기본 라우팅 및 3대 영역(출결현황, 수강료 납부, 선생님 코멘트) 탭 레이아웃 및 캘린더/리스트 기초 연동.
* **Phase 16J/K:** 알림 및 설문 탭 구현, 설문 제출 상태와 미확인 배지 해제 라이프사이클 분리, 코멘트 확인 시 unread 상태 실시간 동기화.
* **Phase 16L/M:** 등원/하원, 수강료 청구/미수납/완납, 교재비 청구/미수납/완납 시 parentMessages 테이블 자동 생성 및 설정 매핑 엔진(SMS/알림톡/Push 활성화 상태 매핑).
* **Phase 16N:** 학부모 포털 내 영역별 미확인 알림 개수(배지) 집계 및 각 리스트/달력의 미확인 항목 우상단 Red Dot 인디케이터 정책 수립 및 뷰 바인딩.
* **Phase 16O:** 원장 메시지 보내기 3단 패널 내 수신자 목록에서 보호자1/2 연락처 유무에 따른 동적 노출, 발송 전 최종 검토(Focus Confirm) 모달, 상황별 템플릿(결석/수강료/교재비) 치환 및 자동 초안 로드.
* **Phase 16P:** 오늘 원장 콘솔의 Row 액션에서 [메시지 보내기] 클릭 시, 학생 정보와 상황에 맞는 템플릿 및 수업 시간(Class Time) 파싱 데이터를 연동(Handoff)하여 메시지 작성 화면으로 매끄럽게 연결.

## 2. 핵심 데이터 모델 요약

### 1) `parentContacts` (학부모 연락처)
* **목적:** 원생별 보호자 정보를 구조화하여 메시지 발송 시 정확한 매핑을 지원합니다.
* **필드 구성:**
  - `id`: 고유 식별자
  - `studentId`: 연결된 원생 ID
  - `slot`: `'parent1'` (보호자1/주연락처) 또는 `'parent2'` (보호자2/부연락처)
  - `name`: 보호자 이름
  - `relation`: 관계 (`'mother'`, `'father'`, `'grandparent'` 등)
  - `phone`: 전화번호
  - `canReceiveMessage`: 메시지 수신 동의 여부 (`true`/`false`)
  - `isPrimary`: 주연락처 플래그 (`true`/`false`)

### 2) `parentMessages` (학부모 메시지함)
* **목적:** 알림톡/SMS/Push와 연계되어 학부모에게 자동/수동으로 전달되는 모든 소통 기록을 저장하며, 학부모 포털의 보조 데이터로 활용됩니다.
* **필드 구성:**
  - `id`: 고유 식별자
  - `studentId`: 대상 원생 ID
  - `type`: 메시지 구분 (`'check_in'`, `'check_out'`, `'tuition_billing'`, `'tuition_paid'`, `'tuition_overdue'`, `'book_billing'`, `'book_paid'`, `'book_overdue'`)
  - `title`: 메시지 제목
  - `body`: 메시지 본문
  - `pushRequired`: 모바일 푸시 필요 여부 (`true`/`false`)
  - `pushStatus`: 푸시 발송 상태 (`'pending'`, `'sent'`, `'not_required'`)
  - `readStatus`: 학부모 확인 여부 (`'unread'`, `'read'`)
  - `readAt`: 학부모 확인 시각 (ISO String)
  - `dedupeKey`: 중복 생성 방지를 위한 고유 키 (`{TYPE}_{ID}`)
  - `relatedDomainId`: 참조 엔티티 ID (출결 ID 또는 결제 ID)

### 3) `parentMessageSettings` (학부모 메시징 정책 설정)
* **목적:** 이벤트별 메시지함 저장 및 모바일 푸시 발송 허용 여부를 제어합니다.
* **필드 구성:**
  - `studentId`: 원생 ID (외래키)
  - `tuitionBilling`, `tuitionPaid`, `tuitionOverdue`, `bookBilling`, `bookPaid`, `bookOverdue`, `checkIn`, `checkOut` 각각에 대해:
    * `messageEnabled`: 메시지함 저장 활성화 여부
    * `pushEnabled`: 모바일 푸시 활성화 여부
  - **정합성 룰:** `messageEnabled`가 `false`이면 `pushEnabled`는 자동으로 `false`로 보정(동기화)됩니다.

### 4) Handoff Payload 규격
* **목적:** 오늘 원장 콘솔에서 메시지 보내기 화면으로 화면을 전송할 때 필요한 콘텍스트를 직렬화하여 전달합니다.
* **스토리지 키:** `sessionStorage` 내 `dayday_handoff_payload`
* **구조:**
  ```json
  {
    "source": "today_console",
    "taskId": "TASK_ID",
    "studentId": "STUDENT_ID",
    "suggestedTemplateType": "absent | billing | overdue | book_billing",
    "relatedDomainType": "attendance | billing | book",
    "relatedDomainId": "DOMAIN_ID",
    "meta": {
      "classTime": "14:00 ~ 15:00"
    }
  }
  ```

## 3. 원장 화면 구현 요약

* **메시지 보내기 수신자 선택:** 
  - 원생 목록에서 선택 시 우측 수신자 옵션에 `'보호자1'`, `'보호자2'`, `'원생 본인'` 칩이 활성화됩니다.
  - 보호자1 정보가 있을 경우 기본 체크되며, 연락처가 없거나 수신 비동의인 경우 경고 메시지가 노출되고 체크가 불가능합니다.
  - `'발송인원 추가'` 클릭 시 최종 수신인 패널에 담기며 선택 목록이 깔끔하게 정리됩니다.
* **발송 전 확인 모달 (Focus Confirm Overlay):**
  - 발송 클릭 시 화면 전체에 포커스 오버레이가 생성되어 수신인 명단(발송 가능 대상 및 수신 거부/제외 대상 사유 포함)과 치환된 메시지 본문 미리보기를 스크롤 형태로 제공합니다.
  - 오버레이 내부의 최종 `'발송'` 클릭 시에만 실제 로그가 적재되며, 취소 시에는 어떤 DB 부작용도 남지 않습니다.
* **템플릿 초안 자동 완성:**
  - 결석 확인, 수강료 독촉, 교재비 독촉 등 상황에 맞는 최적화 템플릿(메시지 보관함 탭)이 마련되어 있습니다.
  - Handoff로 진입할 경우 해당 템플릿이 자동으로 compose 입력창에 사전 세팅됩니다.
* **오늘 콘솔 Handoff:**
  - 원장 오늘 콘솔의 Row에서 [메시지 보내기]를 클릭하면 `sessionStorage`에 페이로드를 임시 적재한 후 메시지 보내기 뷰로 즉시 라우팅합니다.

## 4. 학부모 화면 구현 요약

* **출결 현황 달력/리스트:**
  - 등/하원 여부 및 지각 정보가 달력 일자별로 표기됩니다.
  - 리스트 탭에서는 당일 미확인 출결 기록에 대해 우상단에 빨간색 점(Red Dot) 인디케이터가 표시되며, 상세 정보 모달을 열어 확인할 시 미확인 상태가 해제됩니다.
* **수강료 납부 (미납/완료):**
  - 미납 탭 및 완료 탭으로 이원화되어 교육비/교재비의 청구 상태를 한눈에 파악합니다.
  - 미확인 수납/청구 내역은 Red Dot이 표시되며 상세 모달 조회 시 해제됩니다.
* **선생님 코멘트:**
  - 강사가 남긴 피드백을 시간 역순으로 리스팅합니다.
  - 미확인 코멘트는 상세 팝업을 눌러 코멘트 내용을 완독(상세 확인)할 때 미확인 배지 상태가 해제됩니다.
* **알림 및 설문:**
  - 학원 공지사항(알림) 및 설문을 모아보는 탭입니다.
  - 설문의 경우 미확인 상태(Red Dot) 해제는 상세 팝업 조회 즉시 발생하며, 이는 설문의 최종 '제출(Submitted)' 상태와 완전히 분리되어 작동합니다.
* **공통 미확인 배지 정책:**
  - 학부모 포털 하단 내비게이션 탭 메뉴에 실시간으로 미확인 알림 카운트(배지)가 표시되며, 사용자가 확인을 완료하는 즉시 차감됩니다.

## 6. 수동 메시지 보내기 흐름 요약

원장 및 직원이 직접 메시지를 작성하여 발송하는 수동 흐름은 다음과 같은 단계를 따릅니다:

1. **대상 검색 및 선택:** 좌측 패널에서 원생을 이름/클래스/미납여부 등으로 검색하고 체크박스를 선택합니다.
2. **수신 보호자 지정:** 선택된 원생별로 연락처 상태 및 수신 동의 상태에 따라 보호자1(주연락처), 보호자2(부연락처), 원생 본인 중 전송할 대상을 선택한 뒤 '발송인원 추가' 버튼을 눌러 임시 수신처로 빌드합니다.
3. **메시지 작성 및 템플릿 선택:** 중앙 패널에서 제목과 본문을 직접 입력하거나, 우측 보관함 패널의 상황별 템플릿(결석/수강료/교재비/공지 등) 또는 원장 저장 템플릿을 선택하여 본문 초안을 채웁니다. 매크로(`#{이름}`)를 사용하여 원생별 자동 치환이 가능합니다.
4. **발송 옵션 세팅:** 발송 방식(SMS/알림톡/Push) 및 예약 전송(예약 시간 설정) 여부를 선택합니다.
5. **발송 전 검토 모달:** '발송하기' 클릭 시 Focus Confirm 오버레이가 나타나 최종 발송 대상(발송 불가 대상 사유 포함)과 치환 결과 미리보기를 검토합니다.
6. **최종 발송:** 검토 모달에서 최종 '발송'을 클릭하면 이력 로그(`outboundMessageLogs`) 및 개별 메시지 레코드가 적재되며, 취소 시에는 어떤 데이터도 생성되지 않습니다.

## 7. 오늘 원장 콘솔 Handoff 흐름 세부 요약

```
[오늘 원장 콘솔] ➔ 대상 Row의 [메시지 보내기] 클릭
       │
       ▼ sessionStorage에 dayday_handoff_payload 세팅 후 '/dir-message-send' 이동
[메시지 보내기] 
       │ 1. 렌더링 시 페이로드 파싱 후 즉시 sessionStorage에서 페이로드 삭제 (1회 소비 방침)
       │ 2. 페이로드 정보 기반으로 대상 원생, 보호자1, 최적의 템플릿(수업 시간 치환 포함) 자동 선택
       │ 3. compose 입력창 세팅 완료 (만약 원장이 일반 메뉴로 재입력 중이던 초안이 있었다면 덮어쓰지 않고 보존)
       │
       ▼ 발송 모달 확인 후 최종 전송
[발송 완료 피드백] ➔ "오늘 원장 콘솔로 돌아가시겠습니까?" 다이얼로그 팝업
       │
       ▼ [확인] 클릭 시
[오늘 원장 콘솔 복귀] ➔ 연동 대상 원본 태스크는 자동으로 완료 처리되지 않고 오픈 상태를 유지
```

## 8. 명시적 제외 범위 (Out of Scope)

프로젝트 기한과 인프라 제약을 고려하여 아래 항목들은 본 설계 및 프로토타입 구현 범위에서 명시적으로 제외되었습니다.

1. **실제 외부 SMS API 연동 없음:** 외부 문자 발송 게이트웨이 연동 코드가 존재하지 않으며 발송 내역 적재(Stub)로 대체합니다.
2. **카카오 알림톡 API 연동 없음:** 카카오 비즈니스 채널 API 연동 및 알림톡 템플릿 검증/승인 비즈니스 제어 로직이 없습니다.
3. **실제 모바일 Push 서버/토큰 연동 없음:** 디바이스 Push 토큰 수집 정책 및 FCM(Firebase Cloud Messaging)이나 APNS 실제 연동 인프라가 배제되었습니다. (`pushRequired = true` 플래그 관리 및 내역 상태 변경으로 검증 대체)
4. **학부모 앱 설치 여부 판별 없음:** 학부모가 현재 하이브리드 앱을 설치했는지, 혹은 웹브라우저로만 보는지 판별하여 채널을 우회하는 동적 스위칭은 구현되지 않았습니다.
5. **알림톡 템플릿 승인 제어 없음:** 카카오 채널에서의 템플릿 사전 승인 및 심사 관련 연동 기능이 배제되었습니다.
