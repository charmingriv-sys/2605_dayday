# Phase 17G-4B Today Console Task Drawer Functional Policy
## 오늘 원장 콘솔 task 상세 드로어 기능 정책 및 최소 재구현 명세

본 문서는 튜링음악학원 DayDay 시스템의 오늘 원장 콘솔(todayConsole) 내 운영 task에 대해, 우측 상세 드로어(Drawer)를 최소 범위로 안전하게 재구현하기 위한 기능 정책 및 상세 명세서입니다.

---

## 1. Phase 기준 및 문맥 정의
* **최종 코드 구현 Phase**: Phase 17C (원생 상태 관리 UI 및 E2E 테스트 통과)
* **최종 정책 문서 Phase**: Phase 17G (휴원/퇴원 대시보드 및 콘솔 반영 정책 설계)
* **이번 정책 Phase**: Phase 17G-4B
* **17G-3 대시보드 KPI 작업 연계**: 17G-3 대시보드 KPI 작업은 미착수 상태이며, 이번 Phase에서는 이를 다루지 않습니다.
* **본 문서의 성격**: 오늘 콘솔 task 상세 드로어의 최소 재구현을 시작하기 전, 기능 설계 표준을 정립하고 기존 기능과의 충돌을 원천 차단하기 위한 정책 정의 문서입니다.

---

## 2. 조사 결과 반영 및 방향성 (Phase 17G-4A / 17G-4A-2)
* **조사 결과 요약**: 
  과거 오늘 콘솔 전용 task 상세 드로어로 동작하던 복구 가능한 구현 코드는 현재 Git 히스토리 및 백업본 조사 범위 내에서 발견되지 않았습니다.
* **재구현 접근 방식**: 
  본 드로어 추가 작업은 "기존 오늘 콘솔 드로어의 소스 복원"이 아닙니다. 대신 출결 제어 콘솔(`attendanceControlView.js`) 및 주요 일정 화면(`majorScheduleView.js`)에 구현되어 있는 일관된 **우측 슬라이드 드로어 패턴**을 참고하여, 오늘 콘솔에 맞게 최소 범위로 재가공하는 **"최소 재구현(Reconstruction)"**으로 정의합니다.
* **사용자 기억 존중**: 
  드로어 UI는 시스템 전체의 일관성 및 편의성을 위해 적합한 설계이므로, 사용자의 기억과 일관성을 맞춰 오늘 콘솔에 안전하게 도입하는 방향으로 수립합니다.

## 3. 오늘 콘솔 task 유형 및 Drawer 매핑 정책
오늘 콘솔의 업무는 크게 두 가지 영역으로 구분되며, 드로어 노출 정책 역시 이에 대응하여 분리 적용합니다.

### 3-1. 시스템 생성 task (드로어 오픈 대상)
시스템의 데이터 검사 엔진 및 정책에 따라 자동 생성되는 과업(Task)들로, 카드 클릭 시 **드로어가 오픈되는 주 대상**입니다.
* **미수납 관련 task** (`overdue`, `billing`, `book_billing` 등)
* **미출결/출결 경고 관련 task** (`absent`, `attendance_warning` 등)
* **교재/수업/운영 점검 관련 task** (`book_check`, `schedule` 등)
* **기타 시스템 체크 task** (`staff_warning` 등)

### 3-2. 사용자 수동 운영 메모 task (드로어 대상 제외)
원장이 필요에 따라 수동으로 작성한 할 일(Todo/Memo)로, **드로어 대상에서 제외**합니다.
* **정책**: 수동 운영 메모 카드를 클릭할 때에는 드로어를 열지 않고, 기존과 동일하게 화면 하단/사이드의 '운영 메모 추가/수정 폼'으로 진입하여 즉시 수정 모드(`editingTaskId`)로 연동하는 흐름을 그대로 보존합니다.

## 4. Drawer 동작 및 표시 정책

### 4-1. 진입 및 방어 조건 (Event Propagation Guard)
* **카드 본문 클릭**: 시스템 생성 task 카드의 빈 영역 또는 텍스트 본문(클릭 존)을 클릭하는 경우에만 우측 드로어가 열리도록 처리합니다.
* **액션 버튼 클릭 보호**: 카드 내부에 노출된 `완료`, `보류`, `제외`, `메시지 보내기` 등의 버튼 클릭 시에는 드로어가 열리면 안 됩니다. 버튼 클릭 시 이벤트 버블링을 확실하게 차단(`e.stopPropagation()`)하여 드로어가 비의도적으로 중복 노출되는 현상을 방지합니다.
* **도메인 데이터 보호**: 드로어는 현재 task의 상황을 명확하게 파악하고 후속 액션으로 넘겨주는 '상세 뷰어' 목적을 가집니다. 드로어 내부에서 도메인 데이터(출결 상태, 청구서 금액 등)를 직접 강제 변경하는 화면을 1차적으로 제공하지 않으며, 상태 전이가 필요한 경우 기존의 오늘 콘솔 task 액션 핸들러를 재사용합니다.

### 4-2. 드로어 표시 최소 정보 명세
상세 드로어 내부에는 대상 업무의 유형과 성격을 한눈에 파악할 수 있는 핵심 메타데이터가 렌더링되어야 합니다.
1. **업무 개요**: task 제목, 카테고리(유형), 우선순위(중요도).
2. **진행 상태**: 현재 상태(대기/보류/제외/완료) 및 완료/제외된 경우 당시 처리 시각.
3. **일정/기준일**: 해당 task가 발생하거나 완료/조치해야 하는 타겟 날짜.
4. **연계 원생**: task와 연계된 원생 이름 및 담당 강사 정보 (해당하는 경우).
5. **판단 정보**:
   * *미납 관련*: 대상 수납 월, 청구 금액, 미납 구분(원비/교재비).
   * *출결/일정 관련*: 해당 수업/이벤트 시간 및 세부 상세 내용.
6. **실행 액션 (기존 버튼 연계)**: 드로어 하단에 해당 task에 주어지는 액션 버튼(`완료`, `보류`, `제외` 등) 및 `메시지 보내기` 진입점을 동일하게 제공합니다.

*주의: 상세 수납 전체 원장 대장, 상세 출결 30일 전체 이력, 퇴원생/휴원생의 무관한 개인 민감 정보 등은 정보 과노출 및 보안 정책 준수를 위해 노출 항목에서 명시적으로 제외합니다.*

## 5. 휴원/퇴원 원생 상태 정책과의 관계 (Phase 17 연계)
본 드로어는 Phase 17A~17G까지 수립된 원생 상태(휴원/퇴원) 도메인 정책을 완벽히 계승합니다.
* **드로어 내 상태 표시**: 드로어 최상단 원생 이름 옆에 해당 원생의 현재 상태 배지(`[휴원]`, `[퇴원]`)를 명확하게 렌더링하여 원장이 대상자의 상태를 실시간으로 인지할 수 있도록 유도합니다.
* **퇴원생 미납 채권 표시**: 퇴원생의 미결제 수납 관련 task(원비/교재비 미납 등)가 드로어로 노출되는 경우, 해당 원생이 퇴원 상태(`withdrawn`)임을 배지로 강조 표시하고, 임의 삭제 대신 수동 조치 경로(메시지 전송 또는 수납 처리 완료)를 드로어 내에 안전하게 제공합니다.
* **출결 예외 처리**: 휴원생/퇴원생의 스케줄에 따른 미출결 경고 task는 이미 생성 필터링 단계에서 배제하는 정책을 적용하므로, 드로어 노출 대상에서도 자연스럽게 격리됩니다.

## 6. 충돌 및 오작동 방지 가이드 (Conflict Prevention Rules)
* **이벤트 전파 차단**: `task-actions-container` 및 `btn-handoff`(메시지 보내기)를 클릭할 때는 드로어가 팝업되는 동작이 트리거되지 않도록 클릭 이벤트 타겟을 검증하고 차단 필터를 적용합니다.
* **기존 State 흐름 보존**: 드로어 제어를 위해 스토어(`stateStore`)의 글로벌 DB 상태 구조를 인위적으로 확장하지 않으며, `todayConsoleView.js` 컴포넌트 내의 로컬 뷰 상태 변수(`activeTaskId` 또는 `selectedTaskId`)만을 활용해 표시 여부를 제어합니다.
* **E2E 테스트 안정성**: 드로어 신설로 인해 기존에 작성된 `tests/e2e/today-console-flow.spec.js` 내의 Done/Snooze/Dismiss 버튼 경로가 깨지지 않도록, 카드 내부 기존 HTML 계층과 selector를 불필요하게 변경하지 않습니다.
* **오류 방어**: 드로어 내 특정 데이터 렌더링 중 오류(예: 존재하지 않는 원생 참조 등)가 발생하더라도, `try-catch` 가드를 두어 오늘 콘솔 대시보드 전체 화면이 렌더링 중단되거나 먹통이 되는 사고를 철저히 예방합니다.

## 7. 단계별 재구현 로드맵

### Phase 17G-4C: 오늘 콘솔 task 상세 드로어 최소 재구현 (Minimal Reconstruction)
* **목표**: 시스템 생성 task에만 반응하는 슬라이드 드로어 구조와 닫기 버튼, 백드롭을 생성하고 기초 연동 완료.
* **범위**: 
  * `todayConsoleView.js` 내부에 드로어 UI용 마크업 및 스타일 삽입.
  * 시스템 task 클릭 시 드로어를 오픈하고, 선택된 task의 텍스트 원본(설명글 등) 및 기본 메타데이터(제목, 유형, 상태) 렌더링.
  * 수동 메모 task는 기존 수정 폼 흐름 유지.
  * Playwright E2E 테스트에 최소 드로어 오픈/닫기 시나리오 보완.

### Phase 17G-4D: 드로어 상세 데이터 매핑 및 도메인 정책 연결 (Content Expansion)
* **목표**: task 유형별(수납/출결/교재) 원생 정보 및 상태 배지 등 판단을 돕는 정밀 데이터 로딩 기능 고도화.
* **범위**:
  * 스토어 API 연계를 강화하여 미납 월/금액, 수업 시간대 등 실시간 상세 데이터 렌더링.
  * 휴원/퇴원 원생의 상태 배지 및 경고 텍스트 결합.
  * 세부 다듬기 및 최종 QA.

## 8. 교재 관련 task 명칭 정리 및 신규 교재 확인 정책 (Phase 17G-4E)

기존 오늘 콘솔 내에서 유사한 성격으로 얽혀 있던 교재 관련 업무 프로세스를 명확히 정의하고, 명칭을 보다 직관적으로 정리하기 위해 정책을 다음과 같이 선언합니다.

### 8-1. 교재 관련 큐의 정의 및 명칭 변경
원장이 오늘 콘솔에서 처리해야 할 교재 업무를 명확하게 3개로 분리하여 큐에 노출하며, 혼동을 방지하기 위해 표시명(라벨)을 조정합니다.
1. **`book_check` (표시명 변경: 교재 확인 → 교재 지급 확인)**
   - **의미**: 담당 강사가 원생에게 특정 교재를 지급할 수 있도록 원장 승인/지급 완료 처리를 대기하는 행정적 확인 업무.
2. **`book_billing` (표시명 유지: 교재 결제 확인)**
   - **의미**: 지급이 승인/완료된 교재에 대하여 교재비 수납이 완료되었는지 재무적으로 확인하는 회계적 수납 업무.
3. **신규 큐 (표시명: 교재 확인)**
   - **의미**: 교재 등록 경과일 기준에 따라 원생의 학습 진도가 임박하여 새로운 교재 추천/진도 교체 시기를 점검하는 교습적 업무.
   - **드로어 적용 정책**: 본 큐는 수납이나 행정 절차와는 다르게 학생의 현 상태 점검이 핵심이므로, 별도의 전용 상세 레이아웃을 정의하지 않고 **"오늘 콘솔 일반 드로어(학생 상세 정보, 최근 출결, 메시지 이력 등 노출)"**를 그대로 재사용합니다.

### 8-2. 신규 `교재 확인` 큐의 식별자(Category/Type) 후보 제안
신규 큐 생성을 위해 데이터베이스 및 프론트엔드 연동에 사용할 카테고리/타입 식별자 후보군에 대한 검토 결과는 다음과 같습니다.

* **후보 1: `book_recommendation` (추천안)**
  - *장점*: 비즈니스 도메인 및 기획 관점에서 "다음 교재를 추천하는 큐"의 목적을 가장 직관적으로 표현합니다. 코드 가독성이 매우 뛰어납니다.
  - *단점*: 경과일 기준 점검이라는 유예 기간/경과일의 뉘앙스가 식별자만으로는 드러나지 않습니다.
* **후보 2: `book_elapsed_recommendation`**
  - *장점*: "등록 후 경과일 기준"이라는 기술적 조건이 식별자 이름에 명확히 드러납니다.
  - *단점*: 단어 길이가 길어 코드 작성이 다소 번거롭고 직관성이 반감될 수 있습니다.
* **후보 3: `book_progress_check`**
  - *장점*: 교재의 학습 "진도 점검"의 의미를 잘 전달합니다.
  - *단점*: 기존 `book_check`와 문자열이 유사하여(`_check`가 겹침) 개발 및 쿼리 필터링 시 개발자 실수로 인한 휴먼 에러나 정규식 매칭 오동작 위험이 큽니다.
* **최종 추천**: **`book_recommendation`**
  - 가독성이 우수하고 개발 시 실수 여지가 가장 적으며, 교재 지급(book_check) / 결제(book_billing)에 대응하는 단어의 짝(Recommendation)이 비즈니스 설계상 가장 깔끔합니다.

### 8-3. 다음 구현 Phase 후보 로드맵
- **Phase 17G-4E-1: Book Queue Terminology Repair**
  - 기존 `book_check` 표시명을 `교재 확인`에서 `교재 지급 확인`으로 변경.
  - 오늘 콘솔 내 KPI 요약 라벨, 카드 헤더 도메인명, 처리 승인 버튼 문구, E2E 테스트 단언문 내용 일제 정비. (기존 비즈니스 기능은 현상 유지)
- **Phase 17G-4E-2: New Book Recommendation Queue**
  - 교재 등록 경과일 기준 `교재추천` 상태 리스트 데이터를 오늘 콘솔 신규 `교재 확인` 큐로 연동하여 노출.
  - 기존 `book_check` 및 `book_billing` 데이터 필터와 철저히 분리 처리.
  - 오늘 콘솔 일반 드로어 자동 연계 처리 및 관련 E2E 테스트 시나리오 보완.

## 9. 구현 완료 정책 동기화 (Phase 17G-4F)

본 섹션은 Phase 17G-4C 및 17G-4E 단계에서 오늘 원장 콘솔(Today Console)의 기능 개발, 수기 QA, E2E 검증이 완료된 시점의 최종 물리 구현 정책을 동기화하여 명세합니다.

### 9-1. 오늘 콘솔 Task 상세 드로어 물리 정책
1. **드로어 오픈 및 재사용**
   - 시스템 생성 task(출결, 수납, 교재 등) 클릭 시 화면 전환 없이 우측 슬라이드 드로어가 활성화됩니다.
   - 연계 원생이 존재하는 task의 경우, 출결관제 화면의 원생 인스펙터 상세 템플릿(최근 4주 출결 요약, 수납 정보, 30일 이력 달력, 수정/메시지 전송 이력 등)을 그대로 재사용하여 풍부한 판단 정보를 제공합니다.
2. **드로어 하단 액션 버튼**
   - 드로어 하단 푸터 영역에 `메시지 보내기` 버튼과 `상세정보` 버튼을 제공합니다.
   - **메시지 보내기**: 기존 task에 정의된 handoff payload(학생 ID, 수강료 청구 ID 등)를 그대로 계승하여 메시지 작성 화면으로 자연스럽게 전환합니다.
   - **상세정보**: 해당 원생의 학적 상세 정보를 즉시 조회할 수 있는 상세 모달을 띄웁니다.
3. **UI 겹침 방지 가드 (Close-Before-Action)**
   - 메시지 보내기 또는 상세정보 등 드로어 내 하단 버튼을 실행할 때, 화면 요소의 겹침이나 포커스 이중 잠금을 방지하기 위해 **상세 드로어를 먼저 닫은(Close) 직후**에 화면 라우팅 또는 모달 팝업을 기동합니다.
4. **수동 운영메모 과업의 격리**
   - 사용자가 직접 등록한 수동 운영 메모는 상세 드로어를 열지 않고, 기존 오늘 콘솔 하단의 '운영 메모 추가/수정/삭제 폼'(`editingTaskId`)으로 바로 진입하여 데이터를 보정하는 기존 흐름을 그대로 유지합니다.

### 9-2. 일정확인 Task 상세 및 인라인 드로어 정책
1. **화면 이탈 방지 (Keep Console View)**
   - 일정확인 task(`schedule`, `schedule_check` 카테고리) 클릭 시, 오늘 콘솔 화면을 벗어나지 않고 오늘 콘솔 대시보드 상태를 그대로 유지합니다.
2. **인라인 주요 일정 상세 드로어 제공**
   - 오늘 콘솔 뷰포트 내에서 주요 일정 전용 상세 드로어 마크업을 인라인으로 동적으로 렌더링합니다.
   - 이 드로어에는 일정의 세부 내용(일정명, 구분, 날짜, D-day, 장소, 담당자, 공개여부, 참여 원생, 메모)을 안전하게 노출합니다.
3. **드로어 내부 처리 액션의 격리**
   - 드로어 내부에서는 사용자의 완료/확인 혼동을 방지하기 위해 **확인 완료 처리 버튼을 일절 배제**하고, 단순 정보 조회 후 드로어를 닫는 닫기(`닫기`/`X`) 버튼만 제공합니다.
4. **카드 내 처리 완료 액션 단일화**
   - 일정에 대한 최종 확인 처리는 오직 오늘 콘솔 task 카드의 우측 액션 킷에 위치한 **`[일정확인]`** 버튼을 통해서만 수행됩니다.
   - 버튼 클릭 시 기존의 `confirmMajorSchedule(eventId)` API 연동 및 `syncSystemRecommendations()`를 트리거하여 오늘 큐에서 해당 일정이 즉시 제거되고 majorSchedules DB의 확인 완료 상태가 물리적으로 동기화됩니다.

### 9-3. 교재 관련 Task 3분리 정책
교재에 관한 행정, 회계, 교습 목적을 명확히 분리하기 위해 3가지 큐와 prefix, 데이터 산출 규칙을 독립적으로 운영합니다.

1. **교재 지급 확인 (`book_check`)**
   - *의미*: 담당 강사의 교재 지급 요청 또는 원장의 직접 등록 건에 대해 승인 및 지급 행정 처리를 대기하는 업무입니다.
   - *Task Title Prefix*: `[교재 지급 확인]`
2. **교재 결제 확인 (`book_billing`)**
   - *의미*: 지급 승인/완료 처리된 교재에 대해 청구된 교재비 수납이 완료되었는지 확인하는 업무입니다.
   - *Task Title Prefix*: `[교재 결제 확인]`
3. **교재 확인 (`book_recommendation`)**
   - *의미*: 원생이 현재 교재를 배정받은 등록일(`regDate`) 이후 등원한 출석/지각 횟수가 교재 권장 학습일수(`recommendedDays`)의 90% 이상에 도달하여, 진도 체크 및 다음 교재로의 교습적 추천/교체를 검토하는 업무입니다.
   - *Task Title Prefix*: `[교재 확인]`
   - *자동 해소 (Auto-Resolution)*: 원생에게 해당 교재보다 최신의 신규 교재가 배정(더 최근의 `regDate` 또는 동일 일자 내 더 큰 `orderNo`를 갖는 `studentBook` 레코드 추가)되면, 기존 오픈되어 있던 추천/교체 검토 task는 자동으로 완료(`'done'`) 처리되어 큐에서 사라집니다.
   - *드로어 노출*: 학습 이력과 인적 정보 점검이 주 목적이므로, 전용 템플릿 대신 일반 원생 상세 드로어 템플릿을 연동합니다.

### 9-4. KPI 카드명과 Task Title Prefix의 완전 동기화 정책
오늘 콘솔 대기 과업 카드의 대괄호 prefix는 대시보드 상단의 KPI 요약 필터 카드 라벨명과 **띄어쓰기 한 자까지 완전히 동일하게 매칭**되어 인지적 일관성을 제공합니다.

* **수동 운영메모**: 사용자가 입력한 과업 제목 그대로 노출 (prefix 없음)
* **결석 확인**: KPI 카드명 `결석 확인` $\leftrightarrow$ Task Prefix `[결석 확인]` (띄어쓰기 일치)
* **특이출결**: KPI 카드명 `특이출결` $\leftrightarrow$ Task Prefix `[특이출결]` (유지)
* **특이근태**: KPI 카드명 `특이근태` $\leftrightarrow$ Task Prefix `[특이근태]` (유지)
* **수납확인**: KPI 카드명 `수납확인` $\leftrightarrow$ Task Prefix `[수납확인]` (유지)
* **미수납 확인**: KPI 카드명 `미수납 확인` $\leftrightarrow$ Task Prefix `[미수납 확인]` (띄어쓰기 일치)
* **일정확인**: KPI 카드명 `일정확인` $\leftrightarrow$ Task Prefix `[일정확인]` (유지)
* **교재 지급 확인**: KPI 카드명 `교재 지급 확인` $\leftrightarrow$ Task Prefix `[교재 지급 확인]` (띄어쓰기 일치)
* **교재 결제 확인**: KPI 카드명 `교재 결제 확인` $\leftrightarrow$ Task Prefix `[교재 결제 확인]` (띄어쓰기 일치)
* **교재 확인**: KPI 카드명 `교재 확인` $\leftrightarrow$ Task Prefix `[교재 확인]` (띄어쓰기 일치)

### 9-5. E2E 테스트 안정성 및 오탐 방지 정책
1. **정밀 단언을 통한 오탐 방지 (Bracket-based Assertions)**
   - `[수납확인]`과 `[미수납 확인]` 등 유사 키워드가 부분 일치하여 E2E 테스트가 오작동하는 것을 원천 차단하기 위해, Playwright Assertions 시 대괄호를 포함한 exact prefix(예: `toContain('[수납확인]')`, `not.toContain('[미수납 확인]')`)를 검증 기준으로 준수합니다.
2. **테스트 운용 효율화 가이드라인**
   - UI 라벨, 버튼 텍스트, 큐 prefix, 개별 화면 요소 보정과 같이 국소적인 변경인 경우 **전체 E2E 테스트(`npm run test:full`)의 구동을 금지**합니다.
   - 영향 범위가 특정된 단일 E2E 테스트 스펙(예: `book-warning-flow.spec.js`, `billing-warning-flow.spec.js`, `today-console-flow.spec.js`)만 개별 기동하여 빌드 시간을 단축하고 회귀 현상을 신속히 확인합니다.
   - 전체 테스트는 코어 상태 저장소 구조 개편, 대형 스키마 변경, 보안 기능 보완 등 공통 영향력이 거대하다고 증명된 경우에만 최종 배포 승인 직전 단계에서 선택적으로 수행합니다.
